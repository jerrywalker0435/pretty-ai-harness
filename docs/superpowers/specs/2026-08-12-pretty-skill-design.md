# Pretty 四阶段 Skill 设计

## 输入与范围

本设计以 `docs/prd.md`、`docs/design.md`、`docs/plan.md`、`docs/execution.md` 的反向评审结果和逐项确认的决策为输入，统一改进 Pretty 四阶段 Skill 的职责、阶段门禁、文档结构、测试策略和验证声明。

本设计覆盖：

- `pretty-writing-prd` 的需求澄清、自审和只读评审；
- `pretty-writing-design` 的技术设计、证据、决策、沟通和只读评审；
- `pretty-writing-plan` 的代码事实前置 CR、测试方案审查和只读评审；
- `pretty-executing-plan` 的基线、逐切片 TDD、增量证据、最终验证和自动审计；
- `pretty-java-spring-core` 中四阶段共享合同、模板、质量 Skill 路由、机械校验与覆盖率工具；
- 静态合同测试、校验器测试和隔离行为验证。

保持不变：

- 主流程仍是 `PRD -> Design -> Plan -> Execution`；
- `REQ/AC/DEC/TASK` 是唯一追溯体系，标准制品仍位于 `docs/pretty/<topic>/`；
- 用户批准 Design 后才能进入 Plan，用户批准 Plan 后才能进入 Execution，不增加审批状态、审批人、哈希、指纹或二次确认；
- 根目录样本 `docs/prd.md`、`docs/design.md`、`docs/plan.md`、`docs/execution.md` 只作为反向评审和行为 RED 基线，不在实施中修订或迁移；
- `ai-harness-skill-orchestration-guide.md` 不在本设计范围；
- 不自动覆盖已安装的 Skill 副本，也不自动执行 commit、push、MR、合并或发布。

本文件是同一四阶段合同的唯一活设计，不是变更日志。后续若改进同一合同中的 PRD、Design、Plan 或 Execution，应原地修订本文件，避免与既有 PRD 澄清设计重复。安装器、新阶段、远程编排或组织级审批属于独立能力，另建设计。

本轮只形成后续实施依据，不修改 Skill、模板、校验器、测试、覆盖率工具或样本文档。Plan 必须在实施时重新核实源码，确定实际文件、符号、测试与变更顺序；本设计不提前写逐文件实施清单。

## 设计摘要

四阶段使用共享合同定义边界，各阶段 Skill 只控制本阶段。PRD 锁定可观察业务结果，Design 锁定技术边界与关键决策，Plan 以真实源码形成可审查的实施合同，Execution 以逐切片 TDD、增量证据和自动审计证明实施过程与结果。

仓库事实优先自行调查；只有 PRD 或 Design 中无法由证据裁决、且会改变结果或高影响技术合同的真实选择才逐项使用 `grilling`。Plan 不调用 `grilling`，也不能残留实施决策未知。外部数据库、服务、凭证、部署或独立 Reviewer 不属于 Pretty 内部完成门禁；未验证时严格限制声明。

```text
[用户批准 PRD]
  -> [Design：事实调查、必要 grilling、锁定 DEC 与验证边界]
       !-> 外部结果仍有歧义：[返回 PRD]
  -> [用户批准 Design]
  -> [Plan：代码事实前置 CR、垂直 TASK、UT 方案]
       !-> 技术合同失效：[返回 Design]
  -> [用户批准 Plan]
  -> [Execution：采集工作区基线并运行 Plan 基线]
       !-> 基线失败：[停止并记录]
  -> [逐行为切片：一个 UT -> RED -> 最小 GREEN -> 必要重构]
  -> [受影响范围最终验证]
  -> [自动审计]
       +-- 发现问题 --> [返回切片或相应上游，修正、复验、重审]
  -> [新鲜证据核对、Execution 机械校验、交付]
```

- Agent 自审和机械校验只证明文档达到请求 Review 的条件，不能代替 Design 或 Plan 的用户批准。
- Execution 完成自动审计后直接交付，不再增加一次人工审批；后续 Git 或发布动作仍需单独授权。
- 图只提供阅读入口，正文中的阶段合同和 `DEC` 才是权威来源。

## 现状与约束

### 样本暴露的问题

`docs/prd.md` 的结构、故事、`REQ/AC` 和失败路径较完整，但仍把部分会改变外部结果的规则留给 Design，包括接收对象资格、进程退出后的 at-most-once 后果、同时间候选选择、查询与触达间状态变化和事件来源。这说明章节齐全和追溯完整不能证明需求已澄清。

`docs/design.md` 技术覆盖较完整，但核心方案、多个 `DEC`、接口字段、测试细节和质量过程平铺，缺少分层阅读入口；关键事实多用类名或表名表达，缺少团队可访问的证据锚点；上下游契约和协作事项没有集中表达。部分 `DEC` 混合多个问题，部分内部 DTO、方法、日志字段和测试操作已经接近 Plan。

`docs/plan.md` 展示大量完整候选代码，但事实、上游约束和拟议实现边界不清，任务容易按技术层横向拆分，审查者难以快速定位行为闭环、真实依赖和高风险代码。测试方案虽详细，却没有稳定约束为 UT-only，也没有清楚区分“Plan 审查测试方案”和“Execution 已执行 TDD”。

`docs/execution.md` 能记录命令和结果，但独立 Reviewer、外部环境或集成层级可能被误设为完成门禁；任务记录、终端日志和最终审计职责存在重复；如果完成后一次性补写，无法可靠证明 RED、GREEN、重构和偏差发生的顺序与归属。

### 关键仓库事实

- `skills/pretty-java-spring-core/references/workflow-contract.md` 已承载四阶段共享合同，是统一阶段边界的现有落点。
- `skills/pretty-java-spring-core/assets/templates/` 已包含四阶段模板；结构调整必须与校验器同步演进。
- `skills/pretty-java-spring-core/scripts/validate-pretty-docs.py` 已机械检查阶段文档，不能证明自然语言语义、架构判断或 TDD 真实性。
- `skills/pretty-writing-plan/SKILL.md` 当前要求大面积完整测试和生产代码、路由 `springboot-tdd`，与风险选择性展开和 UT-only 结论不一致。
- `skills/pretty-executing-plan/SKILL.md` 当前把最终独立 Reviewer 设为阻塞门禁，并默认包含更宽测试层级，与自动审计和 Pretty 内外验证边界不一致。
- `tests/test_pretty_skill_contracts.py` 和 `tests/test_pretty_core_scripts.py` 分别覆盖静态 Skill 合同和模板/校验器行为，可作为实施后的稳定机械验证边界。

以上路径只用于核验当前事实，不是实施文件清单；Plan 必须依据实施时源码解析实际改动范围。

### 设计约束

- PRD 的核心职责是产品、研发和测试澄清需求，不替 Design 选择技术实现。
- Design 用于上下游和技术团队评审，不退化为逐文件、逐方法实现计划。
- Plan 的核心职责是代码事实前置 CR 和 Execution 的实施依据，不是完整候选补丁或普通任务清单。
- Execution 的核心职责是验证并审计执行过程，不是追加式终端日志，也不是新的人工审批阶段。
- 机械校验只承担结构、编号、引用、占位符、标准路径和有限禁止项检查，不能代替语义、代码或测试质量判断。
- 简单变更仍保留本阶段固定骨架，但内容可以很短，不生成空表、虚假候选、无意义图或形式化“无影响”记录。
- 已有文档无需迁移才能被阅读；新建或主动修订的标准阶段文档使用新合同。
- 本元设计源于真实样本和 Skill 的反向评审，没有编号的上游 PRD；各 `DEC` 以已确认结论为驱动，不伪造 `REQ` 映射。

## 方案与权衡

采用“共享合同定义阶段边界、阶段 Skill 控制流程、模板提供最小骨架、风险驱动内容展开、静态检查与行为评估共同证明”的方案。

| 方案 | 优点 | 代价与问题 | 结论 |
|---|---|---|---|
| 只修改 Plan/Execution 提示词 | 改动小 | 上游验证边界、模板、校验器和质量路由仍会冲突 | 不采用 |
| 共享合同加阶段专属规则 | 边界唯一，阶段职责清楚，可独立演进 | 需要同步阶段 Skill、模板、校验器和测试 | 采用 |
| 把 Plan 写成完整候选补丁 | CR 信息最完整 | 篇幅和维护成本高，容易掩盖风险并与最新源码漂移 | 不采用 |
| 增加审批状态机、独立审计阶段和固定大表 | 流程可追踪、格式统一 | 简单任务膨胀，把格式正确误当语义正确 | 不采用 |
| 用真实集成环境证明全部风险 | 环境证据强 | 外部能力可能尚不存在，违背速度目标并错误阻塞实施 | 不采用 |
| Pretty 内坚持 UT-only，外部验证单独声明 | 快速、确定、可重复，不依赖未就绪环境 | 不能声称真实集成、部署或基础设施语义已验证 | 采用 |

采用方案的正面结果是四阶段对同一内容只有一个权威边界，Plan 审查成本与风险匹配，Execution 证据可以回溯到具体行为切片。主要代价是实施时需要把共享合同、四阶段 Skill、Plan/Execution 模板、机械规则和验证资产作为兼容单元演进。

如果未来引入真实集成验证、远程审批、组织级合规审计或新的发布阶段，应另建设计，不继续扩大 Pretty 四阶段合同。

## 详细设计

### DEC-001 PRD 与 Design 以外部结果为边界

- **决策问题：** 哪些未明确内容必须在 PRD 中澄清，哪些可以交给技术设计？
- **驱动因素与相关 `REQ`：** 产品、研发和测试必须对可观察业务结果形成同一理解；本元设计无编号上游 `REQ`。
- **候选：** 按文档章节划分；按“业务/技术”标签划分；按合理实现是否会产生不同外部结果划分。
- **采用方案及理由：** 使用“不同结果测试”：两种合理实现若都满足当前 PRD，却会产生不同外部结果，则 PRD 不完整。该标准直接面向验收结果，比章节或主观标签稳定。
- **后果：** PRD 可以保留外部等价的技术自由度，但不能把用户、身份、状态、时序、失败、重复、并发或兼容行为下放给 Design。代价是 PRD Skill 必须主动扫描高风险语义。
- **重新评估条件：** Pretty 引入独立业务规则阶段时，重新评估该边界的承载阶段。

关键词只触发语义检查，不自动判错。影响结果的“当前、有效、最新、成功、及时、幂等、最多一次、部分成功”等表述，必须定义、引用稳定口径、由用户通过场景确认，或者证明只属于外部等价技术选择。PRD 仍以 `REQ/AC` 为唯一需求合同；规则矩阵只是解释视图。

### DEC-002 事实先调查，高影响选择才逐项 `grilling`

- **决策问题：** 各阶段如何关闭抽象和未知？
- **驱动因素与相关 `REQ`：** 用户不应替 Agent 猜仓库事实，默认完整访谈又会拖慢简单任务；本元设计无编号上游 `REQ`。
- **候选：** 所有抽象都询问；一律采用最简单方案；先调查事实，仅询问无法裁决的高影响真实分歧。
- **采用方案及理由：** PRD/Design 先读取协议、领域文档、源码、配置、相邻行为和测试。存在两个以上真实答案、答案会改变业务结果或技术合同、证据无法裁决且下游否则必须代做决定时，才使用 `grilling`。
- **后果：** 一次只解决一个决策，给出具体场景、2–3 个结果、主要后果和推荐答案；确认结果写回 `REQ/AC` 或 `DEC`，不保存问答审计。代价是 Skill 必须区分事实调查和价值选择。
- **重新评估条件：** 某类问题能被稳定、团队认可的机器可读合同唯一裁决时，减少相应提问。

Design 获批时不能存在会影响 Plan 的事实未知或技术选择未知。Plan 不调用 `grilling`：业务结果不清楚返回 PRD；边界、契约或 `DEC` 不清楚返回 Design；仓库事实自行核实；低风险外部等价实现由 Plan 推荐并交用户随 Plan 一并批准。Plan 可以保留外部环境在实施时是否存在的运行时未知，但不能保留“如何实施”的决策未知。

### DEC-003 Design 锁定技术合同，Plan 展开近代码提案

- **决策问题：** Design 与 Plan 各写到什么粒度？
- **驱动因素与相关 `REQ`：** 上下游需要评审边界与代价，Plan 需要确定输入，实施又必须适应最新源码；本元设计无编号上游 `REQ`。
- **候选：** Design 只写概念；Design 写完整文件和代码；Design 锁定约束性合同，Plan 展开可审查实现提案。
- **采用方案及理由：** Design 锁定 `DEC`、模块职责、依赖方向、跨团队契约、数据与一致性、兼容策略、验证边界和剩余风险；Plan 基于真实源码提出文件、符号、行为切片、代码和测试方案。
- **后果：** Plan 不重新决定架构、契约或一致性，但可以按最新源码做外部等价调整。Design 中内部类名、短签名或伪代码默认是说明性示例；公共或跨团队契约仍具约束力。代价是作者必须标明事实、合同和示例。
- **重新评估条件：** 内部接口升级为公共或跨团队合同，或 Plan 反复因说明不足无法执行时，提升 Design 详细度。

Design 不列逐文件实施清单、完整代码、测试 fixture、Mock 操作和命令；Plan 不把 Design 的说明性例子误当源码快照。

### DEC-004 Design 与 Plan 的用户批准是阶段门禁

- **决策问题：** 何时允许进入 Plan 和 Execution？
- **驱动因素与相关 `REQ`：** 技术合同和代码提案都需要用户确认，同时流程必须轻量；本元设计无编号上游 `REQ`。
- **候选：** PRD 批准后直接进入 Plan；增加 Review 状态机；分别在 Design 和 Plan 请求一次用户批准。
- **采用方案及理由：** 用户批准 PRD 后进入 Design；批准 Design 后进入 Plan；批准 Plan 后进入 Execution。每次批准都是进入下一阶段的唯一人工门禁。
- **后果：** 不增加状态表、审批人、签名或二次确认。Design/Plan 的 Agent 自审和机械校验不能代替用户批准。Execution 不再请求完成审批。代价是对话、Git 或 MR 承载协作历史。
- **重新评估条件：** 出现组织级审计或强制审批要求时，另行设计状态和证据机制。

### DEC-005 Design 使用七章固定骨架和条件式阅读视图

- **决策问题：** 如何支持快速评审并避免简单任务膨胀？
- **驱动因素与相关 `REQ`：** 复杂 Design 需要分层阅读，固定大模板会让局部变更产生噪音；本元设计无编号上游 `REQ`。
- **候选：** 完全自由结构；所有项目使用完整矩阵；固定最小骨架并按复杂度增加视图。
- **采用方案及理由：** 固定使用“输入与范围、设计摘要、现状与约束、方案与权衡、详细设计、验证策略、风险与回退”七章；主流程图、决策索引、上下游契约矩阵按语义触发。
- **后果：** 所有 Design 有 3–6 行摘要。简单变更仍保留七章，但内容简短，不制造图、矩阵、索引或虚假 `DEC`。代价是模板和校验器需要同步升级。
- **重新评估条件：** 行为验证证明七章对简单变更仍有明显负担时，调整最小骨架。

跨两个以上模块或服务、涉及外部系统或异步链路、有三个以上处理步骤、涉及状态/事务/并发/失败隔离时增加主流程图。两个以上高影响 `DEC` 时增加决策索引；存在跨团队契约时增加契约矩阵。图固定使用 fenced `text` ASCII：`->` 表示顺序，`+-- 条件 -->` 表示分支，`!->` 表示失败或结果，`[名称]` 表示边界；禁止 Mermaid、PlantUML、Unicode 框线和绘图脚本。

### DEC-006 关键事实使用团队可访问的最小证据

- **决策问题：** 文档中的仓库和外部事实如何让评审者核验？
- **驱动因素与相关 `REQ`：** 个人工作区路径不可移植，逐句引用又会把文档变成调查日志；本元设计无编号上游 `REQ`。
- **候选：** 不提供证据；记录全部调查过程；只锚定驱动决策的关键事实。
- **采用方案及理由：** 同仓库事实使用仓库相对路径加 symbol、配置键或测试名；跨仓库事实使用团队可访问的仓库标识或稳定文档链接；正文简述关键结论。
- **后果：** 评审者能独立核验，背景事实不必逐句引用。个人绝对路径、本地私有资料和仅在作者环境成立的观察不能充当团队事实。代价是作者必须判断决定性证据。
- **重新评估条件：** 团队建立统一证据索引时，可引用该索引，但不能省略正文结论。

### DEC-007 `DEC` 与接口详细度按可挑战性控制

- **决策问题：** 哪些内容应编号为 `DEC`，接口展开到什么粒度？
- **驱动因素与相关 `REQ`：** 高影响选择需要独立挑战，普通规范和实现细节不应伪装成决策；本元设计无编号上游 `REQ`。
- **候选：** 所有技术说明都编号；完全不编号；只编号会约束 Plan、契约或演进且有明显后果的问题。
- **采用方案及理由：** 一个 `DEC` 只回答一个可独立挑战的问题，并包含驱动因素与相关 `REQ`、真实候选或决定性证据、选择与理由、正负后果和重新评估条件。
- **后果：** 仓库事实、编码规范、JDK 版本、普通映射和说明性内部类型不单独成为 `DEC`。跨团队契约需明确输入输出、关键字段、身份/幂等键、错误、兼容和验证；内部接口只写影响职责与依赖方向的最小语义。代价是不能用大量编号制造虚假完整性。
- **重新评估条件：** 普通内部选择开始影响外部兼容、跨模块方向或长期演进时，将其提升为独立 `DEC`。

### DEC-008 区分 Pretty 内外验证并限制声明

- **决策问题：** 数据库、外部服务、凭证、部署或 Reviewer 能力尚不存在时，是否阻塞 Plan 或 Execution？
- **驱动因素与相关 `REQ`：** 这些能力可能在实施阶段尚不存在；Pretty 以快速、确定的代码验证为目标；本元设计无编号上游 `REQ`。
- **候选：** Plan 前确认全部资源；Execution 等待真实环境；区分 Pretty 内外验证，外部缺失不阻塞但降低声明。
- **采用方案及理由：** Pretty 内验证仅包括 UT、mock/fake/stub、编译、快速静态检查、机械校验和适用覆盖率。真实数据库、真实服务、基础设施语义、部署、人工联调和独立 Reviewer 属于 Pretty 外验证，不是 Plan 或 Execution 完成门禁。
- **后果：** Design 识别相关风险和验证限制；Plan 继承验证边界；Execution 未验证时只记录“未验证范围”，不记录负责人、期限或审批结果，也不能把 UT 称为集成、契约或端到端验证。代价是 Pretty 完成不等于真实环境已经就绪。
- **重新评估条件：** 用户或仓库强制规则明确把某项外部验证纳入本次授权范围时，另行明确执行方式和完成口径。

不要求为了替代真实环境而创建 Testcontainers、嵌入式数据库或本地基础设施，也不要求 Execution 完成前取得人工基础设施确认。外部能力缺失不能被放入可控基线命令，因此不构成“基线失败”。

### DEC-009 各阶段只读评审严格不修改

- **决策问题：** 用户只想评估已有文档时，Skill 应如何工作？
- **驱动因素与相关 `REQ`：** 评审授权与写作授权不同，Plan 评审还必须核对标准上游链和真实源码；本元设计无编号上游 `REQ`。
- **候选：** 评审时顺手修订；复制为评审稿；严格只读并输出发现。
- **采用方案及理由：** PRD、Design 和 Plan 的只读评审都不修改、移动或复制文档，不生成下游制品，不开始实施。PRD/Design 可评估用户提供的现有文档；Plan 只接受 `docs/pretty/<topic>/plan.md`，并要求同目录 PRD、Design 和可定位真实源码。
- **后果：** Plan 非标准路径不接受、不迁移、不复制；根目录 `docs/plan.md` 仅作为本元设计的分析样本。写作模式可以自动修订由事实唯一决定的问题，只读模式只能报告。代价是用户若要修订需明确切换写作授权。
- **重新评估条件：** 标准制品路径发生整体变更时，同步修订共享合同。

Plan 只读评审固定输出：阻塞问题、重要改进、代码事实与上下游偏差、执行与验证影响、`可进入 Execution / 修正后再进入 Execution`。必须运行至 Plan 的机械校验，但失败只作为发现；“可进入 Execution”不等于用户已批准。

### DEC-010 质量 Skill 按阶段和真实风险路由

- **决策问题：** 四阶段应如何使用质量 Skill？
- **驱动因素与相关 `REQ`：** 不同阶段的产物和风险不同，无条件串行调用会制造噪音或越权；本元设计无编号上游 `REQ`。
- **候选：** 所有阶段固定运行全部 Skill；完全不使用；按阶段职责和实际风险触发。
- **采用方案及理由：** Design 只在对象职责、封装、聚合或组合/继承发生变化时使用 `121-java-object-oriented-design`；类型、SOLID、接口、模式、领域建模等按真实风险触发。Plan 必须用 `tdd` 审查测试方案，对象设计等只按拟议变更触发。Execution 用 `tdd` 实施行为切片，确有整理目标时在切片内使用 `refactor`；最终有生产代码差异时使用 `clean-code-guard`，Java 生产代码差异再使用 `java-code-review`。
- **后果：** 从 Pretty 路由移除 `springboot-tdd`。JUnit 5、Mockito、AssertJ 等写法服从 `tdd` 与最佳实践，并兼容仓库实际依赖版本，不盲目继承仓库坏习惯。纯 SQL、配置、部署、文档或机械变更不强制 Java/OOD Review。代价是阶段 Skill 必须准确判断触发条件。
- **重新评估条件：** 某类变更反复产生专门缺陷时，再增加证据驱动的专项路由。

Skill 的有效发现写入事实、决策、任务或最终审计，不保留无意义 Skill 调用清单。只有真实风险命中且缺少等价检查手段时，专项 Skill 缺失才影响结论。

### DEC-011 直接代价与剩余风险分开表达

- **决策问题：** 发布、观测、回退与 `DEC` 代价如何避免重复？
- **驱动因素与相关 `REQ`：** 评审者既要看到选择代价，也要知道剩余运行风险如何发现和恢复；本元设计无编号上游 `REQ`。
- **候选：** 每个主题独立成章；全部写入 `DEC`；`DEC` 写直接后果，风险章节写剩余风险与回退。
- **采用方案及理由：** 每个 `DEC` 记录直接正面后果、负面代价和重新评估条件；“风险与回退”只汇总跨 `DEC`、运行环境或设计无法消除的剩余风险。
- **后果：** 真实风险说明触发信号、缓解、回退和恢复验证；发布顺序和观测仅在确有配置、数据、消息、外部依赖或运行行为变化时写入该章，不设“运行就绪”。代价是作者必须主动去重。
- **重新评估条件：** 团队形成独立发布计划制品时，Design 只保留约束性发布和回退边界。

### DEC-012 Plan 是约束性实施合同与可审查实现提案

- **决策问题：** Plan 的权威性和实现自由度如何平衡？
- **驱动因素与相关 `REQ`：** Plan 既要作为代码事实前置 CR，又要允许 Execution 适配最新源码；本元设计无编号上游 `REQ`。
- **候选：** 普通任务清单；完整候选补丁；约束性实施合同加可等价调整的实现提案。
- **采用方案及理由：** Plan 约束行为、边界、任务、测试入口、独立预期值、风险和完成证据；文件、symbol、签名和关键片段是基于当时源码的可审查提案。Execution 可做不改变合同的等价调整并记录。
- **后果：** Plan 可以留下运行时环境未知，不能留下实施决策未知。改变职责、依赖方向、所有权、事务、跨模块合同或长期扩展点必须返回 Design；改变业务结果返回 PRD。代价是审查者需区分合同与源码快照。
- **重新评估条件：** 实施经常因提案歧义而改变行为或边界时，收紧相应 Plan 字段。

Plan 是单一 `plan.md`，不创建代码附件，不增加“前置 CR 结论”或“执行交接”。用户批准 Plan 本身就是前置 CR 通过并授权进入 Execution。

### DEC-013 Plan 固定五章并垂直切分 `TASK`

- **决策问题：** Plan 如何兼顾快速阅读和可执行性？
- **驱动因素与相关 `REQ`：** 按技术层或列表顺序拆分会隐藏行为闭环和真实依赖；本元设计无编号上游 `REQ`。
- **候选：** 自由任务列表；按 Controller/Service/Repository 横向拆分；固定骨架并按行为或独立风险垂直切分。
- **采用方案及理由：** 固定五章：输入与范围、实施摘要、代码事实与约束、实施任务、测试与验证。`TASK` 优先围绕可验证行为或独立风险闭环，不按技术层或 commit 大小切分。
- **后果：** 复杂 Plan 提供 3–6 行实施摘要；两个以上任务增加 `TASK -> 可观察行为 -> 主要文件/模块 -> 风险 -> 测试边界` 索引。简单 Plan 仍有五章，但可极短。代价是跨层行为可能在一个 TASK 中涉及多个文件。
- **重新评估条件：** 垂直任务无法形成独立验证入口，或真实事务边界要求联合实施时，按最小可验证闭环调整。

每个 TASK 根据适用性包含：目标行为或风险闭环、追溯落点、已核实代码事实、继承约束、拟议变更、具名行为切片、验证入口、真实任务依赖和完成证据。行为切片只用 TASK 内唯一的简短名称，不新增 `STEP/CASE` 编号。TASK 只声明真实依赖，不把列表顺序默认成全序；外部环境不是 TASK 依赖。

所有上游 `REQ/AC/DEC` 必须有真实落点，但不强制全部绑定生产代码 TASK；落点也可以是 UT、跨任务门禁或不变边界验证。

### DEC-014 Plan 区分事实、约束与拟议实现

- **决策问题：** Plan 中不同确定性的内容如何表达？
- **驱动因素与相关 `REQ`：** 把提案写成事实或把 Design 合同写成建议会误导 CR 和 Execution；本元设计无编号上游 `REQ`。
- **候选：** 混合叙述；全部视为强约束；显式区分三类内容。
- **采用方案及理由：** 区分“已核实代码事实”“上游约束”“拟议实现”。代码事实使用相对路径加 symbol/test/config；上游约束引用 `REQ/AC/DEC` 和验证限制；拟议实现说明可按合同等价调整。
- **后果：** “代码事实与约束”只列决定性内容；完整拟议文件和 symbol 放入所属 TASK，避免重复。个人绝对路径不能作为团队证据。代价是 Plan 作者需持续判断内容来源。
- **重新评估条件：** 同一信息在多个 TASK 中反复出现并造成不一致时，提升为共享决定性约束。

### DEC-015 Plan 的代码展开深度由风险决定

- **决策问题：** 作为代码 CR，Plan 是否必须展示所有完整生产和测试代码？
- **驱动因素与相关 `REQ`：** 完整代码利于审查，却会被样板淹没并与源码快速漂移；本元设计无编号上游 `REQ`。
- **候选：** 只写意图；展示完整候选补丁；按风险选择签名、关键片段或完整代码。
- **采用方案及理由：** 高风险算法、SQL、事务、并发、兼容、异常路径和复杂 UT 可以展示完整代码；DTO、getter、普通映射、导入、改名等机械内容使用签名、关键片段或变更表。
- **后果：** Plan 不要求所有片段可单独编译，但展示的签名、类型和关键代码必须与仓库一致且自洽，不能用 `...` 隐藏高风险逻辑。内部 helper、私有方法或内部 DTO 可以由 Plan 提议；不为测试暴露生产方法，也不引入无真实用途抽象。代价是审查者不能把 Plan 当完整补丁。
- **重新评估条件：** 某类省略反复导致实施偏差时，提高该风险类型的展开要求。

Plan 的代码 CR 聚焦拟议职责、依赖、契约、算法、异常、事务、SQL、安全、兼容和可测试性，不声称已经审查最终真实代码。

### DEC-016 Pretty 只能新增 UT，Plan 用 `tdd` 审查测试方案

- **决策问题：** 如何以速度优先保证测试计划和执行质量？
- **驱动因素与相关 `REQ`：** 测试计划直接决定 Execution 的切片质量，真实基础设施和宽测试层级会降低速度与确定性；本元设计无编号上游 `REQ`。
- **候选：** 沿用仓库任意测试惯例；使用 Spring 多层测试；强制 UT-only 并让 `tdd` 分别指导计划和执行。
- **采用方案及理由：** Pretty 只允许新增或扩展 UT，禁止新增或扩展集成、契约、端到端、Spring slice、`@SpringBootTest`、`@WebMvcTest`、`@DataJpaTest`、Testcontainers、嵌入式数据库或本地基础设施测试。Plan 必须使用 `tdd` 审查测试设计，Execution 才实际执行 RED/GREEN。
- **后果：** 仓库已有非 UT 测试不作为默认门禁；只有用户或仓库强制规则要求时才运行，仍不授权新增。SQL、配置、文档和纯机械修改不制造 UT，改用静态解析、编译、搜索不变量或确定性脚本；无法证明时降低声明。代价是 Pretty 不覆盖真实集成语义。
- **重新评估条件：** 速度目标或 Pretty 的授权范围发生明确变化时，另行设计其他测试层级。

UT 测试稳定业务行为单元，可以覆盖多个真实领域对象和纯内存协作者；不启动 Spring，不访问真实或嵌入式基础设施。边界外的 Repository、Gateway、Service、远程客户端、时钟等可以 mock/fake/stub，包括本方接口；被测规则使用真实对象。断言以业务结果、状态变化或完整边界请求为主，不以调用次数或顺序为主要成功标准。UT 必须快速、确定、可并行且无机器环境依赖。

Plan 为每个行为切片说明：UT 边界和 Given-When-Then 场景、独立预期值、mock/fake/stub 边界、预期 RED 原因、最小 GREEN 条件和可解析验证入口。完整 UT 代码按风险选择性展开；命令可按测试方法、类或模块集中定义并复用。Plan 不写测试、不运行 RED/GREEN，也不声称 TDD 已经发生。用户批准 Plan 即确认这些测试边界，Execution 不逐项再问。

### DEC-017 覆盖率继承政策并限制机械声明

- **决策问题：** 覆盖率门禁如何兼顾质量、工具能力和 UT-only？
- **驱动因素与相关 `REQ`：** 覆盖率不能替代场景质量，现有工具只能机械统计相对基线新增可执行行与分支；本元设计无编号上游 `REQ`。
- **候选：** 不设覆盖率；全仓统一阈值；继承仓库政策并对缺省情况设有限门禁。
- **采用方案及理由：** 优先继承仓库明确政策；无政策时，对可由 UT 覆盖的新增 Java 行为默认行 90%、分支 80%。实质修改既有行为必须有针对性 UT，但不能伪造工具没有提供的“修改行覆盖率”。
- **后果：** SQL、配置、文档、生成物和机械修改为不适用。覆盖率不能替代关键场景和失败路径，不能为了数字创建非 UT、弱断言或无价值测试。代价是修改既有代码的证明主要依赖针对性场景而非统一增量百分比。
- **重新评估条件：** 覆盖率工具能够可靠识别修改行，或仓库政策明确覆盖修改行时，扩展机械门禁。

### DEC-018 Execution 先做可控基线并保存归因证据

- **决策问题：** 如何区分历史失败、用户原改动和本次实施影响？
- **驱动因素与相关 `REQ`：** 非洁净工作区必须被保留，基线失败不能被冒充为本次成功；本元设计无编号上游 `REQ`。
- **候选：** 强制洁净工作区；忽略已有改动；采集临时归因基线并运行 Plan 指定可控基线。
- **采用方案及理由：** 先在临时目录采集执行开始 HEAD、staged、unstaged、untracked 范围和必要 diff；在尚未创建或修改 `execution.md` 时运行 Plan 指定基线。基线通过后立即创建 Execution；失败则只创建最小停止记录。
- **后果：** 不 stash、reset 或覆盖用户内容。基线默认覆盖受影响模块编译、相关现有 UT、必要快速静态检查和将修改的测试入口；任一命令失败都强制停止，不开始 TDD、不改生产代码、不自动把失败纳入修复。代价是开始阶段需要一次受控快照和基线运行。
- **重新评估条件：** 仓库提供等价且能可靠区分用户改动的执行沙箱时，可替换临时快照机制。

临时基线不进仓库，也不作为长期审计附件。最终审计比较执行前后状态；同一位置无法安全区分且有覆盖风险时停止。临时基线丢失仅在存在写入覆盖风险时停止，否则继续并声明归因限制。外部数据库或服务不存在不是基线失败，因为它们不能进入可控基线。基线恢复全绿后才可继续。

### DEC-019 Execution 逐行为切片并增量维护证据

- **决策问题：** Execution 如何证明实施过程，而不是完成后复述结果？
- **驱动因素与相关 `REQ`：** 追加日志噪音大，完成后凭记忆补写又无法审计真实 RED/GREEN；本元设计无编号上游 `REQ`。
- **候选：** 保存完整终端日志；完成后一次性写报告；逐切片增量维护可修订证据账本。
- **采用方案及理由：** Execution 固定六章：输入与基线、执行摘要、任务证据、测试与验证结果、偏差与未验证范围、最终审计与结论。每完成一个行为切片就更新所属 TASK，最终整理为可读证据账本。
- **后果：** 每个切片执行一个 UT、正确 RED、当前切片最小 GREEN；GREEN 后检查明确整理目标，确需整理时在同一切片内用 `refactor` 小步复验。记录命令、退出码、预期/实际失败摘要和通过摘要，不复制完整日志，不记录时间戳、签名、哈希链或无意义 Skill 清单。代价是 Execution 需要持续维护。
- **重新评估条件：** 自动化工具能从可信执行事件生成同等粒度且可修订的证据时，可减少人工记录。

每个 TASK 记录结果、实际相对路径与 symbol、切片 RED/GREEN/实际重构证据、实质偏差和任务完成证据。TASK 状态只有“完成”“已满足（无生产差异）”“停止”。测试首次通过时立即停止该切片并检查断言、现有实现和用户原改动：行为完整存在则记录“已满足（无生产差异）”并运行回归 UT；部分存在则只为缺失行为取得真实 RED；需要改变入口、预期或任务合同则返回 Plan。

同一稳定入口、行为和预期下遗漏的输入或错误分支，可直接补 UT 并执行真实 RED/GREEN；改变测试层级、入口、预期或新增验收语义则返回 Plan、Design 或 PRD。偏差只记录文件/symbol、任务/切片、测试边界/命令、有意义等价实现、未实施/必要新增内容和外部未验证范围，不记录 import、格式、局部变量等噪音。

Plan 是实施合同而非源码快照。Execution 开始时重新核验关键事实；等价漂移采用真实值并记录，合同失效才返回上游。多任务中途停止时保留已完成证据，当前任务停止，后续任务标记未执行，最终不能写“部分完成”；上游修订获批后从首个受影响任务恢复。

### DEC-020 最终验证后自动审计并直接交付

- **决策问题：** Execution 完成后由谁审计、审计几次、如何形成最终结论？
- **驱动因素与相关 `REQ`：** 流程到这里应自动闭环，强制独立 Reviewer 会因能力不可用而错误阻塞；本元设计无编号上游 `REQ`。
- **候选：** 完成后请求只读审计；强制独立 Reviewer；当前 Agent 自动完成一次最终审计闭环，必要时循环修正。
- **采用方案及理由：** 全部 TASK 与最终验证完成后，当前 Agent 自动审计真实最终状态。独立 Agent 是可选增强，不可用不阻塞。审计针对一个稳定最终版本执行一次；只有审计发现导致代码、测试或证据发生实质变化时，才对新最终版本重新审计。
- **后果：** 自动审计只检查，不在审计动作中直接重构或实现。行为错误返回对应 TDD 切片；行为保持结构问题返回切片并使用 `refactor`；超出合同返回上游。修正、复验后重新进入同一审计闭环。代价是最终结论依赖当前 Agent 的证据纪律。
- **重新评估条件：** 平台提供稳定独立 Reviewer 且用户明确要求将其设为门禁时，另行修改完成口径。

最终验证默认运行受影响模块编译、本次全部新/改 UT、直接相关回归 UT、快速静态检查和适用新增代码覆盖率；不默认全仓测试或已有集成测试。真实 diff 扩大影响范围时补跑新增范围，只能声称“受影响范围通过”。

自动审计核对：最终 diff 与 TASK 归属；`REQ/AC/DEC/Plan` 一致性；RED/GREEN 与真实代码/测试；基线、编译、UT、覆盖率和静态证据；实质偏差；验证声明；代码质量、安全、异常、事务和兼容风险。有生产代码 diff 时使用 `clean-code-guard`，Java 生产代码 diff 再使用 `java-code-review`；无生产代码差异时只核对任务、证据和声明范围。

最终顺序固定为：

```text
[完成切片并更新任务证据]
  -> [最终验证]
  -> [自动审计]
       +-- 有问题 --> [返回切片或上游，修正、复验、重审]
  -> [verification-before-completion 核对证据新鲜度]
  -> [写最终审计与结论]
  -> [校验最终 execution.md]
  -> [交付并停止]
```

`verification-before-completion` 位于审计后，用于核对证据新鲜度，不机械重复已经新鲜且未受变化影响的同一命令。审计后若发生影响验证的变化，只重跑受影响范围。最终审计记录采用“发现 -> 证据 -> 影响 -> 修正/处置 -> 复验”；没有实质发现时记录真实核对范围和依据，不写空泛结论。

最终状态只有“完成”“停止：<原因>”“返回 Plan / Design / PRD：<原因>”。外部未验证或独立 Reviewer 未使用不形成阻塞状态。交付后不再请求批准 Execution；commit、push、MR、合并和发布仍需用户另行授权。

### 上下游影响与契约

| 边界/参与方 | 输入输出 | 兼容方式 | 需协作事项 | 验证方式 |
|---|---|---|---|---|
| PRD -> Design | 已批准且外部结果唯一的 `REQ/AC` | 保持编号与标准路径 | Design 发现结果歧义时返回 PRD | 业务场景与跨阶段引用 |
| Design -> Plan | 已批准的 `DEC`、边界、契约、验证限制和风险 | 说明性内部示例可等价调整 | Plan 改变技术合同时返回 Design | Plan 事实、追溯和行为评审 |
| Plan -> Execution | 已批准的 TASK、行为切片、拟议实现、UT 方案和命令 | 等价源码漂移可记录 | 合同失效时返回相应上游 | 基线、逐切片证据与偏差 |
| Execution -> 用户 | 真实 diff、受影响范围验证、自动审计和未验证范围 | 不自动扩大到 Git/发布动作 | 后续动作另行授权 | 最终状态与新鲜证据 |
| 共享核心 -> 阶段 Skill | 唯一阶段边界、UT-only 和质量路由 | 阶段 Skill 只保留专属流程 | 同步消除重复或冲突 | 静态合同与隔离行为测试 |
| 阶段 Skill -> 模板/校验器 | 固定章节、编号和有限机械规则 | 旧文档仍可读，新建/主动修订采用新结构 | 同一兼容单元演进 | 模板和校验器回归 |
| 仓库版 -> 已安装副本 | 仓库版是后续实施对象 | 不自动覆盖个人安装 | 仅报告差异和安装动作 | 内容或版本差异核验 |

共享核心承载跨阶段原则；各阶段 Skill 只控制自己的输入、流程、输出和停止条件；模板提供最小骨架；校验器只执行机械规则；行为评估证明 Agent 是否按合同决策。具体文件改动由 Plan 基于实施时事实解析。

## 验证策略

验证本设计时同时使用机械测试和隔离行为测试。机械测试证明结构与有限禁止项；行为测试证明阶段判断、TDD 计划质量、执行顺序、状态和声明边界。二者不能互相替代。

### 稳定验证边界

| 风险或合同 | 稳定验证边界 | 验证原因 |
|---|---|---|
| 多个 Skill 对阶段边界表述漂移 | 静态 Skill 合同 | 可确定检查关键职责、返回规则和跨阶段继承 |
| 模板与校验器章节不一致 | 模板/校验器测试 | 验证 Design 七章、Plan 五章、Execution 六章及编号 |
| 自然语言规则被关键词规避 | 隔离上下文行为评估 | 正则不能证明 Agent 会正确判断、询问或停止 |
| 只读评审意外写文件 | 文件系统前后差异 | 必须证明没有修改、复制或生成下游制品 |
| Plan 退化为完整补丁或横向清单 | 复杂和简单 Plan 行为样本 | 验证风险展开、垂直 TASK 和分层阅读 |
| 测试计划同义反复或实现耦合 | `tdd` 测试方案行为样本 | 验证独立预期值、稳定入口和最小 GREEN |
| Pretty 偷增非 UT 测试 | Plan/Execution 行为与有限静态规则 | 验证实际提案和创建动作，而非粗暴屏蔽术语 |
| Execution 伪造 RED/GREEN 或事后补报告 | 增量任务证据与真实命令结果 | 验证每个切片的顺序、退出码和失败原因 |
| 外部能力缺失错误阻塞 | 无数据库/服务/Reviewer 的 Execution 样本 | 验证其只进入未验证范围并限制声明 |
| 自动审计直接改代码或重复空审计 | 含审计发现的 Execution 样本 | 验证返回切片、复验和稳定版本重审 |

### Skill 行为验证

实施遵循 Skill 的 RED、GREEN、REFACTOR：修改前保存当前样本输出或失败作为行为 RED，修改后用同一原始任务在隔离上下文复测。评估 Agent 只接收任务、仓库和样本，不接收本设计的诊断结论或预期答案。静态规则不粗暴全局禁用“集成测试”等关键词，因为“未验证真实集成”是合法声明；只对明确新增或扩展非 UT 测试的结构与动作做有限检查。

PRD/Design 场景至少覆盖：高风险业务词的结果歧义；一次一个高影响选择；事实充分的简单变更不过度询问；复杂 Design 触发摘要、ASCII 图、索引和契约矩阵；简单 Design 保持精简；近代码内容留给 Plan；个人路径不能作为团队证据；外部验证只形成限制而非门禁。

Plan 场景至少覆盖：

- 复杂变更按行为或风险形成垂直 TASK，事实、约束和提案明确分离；
- 高风险代码完整可审查，样板和机械代码用签名、片段或变更表，且不隐藏关键逻辑；
- 每个行为切片具有稳定 UT 边界、独立预期值、真实 RED 原因和最小 GREEN 条件；
- 不创建或扩展集成、契约、端到端、Spring slice 或基础设施测试；
- 简单 Plan 保留五章但不生成空表、图或虚假内容；
- 标准路径只读评审不改文件，非标准路径被拒绝。

Execution 场景至少覆盖：

- 采集用户原改动后运行可控基线，基线失败创建最小停止记录且不修改生产代码；
- 逐切片一个 UT 取得真实 RED 和最小 GREEN，重构只在切片内按明确目标执行；
- RED 首次通过能区分已满足、部分满足和无效断言，不伪造失败；
- 允许等价源码漂移，合同失效返回正确上游；
- 外部环境或独立 Reviewer 缺失只进入未验证范围，不阻塞完成；
- 自动审计读取真实最终 diff，发现问题返回切片或上游，修正后复验并对新稳定版本重审；
- 最终声明只覆盖实际运行的受影响范围。

通过标准：四阶段边界不冲突；Plan 可作为代码 CR 和执行依据；Execution 证据可追溯到真实行为切片；UT-only 和 Pretty 内外验证边界没有被提示词、模板或校验器绕过；新静态合同、行为评估和仓库原有测试无新增回归。

## 风险与回退

| 剩余风险 | 触发条件或信号 | 缓解 | 回退 | 恢复验证 |
|---|---|---|---|---|
| PRD/Design 对所有抽象都提问 | 简单任务出现无结果差异的连续提问 | 仅在四项 `grilling` 条件同时满足时触发 | 恢复上一版提问规则 | 简单样本不再过度盘问 |
| 固定结构造成文档膨胀 | 简单 Design/Plan/Execution 出现空表和虚假内容 | 固定骨架允许极短内容，条件视图按语义触发 | 暂停条件视图，保留最小章节 | 简单样本恢复精简且信息完整 |
| Plan 选择性代码展开隐藏风险 | 高风险逻辑用概述或省略号替代 | 对风险类型设置完整代码要求 | 恢复该类型完整展开 | CR 能独立挑战核心逻辑 |
| Plan 把提案伪装成代码事实 | Execution 因不存在路径、symbol 或签名偏离 | 强制三类来源和相对证据 | 返回 Plan 重新核实 | 提案与事实可明确区分 |
| UT-only 退化为大量 mock 交互测试 | 测试主要断言次数、顺序或复制实现 | `tdd` 审查稳定行为和独立预期值 | 删除无价值测试，回到最窄行为入口 | 行为样本可在重构后稳定通过 |
| UT-only 被误称为真实集成验证 | Execution 声称数据库、服务或部署已验证 | 强制 Pretty 内外边界和声明降级 | 撤回夸大结论 | 未验证范围与实际命令一致 |
| 基线范围过宽导致无关停止 | 默认运行全仓或外部环境测试 | Plan 只指定受影响范围和可控命令 | 收窄到受影响编译、UT 和静态检查 | 基线只反映本次可控入口 |
| 基线范围过窄掩盖真实回归 | 最终 diff 扩大却未增加验证范围 | 最终审计按真实 diff 扩展受影响范围 | 返回相关 TASK 补验证 | 新增影响范围有新鲜证据 |
| Execution 变成终端日志 | 大量完整输出但无法定位行为切片 | 增量证据账本只保留命令、退出码和摘要 | 按 TASK/切片重整报告 | 每项证据能回溯到行为与差异 |
| 自动审计变成自动重构 | 审计阶段直接改变实现且无 RED/GREEN | 审计只报告并返回切片或上游 | 撤回审计内修改，恢复切片流程 | 修正具备 TDD/重构与复验证据 |
| 模板、Skill 与校验器不同步 | 合法文档被拒或违规文档被接受 | 作为一个兼容单元发布和回归 | 整体恢复上一版合同 | 阶段模板和校验结果重新一致 |
| 静态检查制造虚假信心 | 合同文本存在但隔离行为仍违规 | 静态测试与行为 RED/GREEN 并行 | 撤回未通过行为验证的规则 | 同一原始场景稳定满足预期 |
| 仓库版与安装版漂移 | 仓库验证通过但实际调用仍是旧行为 | 报告差异和明确安装动作，不自动覆盖 | 保持安装副本不变 | 用户选择安装后独立核验版本 |

后续实施应把共享合同、相关阶段 Skill、Plan/Execution 模板、机械校验器和测试作为一个兼容单元验证。若实施发现本设计的范围约束使核心合同无法落地，必须返回 Design 说明冲突，不得由 Plan 或 Execution 静默扩展范围。
