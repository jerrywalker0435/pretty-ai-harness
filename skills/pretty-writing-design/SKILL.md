# 编写 Design

Design 把当前 PRD 和真实仓库事实转化为供上下游与技术团队评审的技术合同。它决定技术边界、职责、契约、运行时语义、模型和风险，但不替 PRD 决定外部业务结果，也不展开逐文件实施计划或完整代码。

## 输出与强依赖

- 默认写入 `docs/pretty/<topic>/design.md`，其中 `<topic>` 使用小写字母、数字和连字符。
- 用户调用本 Skill 即视为当前目录中的 PRD 可以作为 Design 输入；发现业务结果仍有歧义、冲突或占位内容时返回 PRD，不自行补全。
- 本 Skill 没有只读评审模式。用户自行 Review；Design 完成后请求 Review 并停止，不自动进入 Plan。
- `domain-modeling` 是强制外部依赖。启动 Design 时必须确认它可用；不可用时停止，不使用本地降级流程。
- 领域术语、领域模型、上下文关系或 ADR 需要处理时，必须调用 `domain-modeling`。`CONTEXT.md`、`CONTEXT-MAP.md` 和 ADR 的创建、更新、格式与决策记录全部由该 Skill 负责，Design 不直接修改这些文件。
- 默认伴随产物只有 `design.md`；由 `domain-modeling` 实际创建或更新的上下文文档/ADR 是按需伴随产物，交付时列出真实路径。
- 不修改 PRD、Plan、生产代码或测试代码，不执行实现、部署、提交、推送或合并。

## 工作流

### 1. 读取输入并建立边界

1. 宣布使用 `pretty-writing-design`，确认标准目录和当前 PRD。
2. 确认 `domain-modeling` 可用；不可用时停止。
3. 读取 PRD、仓库规则、已有领域上下文和足以支持设计的真实仓库事实。已有 `CONTEXT.md`、`CONTEXT-MAP.md` 或 ADR 由 `domain-modeling` 负责读取和维护。
4. 将内容区分为：PRD 合同、仓库事实、外部合同、Design 选择。它们相互冲突时不能静默覆盖。

### 2. 全仓发现入口，深读受影响链路

“真实仓库约束”不是凭文件名、注释或局部实现猜测，也不是逐行通读整个仓库。必须先对全仓库做入口和引用的广度扫描，识别：

- Controller/API、RPC、CLI 或其他公开入口；
- MQ Listener、Publisher、Topic 和消费组；
- 定时任务、调度注册和配置入口；
- 公开接口、Bean/模块注册、Schema/迁移和测试入口。

再对候选入口追踪 `caller → callee → Adapter → 持久化/外部系统`，深读受影响链路及其上下游契约、配置、Schema 和有效测试。与需求无关的模块不要求逐行阅读，但入口遗漏风险不能用“局部阅读”掩盖。

主 Agent 必须判断候选入口为何纳入或排除；存在多个入口且无法排除时继续查明或请求澄清，不能直接定稿。

仓库事实是证据，不自动等于应该保留的设计。既有坏味道、偶然实现和局部最优不能反向成为约束。

### 3. 领域建模门禁与长期决策（强制）

在确定 Design 结论前检查以下信号：

- 新增或重定义业务术语、事件、实体或角色；
- 新增状态、生命周期或状态转换；
- 新增身份、幂等键、归属或唯一性规则；
- 新增跨事件、工单、参与人等上下文的关系；
- 使用“当前有效、最新、历史、失效”等需要统一口径的词语；
- 一个业务规则同时影响两个以上领域上下文；
- Design 新增或改变值对象、聚合、领域事件、上下文边界或核心领域关系。

命中任一信号时，必须调用 `domain-modeling`，不能仅阅读其规范；该 Skill 不可用时停止，不使用本地替代流程。调用后必须由 `domain-modeling` 完成：

1. 读取现有 `CONTEXT.md`、`CONTEXT-MAP.md` 和相关 ADR；
2. 识别并澄清新增或冲突的领域术语和关系；
3. 术语确认后立即更新已有上下文；没有 `CONTEXT.md` 时按其格式创建根目录 `CONTEXT.md`，多上下文关系按其规则维护 `CONTEXT-MAP.md`；
4. 仍存在外部语义选择时停止设计并调用 `grilling`；
5. 未完成领域建模或上下文更新时，不得交付 Design，也不得请求 Review。

`CONTEXT.md` 只记录领域词汇、关系和不变量，不记录类名、数据库、接口或技术方案。ADR 不强制创建，由 `domain-modeling` 按“难以逆转、没有背景会令人意外、存在真实权衡”三项条件判断。Design 只消费其结果，在本次设计中记录落实方式，避免复制完整词条或 ADR 理由。

未命中上述信号时才允许跳过实际的领域建模调用，并在交付说明中记录跳过原因；`domain-modeling` 作为 Design 的强制外部依赖仍必须可用。

### 4. 关闭技术未知和冲突

- 能由代码、配置、Schema、外部合同或上下文文档确认的事实，先自行查明。
- 技术选择、职责归属、接口形状、所有权、依赖方向、一致性、事务、并发或验证边界仍不明确时，调用 `grilling`，一次解决一个高影响决策。
- Design 定稿时不得残留会迫使 Plan 再决定架构、契约、所有权、一致性或验证方式的待定项，不保留 `TODO`、`TBD`、`FIXME`、待确认或未决内容。
- PRD 与 Design 冲突且会改变业务结果或外部行为时返回 PRD。
- 仓库事实与 Design 冲突但不改变业务结果时，以证据修订 Design 或明确技术限制；如果冲突会改变所有权、依赖方向、外部合同、一致性或长期架构，必须澄清后再定稿。
- 方案比较可以保留真实被否决方案及理由，但最终必须只有已选方案，不写等待选择的 A/B 方案。

### 5. 轻量质量路由和子 Agent

质量路由只在 Design 阶段挑战技术合同，不做完整代码审查、测试执行或 Plan 拆解。每次只加载真正相关的最小集合，通常为一个主路由和一个专项路由：

| 触发风险 | 路由 |
| --- | --- |
| 领域术语、模型、上下文边界或 ADR | `domain-modeling`（强制依赖） |
| 模块接口深度、Seam、Adapter 或测试表面 | `codebase-design` |
| Java 职责、封装、聚合、组合或继承 | `121-java-object-oriented-design` 或 `solid-principles`，二选一 |
| 值对象、泛型、类型层次或 primitive obsession | `122-java-type-design` |
| 已证明存在真实构造/替换/通知/适配变化轴 | `design-patterns` |

`domain-modeling` 不可用时停止；其他专项路由不可用时由本 Skill 的 Design Contract Gate 兜底，不形成额外硬依赖。路由 Skill 只提供顾问意见，主 Agent 负责裁决并写入最终 Design。

复杂 Design 可按需启用 1～2 个只读子 Agent 做入口遗漏、链路风险或设计挑战；简单单模块 Design 不启用。子 Agent 不写 `design.md`、`CONTEXT*` 或 ADR，领域建模工作不得委托给普通子 Agent。主 Agent 负责整合、调用 `domain-modeling`、写入和最终验证，子 Agent 输出不是最终证据。

### 6. 编写技术合同

严格使用五个主章节：设计结论、方案全景、关键设计与权衡、设计边界、验证与风险。简单设计可以很短。不要增加“覆盖需求”清单；Design 不重复搬运 PRD 的 REQ/AC，也不新增替代性追溯章节。只有在某个技术选择需要背景时，才就近引用相关 PRD 或仓库事实。

#### 表达形式和权威性

按每个技术合同的主要信息结构选择最小且可核查的表达形式。不同合同维度可以使用不同形式；同一事实只能有一个权威来源，互补表达不得冲突或重复：

- 调用顺序、跨模块协作、事务或异步边界：Mermaid `flowchart` 或 `sequenceDiagram`；
- 状态和状态迁移：Mermaid `stateDiagram-v2`；
- 字段、参数、角色、错误、映射或所有权：Markdown 表格；
- 筛选、防重、并发或错误处理算法： fenced 伪代码；
- 简单线性关系或少量约束：短文本、列表或 ASCII。

图表表达流程、状态或关系；普通文字解释理由、限制、代价和重新评估条件。表达能力不足时补充另一种形式，不让单张图承担它无法表达的字段或异常合同。

#### 技术流程图

只要存在跨模块调用、外部边界、事务、异步、状态变化、并发或失败恢复，就必须有技术流程图；简单线性流程可使用很短的 flowchart/sequence diagram。纯模型、配置或局部类型变化没有真实技术流程时不制造装饰性图形。图中可使用模块、接口、Adapter、持久化、MQ、事务和外部系统，不能退化为逐文件实施步骤；相关异常路径必须表达。

#### 核心领域模型图

只要新增或改变实体、值对象、聚合、领域事件、上下文边界或核心业务关系，就必须有核心领域模型图。图只表达受影响的核心领域概念、关系、聚合边界和关键不变量，不展开 Controller、Service、Repository 或其他实现类。没有领域模型变化时不制造该图。

#### 实体图

“实体图”专指涉及持久化实体或数据模型变化时的 ER/Schema 合同。它应按需表达相关持久化实体、主键、外键、关系基数、唯一性、可空性、生命周期和兼容影响；只列本次相关字段，不罗列全库。只有领域实体变化而没有持久化关系变化时，核心领域模型图足够，不重复画实体图。接口 DTO 和消息体放在边界合同中，不称为实体图。

#### 外部边界合同

对外提供或调用的 HTTP/RPC、监听或发送的 MQ、定时任务必须详细描述。边界表至少区分：

| 边界 | 方向/触发 | 领域/契约所有者 | 技术承接方 | 输入及来源 | 输出/结果 | 失败与运行时语义 |
| --- | --- | --- | --- | --- | --- | --- |
| API、RPC、MQ 或定时任务 | 谁触发、同步/异步 | 谁定义业务语义、不变量或消息含义 | 谁负责接入、转换、发送、消费或调度 | 字段、消息体及获取逻辑 | 返回、状态或后续消息 | 错误、超时、重试、幂等、顺序、并发、恢复 |

专项合同：

- HTTP/RPC：方法、路径/服务名、请求响应、错误语义和鉴权要求。
- MQ：Topic、消息键、消息体、生产/消费方向、确认、重复消费、顺序、重试和死信。
- 定时任务：调度频率、触发条件、重复执行、并发运行、失败恢复和补偿。

“所有者”不是离边界最近的类。领域/契约所有者由上下文、外部合同、业务状态和不变量确定；技术承接方由真实接入、转换或调度实现确定。证据冲突时不能按模块名猜测。

系统实现层必须评估兼容性：接口、MQ、Schema、配置、部署、共享消费者和历史数据均需判断是否存在兼容约束。不要求每次都实现旧版本兼容；如果旧版本或旧消费者明确不再需要，可以明确写出本次不提供旧版本兼容。Skill 文档自身不要求兼容旧版 Design 格式。

#### 运行时语义与非功能设计（按需）

非功能要求不是“验证与风险”中的一句泛泛提醒；只要本次设计受其影响，就必须在 Design 中形成明确的非功能设计合同。按场景触发：

- **兼容性**：接口、MQ、Schema、配置、部署、共享消费者或历史数据存在新旧协作约束时，明确兼容策略、切换边界和回退限制；旧版本明确不再需要时，明确写出不提供旧版本兼容。
- **安全**：涉及认证、授权、租户隔离、敏感数据、数据脱敏、审计或合规时，明确信任边界、责任方、允许/拒绝条件、数据处理和审计语义。
- **并发与一致性**：存在竞态、重复请求、重复消息、顺序、锁、幂等、事务或跨边界一致性时，明确冲突胜者、原子性、隔离、重试、防重、补偿和恢复语义。
- **性能与可用性**：存在延迟、吞吐、容量、超时、资源上限、降级或可用性约束时，明确约束、设计措施、失效行为和恢复方式。
- **可观测性与运行恢复**：需要日志、指标、追踪、告警、回滚、数据保留或灾备时，明确事件所有权、敏感信息边界、告警条件和恢复验证。

每个被触发的主题至少说明：约束或目标及其依据、设计措施与责任边界、失败/降级/恢复语义、可观察的验证面。没有依据不编造 QPS、延迟或可用性数字；没有触发主题时不创建该小节，也不输出“无”清单。

除上述非功能设计外，只要相关，还必须明确状态迁移、成功/失败结果、异常传播、超时、重试、降级、幂等、防重、顺序、事务、一致性、回滚、补偿和恢复。

### 7. Design Contract Gate

质量路由之外，定稿前必须通过本地 Design Contract Gate：

- 全仓入口发现和受影响链路完整，关键结论有足够证据；
- 模块职责、依赖方向、领域/契约所有者和技术承接方明确；
- 外部边界的输入、输出、失败、副作用和系统兼容性判断明确；
- 相关的状态、事务、一致性、幂等、并发、恢复和非功能语义已形成具体设计，而不是只写风险或验证提醒；
- 技术流程图、核心领域模型图、实体图与表格和文字一致；
- 不存在会迫使 Plan 再决定架构或契约的未知项；
- 未为完整性制造多余模式、接口、抽象、兼容层或图形；
- Design 不改变 PRD 的外部结果，也不提前写 Plan 的逐文件任务、完整代码或测试实现。

这是 Design 合同校验，不是代码质量自评。Gate 不通过就修订或澄清，不把问题推给 Plan。

### 8. 验证、自审和交付

“验证与风险”只定义需要证明什么，不写完整测试代码、fixture、执行命令或执行结果：

- 指出必须证明的流程、状态、边界、异常、幂等、并发或一致性语义；
- 指出观察面：接口结果、状态变化、消息、持久化、日志/指标或外部交互；
- 指出适合的单元、集成、契约或运行环境验证边界；
- 记录无法验证的范围、原因、风险和缓解方式。

自审 Design 的合同一致性、领域文档/ADR 结果、图形与表格、未知项、越界实现和质量 Gate。然后运行：

```bash
python3 <pretty-writing-design>/scripts/validate_design.py \
  docs/pretty/<topic>/design.md
```

交付时说明 Design 路径、主要技术结论、`domain-modeling` 实际变更的文档路径和校验结果，请求用户 Review 后停止。不得自动创建或修改 Plan。

## 红线

- 不提供独立只读评审模式；不代替用户完成 Review。
- 不替 PRD 决定外部业务结果。
- 不在 `domain-modeling` 不可用时本地模拟其职责。
- 不由 Design 直接创建或更新 `CONTEXT.md`、`CONTEXT-MAP.md` 或 ADR。
- 不保留“覆盖需求”清单、待定技术选择或占位内容。
- 不为满足模板完整性制造技术流程图、领域模型图、实体图、模式、接口或兼容层。
- 不把技术流程图伪装成逐文件实施计划，不写完整生产代码或测试实现。
- 不把仓库现有坏味道当作技术约束，不用局部实现替代全链路证据。
- 不自动进入 Plan、执行代码、运行项目测试或进行 Git/部署动作。
