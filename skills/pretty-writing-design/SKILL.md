# 编写 Design

把 PRD 和真实仓库事实收敛为可评审、可执行的技术合同。Design 定义外部边界、职责、数据所有权、依赖方向、运行时语义、模型、风险和行为级实施影响；不选择业务结果，不复制完整源码，也不证明真实实现质量。

## 输入与交付

- 读取或复用同目录 `prd.md`（含其“Design 交接”定位快照）和 [Design 模板](assets/design.md)，
  以已确认的公共入口和测试为起点；快照只作当前仓库定位线索，不替代 Design 合同。只读取本次
  合同实际触发的 Context/ADR、构建配置、Schema、外部协议和真实代码，不猜测 API、Schema 或依赖。
- 默认写入 `docs/pretty/<topic>/design.md`，topic 使用小写 kebab-case。完成后停止，请用户
  Review；后续由用户调用 `$pretty-executing`，明确指定 `Plan` 时生成实施计划，否则直接执行。
- 交付只报告机械校验结果并等待用户 Review；不生成 Reviewer receipt，不启动独立 Reviewer，
  不用构建、测试或覆盖率证明 Design。

## 调查快路径与并行

Design 只获取关闭技术合同所缺少的知识。以下是互斥路径，不是必须依次执行的阶段：

1. **同会话热路径**：PRD、合同决定、公共验证入口和影响锚点已经读取且未变化时，直接写入或
   更新 `design.md`，不再做新鲜度确认或确信性搜索。
2. **已知入口路径**：在一个只读批次中并行读取 PRD、模板、入口及规则所有者、公共测试，以及
   被合同触发的直接边界事实；随后立即落稿。
3. **入口未知路径**：先读取 PRD 和模板，再按“已知 Symbol → 受影响模块精确搜索 → 全仓精确
   搜索”定位入口；定位后用一个并行批次读取完整受影响链路。前一级能够定位时不得升级。

修改已有 Design 时使用差量路径：只重新调查用户反馈或 PRD 变化影响的 `REQ/AC/TASK`、对应
锚点和边界；未受影响的合同直接保留。任何路径都不创建调查报告、仓库快照或证据清单。

入口已知后，将相互独立的读取合并到同一批次：生产入口与规则所有者、公共行为测试、直接
caller/callee，以及按需触发的事实。只有跨上下文术语、所有权或既有架构决定变化时读取
Context/ADR；只有模块归属或依赖 API 需要确认时读取构建配置；只有持久化或外部边界变化时
读取 Schema、Adapter 和外部协议。不能指出要关闭的合同缺口时不读取。

PRD 的“Design 交接”若标为“已核验”，直接进入已知入口路径：在同一并行批次读取其列出的
`REQ/AC → path#symbol`、公共测试和本次合同触发的边界事实，并核验路径与 Symbol 的新鲜度；不
重新证明 PRD 已关闭的业务语义。若交接缺失或只有部分定位，只定位缺失项并沿
受影响链路补齐。快照中的路径或 Symbol 失效时只围绕失效项定向重定位；普通重命名、迁移或
测试文件移动不返回 PRD，只有当前外部行为、业务结果或验收语义发生冲突才返回 PRD。核验后的
定位直接写入 Design 既有“公共验证入口”和“影响锚点”，不复制快照章节、不创建对账报告。

默认不安排第二次调查。若仍有会改变业务结果、外部合同、不可逆 Schema、数据所有权、依赖方向
或一致性语义的未知项，只选择一次定向补证或一次用户澄清；普通命名、文件选择、同类实现数量、
参数调优和非必要运维扩展不触发补证。补证没有关闭缺口时停止，不继续搜索。用户明确要求忽略
Git 历史时，不读取提交、分支、标签或历史差异。

## 收口与 Execution 交接

每个 `REQ/AC` 已归属结果 TASK，每类公共入口已有真实职责链，输入信任边界、成功与可区分失败、
查询/命令及副作用、协议可见类型、外部边界、所有权、依赖方向、事务/幂等语义和验证观察面均已
关闭，且不存在合同级未知项时，调查立即收口。直接生成最终形态，不先落空模板，也不把“完整
初稿后全文精简”作为独立步骤。

调查结果只写入模板既有位置：

- `实施影响` 只写供人工评审的结果 TASK：对应需求、结果、输入与不变量、失败语义和验证观察面。
- 文档末尾单独设置 `Executing 定位与交付`，只写供后续执行使用的内容：变更职责链路、公共验证
  入口、影响锚点、Execution 交付、人工运维产物和依赖；按相同 TASK ID 与 `实施影响` 对应。
- `公共验证入口` 标记“现有”或“新增”，并使用 `仓库相对路径#symbol`；`影响锚点` 按链路顺序
  标记“现有”或“新增”的 `仓库相对路径#symbol`，至少覆盖入口和规则所有者，适用时覆盖
  Adapter、持久化点或外部边界。
- `Execution 交付` 在同一字段写明构建根或模块，以及 `Add/Modify/Test/DDL` 文件路径；配置数据
  DML 和人工操作只写入 `人工运维产物`。
- 只交接技术合同和定位，不复制完整源码、行号、Git 哈希或调查过程。

已批准 Design 中的业务结果、失败语义、不变量、所有权和依赖方向是 Execution 的权威合同；
公共验证入口、影响锚点、交付文件和构建模块是候选执行范围。Execution 只检查这些易变仓库事实
是否仍然有效，不得重新读取 PRD、Context 或 ADR 来证明同一知识。

## Design 合同门禁

- 会改变业务结果、外部可见合同、不可逆 Schema、数据所有权、依赖方向或一致性语义的未知项必须在 Design 关闭；业务语义不明返回 PRD，缺少必要用户决策时停止并请求澄清，不能把未知项推给 Execution。类名、文件名、同类实现数量以及可由现有规范直接决定的普通实施细节不构成调查阻塞项，应在 Design 中给出一致选择或列为候选影响锚点。
- 只描述一次真实受影响链路：入口 → caller/callee → Adapter → 持久化或外部系统。设计边界只表达系统与外部参与者、服务、消息基础设施和调度器的合同；内部模块和逐方法调用树属于实施影响。
- 不写完整 Java、完整测试、执行命令、执行结果、覆盖率数字或质量自评。配置数据 DML、事件定义、模板关系、白名单、种子/reference data、激活/禁用/回滚由人工运维负责；结构性 DDL 只能声明为代码库文件交付且不执行。
- Design 不得要求新增无领域归属的通用规范化 Helper（如 `normalizeText`），也不得用 `continue`、空值降级、步骤注释等普通实现指令削弱共享质量规则；例外必须绑定具体 Symbol 和可核查仓库事实。

## ADHD 友好的最小充分表达

将 `$i-have-adhd` 的“结论先行、降低工作记忆负担、抑制旁支”固化为最终 Design 的产物规则，而不是依赖它在当前会话中已启用。用户启用该 Skill 时，它还负责对话和交付消息的形态；“首行给出下一动作”和“五项列表上限”不机械套用于文档，技术合同和 `REQ/AC` 覆盖优先于篇幅。

- 完整性按业务结果可追溯、合同维度已关闭、失败可区分、职责与依赖明确、验证入口和影响锚点可执行来判断，不按解释长度、图表数量或 TASK 数量判断。
- 每个事实只设一个权威落点：设计结论写方案、边界和代价，方案全景写关系，关键设计写决定与依据，设计边界写外部合同，实施影响 TASK 写人工可读结果，文档末尾的 Executing 小节写定位与交付，验证与风险只写验证层级、未验证范围和重要风险；其他位置只保留 `REQ/AC`、Symbol、路径或具体标题等追溯引用，不换句话重复语义。
- 使用能承载合同的最小形式：同一语义只选图、表或文字中的一种解释载体；删除不适用的可选小节；图只保留受影响节点，模型和 Schema 只保留相关字段，每个 TASK 字段优先一行并使用 `REQ/AC`、`path#symbol` 和文件路径表达精确关系。
- 共享同一可观察结果、信任边界、失败语义和公共验证入口的需求合并为一个 TASK；任一维度需要独立实现或验证时必须拆分，不能为减少 TASK 数混合不同职责链路。TASK 必填字段仍须明确；引用前文时使用具体标题或表格行，并补充本 TASK 的差异，禁止写“同上”。
- 成稿时不写任何不改变设计决定、外部边界、不变量、失败语义、所有权、追溯、验证或风险的
  句子，包括调查过程、源码复述、教程、通用最佳实践和重复验收描述；不设置会迫使遗漏合同的
  总字数上限。

## 固定文档结构

最终文档严格使用以下七个二级章节：

1. `设计结论`
2. `方案全景`
3. `关键设计与权衡`
4. `设计边界`
5. `实施影响`
6. `验证与风险`
7. `Executing 定位与交付`

`实施影响` 必须包含至少一个结果 TASK；文档末尾的 `Executing 定位与交付` 必须包含对应的变更
职责链路和同一组 TASK ID。TASK 字段以
[Design 模板](assets/design.md) 为唯一结构定义，按可观察结果垂直拆分，不按
Controller/Service/Repository 横向拆分；每个 PRD 需求和验收标准都要对应，明确非实施项除外
并说明原因。

## 文档校验与用户 Review

写入后只运行一次 `scripts/validate_design.py`，检查章节、TASK 字段、REQ/AC 覆盖、占位内容、
Mermaid 和 DDL/DML 归属。校验失败只修正文档并重跑校验，不重新调查仓库。它不检查生产代码、
测试执行、覆盖率或运行质量。

## 红线

- 不创建 `execution-plan.md` 或新的规范阶段。
- 不修改 PRD、生产代码、测试代码、配置数据或治理文档；Context/ADR 由 `domain-modeling` 维护。
- 不把逐文件实施计划冒充设计边界，不保留占位词、待定技术选择或未经 PRD、外部协议或真实仓库事实支持的兼容承诺。
- 不把配置数据 DML、发布、部署、激活、回滚或数据库执行分配给 Execution。
