# 编写 Design

把 PRD 和真实仓库事实收敛为可评审、可执行的技术合同。Design 定义外部边界、职责、数据所有权、依赖方向、运行时语义、模型、风险和行为级实施影响；不选择业务结果，不复制完整源码，也不证明真实实现质量。

## 精简辅助：i-have-adhd（可用时默认使用）

开始工作前，若 `$i-have-adhd` 可用则加载并应用其规则；同一会话已加载且仍生效时直接复用。
加载成功后将其用于对话、交付消息以及组织正文和检查冗余。未安装或无法加载时继续执行，
使用本 Skill 的内置精简规则，不把它作为阻塞条件。

若已加载该 Skill，对话和交付消息遵循其规则；Design 正文始终按本模板与下方精简规则保留完整技术合同，
不机械套用首行操作或五项列表上限，不因此省略必填图、接口映射、DDL 或 TASK。

## 输入与交付

- 读取或复用同目录 `prd.md`（含其“Design 交付”定位索引）和 [Design 模板](assets/design.md)，
  以已确认的公共入口和测试为起点；索引只作当前仓库定位线索，不替代 Design 合同。只读取本次
  合同实际触发的 Context/ADR、构建配置、Schema、外部协议和真实代码，不猜测 API、Schema 或依赖。
- 先按下方流程给出 2～3 个技术方案简述，用户确认具体方案后才生成详细 Design。默认写入
  `docs/pretty/<topic>/design.md`，topic 使用小写 kebab-case。完成后停止，请用户
  Review；后续由用户调用 `$pretty-executing`，明确指定 `Plan` 时生成实施计划，否则直接执行。
- 交付报告合同自检与机械校验的实际结果并等待用户 Review；不生成 Reviewer receipt，不启动独立 Reviewer，
  不用构建、测试或覆盖率证明 Design。

## 新增必要性与复用边界

本 Skill 遵循“非必要、勿新增”：先复用已有的领域概念、规则所有者、职责、边界，
只有 PRD/合同要求或当前技术边界确实无法由现有承载表达时才新增模型、抽象、章节、图、表、
文件或设计产物。新增项必须有当前用途，并能说明独立规则、不变量、生命周期、外部协议、迁移前提、
验证观察面或其他必要契约；纯包装、转发、重复决策、未来扩展预留和排版偏好都不足以构成必要性。

必要性结论写入已有 Design 正文章节，交付索引只引用该位置，不新增复用清单、调查报告、决策清单或审查阶段。仅在
当前合同实际触发时保留可选章节；不适用的章节、图表和字段删除。`Context/ADR` 由 `domain-modeling`
按其自身必要性规则维护，Design 不因记录方便而新建它们；校验过程的临时输出只在命令需要时产生，
不作为 Design 交付物。

## 固定流程与查证边界

严格执行 `PRD 提取 → 方案定向查证 → 2～3 个方案简述 → 用户确认 → 选定方案补证 → 写 Design → 校验 → 停止`：

读取或复用 PRD 后，先提取“背景与问题”“目标与非目标”，以及影响实现的业务结果、外部
边界、数据所有权、依赖方向、一致性和失败语义；只定向查证形成可行候选方案所需的仓库事实。

在对话中提供 **2～3 个**有实质技术差异、符合 PRD 和仓库约束的方案，每个用一小段或一行
表格简述核心实现思路、复用与改动范围、主要收益和代价；标明推荐方案及决定性理由。不得用
同一方案的改名、违反 PRD 的方案或明显不可行的方案凑数；约束不足以支持两个可行方案时，
说明具体限制并请求澄清，不自行进入详细设计。

给出简述后明确请用户选择或确认具体方案，等待回复。确认前不生成或改写 `design.md`，不
展开详细流程、模型、接口、DDL 或 TASK；PRD 已批准、推荐方案或用户沉默均不代表方案已确认。
同一会话已明确确认且仍适用的方案直接复用，不重复询问。确认后只围绕选定方案补齐技术合同，
在“设计结论”写明选定方案及依据；若新事实使该方案不可行或需改变核心技术方向，更新
2～3 个方案简述并重新取得选择。方案讨论保留在对话中，不创建前置分析文件或独立决策清单。

方案优先复用现有领域概念、规则所有者和能力，再在原职责内扩展；拟新增模型或抽象时按下方
“Design 合同门禁”核验必要性。优先使用已读事实，必要补证只沿受影响链路及所属模块定向
核验定义、调用方和边界，不为证明不存在可复用实现做全仓盘点。

Design 只获取关闭技术合同所缺少的知识。以下是互斥路径，不是必须依次执行的阶段：

1. **同会话热路径**：PRD、用户确认的方案、合同决定、公共验证入口和影响锚点已经读取且未变化
   时，直接写入或更新 `design.md`，不再做新鲜度确认或确信性搜索。尚未确认方案时先完成上述选择。
2. **已知入口路径**：在一个只读批次中并行读取 PRD、模板、入口及规则所有者、公共测试，以及
   被合同触发的直接边界事实；用户已确认方案且关键合同已关闭时立即落稿，否则先完成方案选择
   或按下方规则定向补证。
3. **入口未知路径**：先读取 PRD 和模板，再按“已知 Symbol → 受影响模块精确搜索 → 全仓精确
   搜索”定位入口；定位后用一个并行批次读取完整受影响链路。前一级能够定位时不得升级。

修改已有 Design 时使用差量路径：只重新调查用户反馈或 PRD 变化影响的 `REQ/AC/TASK`、对应
锚点和边界；未受影响的合同直接保留。已有确认仍适用时直接修订；需要改选核心技术方案时先
重新提供 2～3 个简述并等待确认。任何路径都不创建调查报告、仓库快照或证据清单。

入口已知后，将相互独立的读取合并到同一批次：生产入口与规则所有者、公共行为测试、直接
caller/callee，以及按需触发的事实。只有跨上下文术语、所有权或既有架构决定变化时读取
Context/ADR；只有模块归属或依赖 API 需要确认时读取构建配置；只有持久化或外部边界变化时
读取 Schema、Adapter 和外部协议。不能指出要关闭的合同缺口或具体复用疑点时不读取。

PRD 的“Design 交付”提供定位时，直接进入已知入口路径：在同一并行批次读取其列出的
`REQ/AC → path#symbol`、公共测试和本次合同触发的边界事实，并核验路径与 Symbol 的新鲜度；不
重新证明 PRD 已关闭的业务语义。若索引缺失或只有部分定位，只定位关闭技术合同所需的缺失项并沿
受影响链路补齐。索引中的路径或 Symbol 失效时只围绕失效项定向重定位；普通重命名、迁移或
测试文件移动不返回 PRD，只有当前外部行为、业务结果或验收语义发生冲突才返回 PRD。核验后的
定位直接写入 Design 的交付索引；将 PRD 的“背景与问题”“目标与非目标”纳入 Design 同名
章节，保留已确认的问题、目标和排除边界，可等义精简，不复制 PRD 全文、不创建对账报告。

不重复调查已关闭的合同。若仍有会改变业务结果、外部合同、不可逆 Schema、数据所有权、依赖
方向或一致性语义的未知项，只围绕该缺口定向补证；读取批次数不能替代合同完整性判断。可由
PRD、已核验协议和项目规范决定的普通技术细节在用户选定方案内直接确定，不替用户完成前置
方案选择；业务规则、预期行为或其他必要用户决策不明确时请求澄清。普通命名、文件选择、
参数调优和非必要运维扩展不触发补证。没有新的可查证线索、事实不可取得或必须由用户决定
时，指出缺少的具体决定及影响并停止，不把未关闭
的合同交付为可执行 Design。没有新的关键决策需要验证时必须结束调查。用户明确要求忽略 Git
历史时，不读取提交、分支、标签或历史差异。

## 收口与 Executing 交付

以下条件全部满足后立即收口：

- 需求范围已覆盖，每个适用的 `REQ/AC` 已归属结果 TASK；
- 用户已确认具体技术方案，影响行为或实现方向的核心技术选择已经确定，且关键变更的现状、
  目标和修改或迁移方式一致；
- 主要风险和必要假设已经说明；
- 没有影响行为的技术问题悬而未决。

不影响行为或核心技术选择的剩余实现细节交给 Execution，不继续阻塞 Design。直接生成最终形态，
不先落空模板，也不把“完整初稿后全文精简”作为独立步骤。

调查结果只写入模板既有位置：

- `实施影响` 写供人工评审的结果 TASK，说明对应需求、结果、输入与不变量、失败语义和
  验证观察面；职责协作由“方案全景 → 技术流程”表达，不另设链路小节。
- 文档末尾设置 `Executing 交付`，与 PRD 的 `Design 交付` 统一使用
  `关联项 | 关键内容 | 定位` 三列表格。交付只帮助下一阶段找到已确认的合同与仓库事实，
  不替下一阶段决定实现。
- 以 TASK ID 关联 `实施影响`，每个 TASK 至少定位其结果合同；按需补充关键设计小节、已读取的
  影响锚点和公共验证入口。文档内使用 `章节 → 具体标题`，仓库内使用 `仓库相对路径#symbol`，
  每个定位独占一行；同一内容不在交付重复定义。
- 只列已知定位，不写现有/新增标记、定位状态或空项；不为填表搜索、虚构未来文件或 Symbol。
- 新增、修改或删除哪些文件、类型拆分、测试补充、构建模块和 TASK 实施顺序由 Executing
  根据合同与仓库事实决定，不在交付中列 `Add/Modify/Test/DDL` 文件清单或实施安排。
- 配置数据 DML 和人工操作的责任与必要前提写入 `设计边界`；DDL 语句在 `方案全景` 定义，
  需要导航时只索引相应小节，不预定文件落点。交付不复制源码、行号、Git 哈希或调查过程。

已批准 Design 中的业务结果、失败语义、不变量、所有权、依赖方向、公共/外部协议及明确的
事务、并发、幂等、安全约束是 Execution 的权威合同；交付索引只定位该合同与现有仓库事实。
具体文件、构建模块、类型和方法拆分由 Executing 在合同和授权范围内确定。
必须保留的文件、symbol、签名或装配应在对应决定处明确要求及依据，交付索引引用该决定；仅在
图或示例中出现不等于必须保留该实现结构，图中表达的领域语义和边界仍须保持。
Execution 可核验易变仓库事实和具体复用疑点，将等价简化的实际落点与依据写入执行记录；
无法在当前授权和合同内解决的变化返回 Design，不自行改写上游文档，也不重新读取 PRD、
Context 或 ADR 来证明同一知识。

## Design 合同门禁

Design 描述目标状态，现有代码尚未具备目标能力是预期变更。对涉及版本、状态机、幂等、
Schema 或外部恢复协议的变更，在既有模型、关键设计或边界章节说明“当前承载 → 目标语义 →
修改或迁移方式”。以下仅检查本次触发项，每项只写一次，交付索引引用对应决定：

- 概念复用与新增必要性：拟新增模型或抽象时，在“核心领域模型”或“关键设计与权衡”说明
  现有承载及复用/扩展选择；确需新增时引用相关 `path#symbol` 或边界事实，说明现有能力
  为何不足，以及新增概念承担的独立规则、不变量、生命周期或必要契约。无现有承载时说明
  本次需求与边界依据，不虚构锚点。只有包装、转发或重复决策且无独立语义时合并或省去，
  不为未来变体预设抽象；名称或字段相似不足以合并不同身份、生命周期、所有权或协议边界。
  结论写入已有章节，不新增复用清单、调查报告或审查阶段。
- 字段与版本：明确本次新增或修改的领域字段及映射对应的持久化字段与复用或新增选择；版本的作用域、初始化、
  递增触发、条件更新、重试及结果回写是否递增、外部版本来源必须明确。改变已有版本来源
  时说明历史数据与远端已接受版本的衔接；写“DDL 无”必须与字段映射和迁移方案一致。
- 领域模型与 ER 边界及值对象持久化：领域模型与 ER 实体不是一一对应关系。`核心领域模型`
  用 `classDiagram` 表达领域实体、值对象及业务关系；`持久化实体` 的 `erDiagram` 只针对
  领域实体及其持久化关系建模，不因值对象有独立类型就把它提升为 ER 实体或单独关系。值对象
  默认作为所属领域实体的字段说明映射。值对象为一对多时，必须评估预期基数/数据量、增长
  趋势、是否需要独立增量写入或查询；数据量不大且没有独立业务增量时可将其序列化为所属
  实体的一个 JSON 字段，并明确序列化结构、默认/空值、版本兼容、查询与索引限制。数据量大
  或需要独立业务增量时，说明采用独立持久化结构（如子表）或其他现有方案的依据、映射、
  一致性和迁移前提，但没有独立身份、生命周期或规则时仍不要把值对象虚构为领域实体。
- 表结构：新增、修改或删除表、列、索引、约束时，必须在“方案全景 → 持久化实体 → 表结构变更 DDL”
  中直接提供完整的 `sql` 代码块，覆盖本次全部结构变更。沿用仓库已知的数据库产品与 SQL 方言，
  使用真实表名、字段名，允许不带库名前缀的表名，不强制 `USE` 或环境库名映射。实际业务库名
  和 MySQL 等数据库的环境版本不是 Design 必填信息，不因缺失而追问、补证或阻塞生成，也不猜测。
  多数据源时按逻辑数据源或业务归属区分结构变更；实际连接库由人工运维在执行数据库变更前选择。
  使用版本相关语法时说明兼容性假设与人工验证事项，不要求补齐环境版本。已有表提供增量 DDL，
  说明适用的执行顺序、历史数据兼容或迁移前提，不能只写字段表或 SQL 文件路径。
  DDL 是可评审的设计合同，不在 Design 阶段执行。
- 状态与幂等：明确合法源状态、目标状态、重复或终态请求结果、原子更新范围，以及幂等键
  在重试和新业务操作中的复用或更新规则；不能只写“单调”“幂等”或“最终一致”。
  涉及重复提交、消息重复投递、重试、并发重复执行或幂等规则变化时，在“关键设计与权衡”
  保留“幂等设计”，按模板说明去重承载、并发及重复结果和适用的外部副作用恢复责任；其他
  章节已定义的状态、约束或协议使用具体标题引用。未触发时删除该小节。
- 对账与补偿：区分已有查询能力和待新增编排，明确核对对象、查询窗口与分页、差异判定、
  补偿操作及失败后续跑语义；覆盖本地存在而远端缺失的发现路径。失败重试不能替代需求
  指定的差异对账。外部 API 和字段须有协议或仓库事实支持。

- 验证归属按下方“验证边界”执行；需要外部证明的事实不等于 Execution 的验收条件。
- 会改变业务结果、外部可见合同、不可逆 Schema、数据所有权、依赖方向或一致性语义的未知项必须在 Design 关闭；业务语义不明返回 PRD，缺少必要用户决策时停止并请求澄清，不能把未知项推给 Execution。类名、文件名、同类实现数量以及可由现有规范直接决定的普通实施细节不构成调查阻塞项，交给 Executing 决定。
- 真实受影响的技术链路只在“技术流程”描述一次：入口 → caller/callee → Adapter → 持久化或外部系统。业务流程表达业务动作及系统间交接，设计边界表达系统与外部参与者、服务、消息基础设施和调度器的合同；已读取的文件与 Symbol 定位写入 Executing 交付索引，不展开逐方法调用树。
- `外部边界合同` 放在 `非功能设计` 之前，对 HTTP、RPC、MQ 接口本次新增或修改的参数及映射逐项说明来源、目标字段及映射规则；覆盖请求、响应和消息中的变更，未变化部分按需引用已有协议，具体字段与表达要求以 [Design 模板](assets/design.md) 为准。
- 不写完整 Java、完整测试、执行命令、执行结果、覆盖率数字或质量自评；上述 DDL 代码块属于必需的设计内容。配置数据 DML、事件定义、模板关系、白名单、种子/reference data、激活/禁用/回滚由人工运维负责；Execution 按设计交付结构性 DDL 文件，不执行数据库变更。
- Design 不得要求新增无领域归属的通用规范化 Helper（如 `normalizeText`），也不得用 `continue`、空值降级、步骤注释等普通实现指令削弱共享质量规则；例外必须绑定具体 Symbol 和可核查仓库事实。
- 必要的业务原因、隐含约束、调用合同和兼容取舍注释（含合同 JavaDoc）不属于步骤注释。Design
  应说明这些语义及必要的运行观测结果；Execution 按信息缺口主动补充注释与日志，不以 Design
  是否逐项要求为前提，也不要求每个方法添加注释或日志。

## 验证边界

- Execution 的验收限定为不依赖真实数据库、外部服务或部署环境的单元/行为测试及既有编译、
  覆盖率门禁；不以非 UT 测试或外部环境验证作为 Plan/Execution 的前置条件或完成条件。
  HTTP/Dubbo、adapter 的协议映射可通过本地隔离测试验证，不由“契约测试”名称推导真实联调。
- 真实事务提交、数据库唯一约束、repository 查询集成测试、SQL 执行计划和设备/服务联调归人工
  外部验证。在“验证与风险”使用独立的 `- 人工外部验证：` 条目，写明 TASK、验证事项及
  `不作为 Plan/Execution 门禁`；不放入 Executing 交付的公共验证入口或设为执行门禁。
- 对应的本地测试验证 Java 的输入、分支、异常边界、协议请求及可观察结果；明确 mock 不能证明
  真实数据库事务、唯一约束、SQL 语义或执行计划。外部验证未完成时保留为未验证范围和风险，
  不宣称已证明，也不通过扩大 Execution 权限来关闭它。

## ADHD 友好的最小充分表达

本节将精简表达规则落实到 Design 正文，写作和交付前均须检查；`$i-have-adhd` 可用时一并应用。

- 背景与问题、目标与非目标承接 PRD 同名章节，交代问题、预期结果和范围排除；保留原意及
  必要范围，不复制需求和验收清单。设计结论用一段写用户选定方案、依据、主要边界和代价，不重复前两节；
  沿用的能力只指出复用位置，展开本次变化及必要衔接。
- 逐字段说明仅覆盖本次新增或修改的内容，适用于领域模型、持久化映射和外部接口。修改包括
  业务含义、用途、约束或映射规则变化，不限于名称或类型变化；新增模型或接口的全部字段均在范围内。
  未变化字段无需逐项解释，必要时概述复用关系或引用已有定义；图中出现沿用字段不扩大说明范围。
- 业务流程写业务动作和系统交接，技术流程写实现职责与运行机制；领域模型和持久化关系按条件画图，
  不要求两者一一对应。流程图后不逐节点复述；核心领域模型图后说明模型业务意图及本次新增或修改字段，
  按下方固定结构和模板执行。其他图后只补图中没有的不变量、约束或迁移前提。
- 一个技术决定只在关键设计、模型或边界的一处完整定义；其他位置引用具体标题或表格行并只写差异。接口参数映射完整覆盖本次新增或修改内容，DDL 完整覆盖本次结构变更；TASK 必填字段优先一行，交付只索引关键章节和现有路径、Symbol，不重写方案或列文件动作。
- 共享结果、信任边界、失败语义和公共验证入口的需求合并为一个 TASK，任一维度需独立实现或验证时拆分。可选小节未触发就删除；无独立权衡或额外风险时一句说明，不补通用最佳实践和假设问题。
- 删掉一句后，不影响设计决定、实现、验收或风险判断，就删除；引用仍需精确，不能写“同上”。不删必要业务结果、失败语义、所有权及追溯，不用省略合同或固定总字数换取简短。

## 固定文档结构

最终文档严格使用以下九个二级章节：

1. `背景与问题`
2. `目标与非目标`
3. `设计结论`
4. `方案全景`
5. `关键设计与权衡`
6. `设计边界`
7. `实施影响`
8. `验证与风险`
9. `Executing 交付`

前两节必填，位于设计结论之前，承接 PRD 同名章节的已确认内容，使读者无需跳转 PRD 也能
理解本次设计的原因与范围；可以沿用原文或等义精简，不能只写引用或省略已确认的范围边界：

- `背景与问题`：保留当前业务场景、受影响对象、当前问题及可观察行为；可补充与设计直接
  相关的已核验仓库事实，不展开调查过程或提前描述方案。
- `目标与非目标`：使用 `**目标**`、`**非目标**` 分组。目标保留 PRD 的可观察结果，关联适用的
  `REQ/AC` 并由后文结果 TASK 承接；必要技术约束可补充，不把新增类、文件或组件当作业务目标，
  不增加业务结果或验收指标。非目标保留 PRD 明确排除的问题、场景或能力及范围边界，不得排除
  必需需求或承诺未确认的后续阶段。PRD 确实没有明确非目标时如实说明，不虚构条目，也不用
  “无额外非目标”代替 PRD 已列出的排除项。

`方案全景` 必须说明整体方案、业务流程和技术主链路；以下四个小节按下列顺序排列，以图形表示为主，文字和表格说明为辅：

- `业务流程` 必填，位于“技术流程”之前，使用 Mermaid `flowchart`，以业务语言表达触发条件、
  参与者动作、关键判断和成功/失败结果，不以类名、方法名或技术调用代替业务动作。跨系统时
  必须使用泳道图，以 `subgraph` 按系统划分并标明名称，动作归入所属系统，跨泳道连线表达
  业务交接及结果反馈，区分业务流程边界；单系统也画业务流程图。沿用流程时画清本次涉及
  的流程及变化点；技术流程补充实现职责和运行机制，不逐节点重复业务流程。
- `技术流程` 必填，使用 Mermaid `flowchart`、`sequenceDiagram` 或 `stateDiagram-v2` 表达
  入口、关键职责和结果；简单链路也用图，涉及事务、异步、状态流转、并发或失败恢复时画出
  影响合同的边界与分支。关系未变化也画清本次方案沿用的主链路和变化点，不以存在外部边界
  为前提，不能只写“无变化”。
- `核心领域模型` 在相关模型或关系变化时必填，以 Mermaid `classDiagram` 表达领域实体、
  值对象、聚合、领域事件及相关关系；只保留本次涉及的类型、关键属性和关系，不画
  Controller/Service/Repository。图后紧接模型及字段的业务说明：逐个解释模型代表的业务概念、
  存在理由、职责边界及关键业务规则，仅对本次新增或修改的领域字段逐项解释业务含义、用途和约束，
  包括图中未展开的变更字段；未变化字段无需逐项解释。变更字段不能仅列名称或类型；具体表达按
  [Design 模板](assets/design.md)。
- `持久化实体` 在持久化模型、映射或表结构变化时必填，以 Mermaid `erDiagram` 表达相关
  领域实体对应的持久化实体、关键字段、主外键和关系基数；它与核心领域模型不是一一对应，
  不把值对象单独画成 ER 实体或关系。单实体也用图，不虚构关联。值对象默认作为所属领域实体
  的字段；一对多值对象必须在图后说明数据量、增长和独立增量需求，并据此决定 JSON 字段或
  独立持久化结构。本次新增或修改的领域字段到持久化字段的映射、值对象存储决策、约束及迁移前提按需用文字或
  表格补充；涉及表结构变化时仍必须包含上述完整 DDL，图和说明不重复抄写 DDL 已明确的列定义与约束。

条件未触发的小节删除；同一视角的流程只在方案全景解释一次，其他章节引用其具体标题。

`实施影响` 必须包含至少一个供人工评审的结果 TASK；文档末尾的 `Executing 交付`
必须索引同一组 TASK ID，并按 TASK 在正文中首次出现的顺序排列。TASK 字段以
[Design 模板](assets/design.md) 为唯一结构定义，按可观察结果垂直拆分，不按
Controller/Service/Repository 横向拆分；每个 PRD 需求和验收标准都要对应，明确非实施项除外
并说明原因。

`Executing 交付` 的表格格式以 [Design 模板](assets/design.md) 为准。每个 TASK 的结果合同
定位必填，其余条目只在能帮助找到相关合同或已读取入口时保留，不设置必须填满的字段。

## 文档校验与用户 Review

收口前确认详细设计对应用户已确认的方案；复用已读事实，核对“背景与问题”“目标与非目标”
完整承接 PRD，目标已落实到结果 TASK、非目标没有遗漏既定范围或排除必需需求；按
“Design 合同门禁”自检目标语义、当前承载、修改或迁移方式及 TASK/交付索引是否一致。
涉及 DDL 时核对结构变更完整性、表名与字段映射、SQL 方言及迁移语义的一致性；
实际业务库名和数据库环境版本不作为自检门禁。缺少关键决定时回到定向补证，不新增报告或审查阶段。

写入后运行一次 `scripts/validate_design.py`，检查章节、业务流程图及其位于技术流程之前的顺序、TASK 字段、REQ/AC 覆盖、占位内容、
Mermaid、交付索引及其文档内定位、显式 DDL 小节或索引对应的 SQL 代码块、DDL/DML 归属及显式外部验证表述的归属。结构校验失败只修正文档并重跑，不触发仓库
重查；发现合同缺口则按前述规则处理。脚本通过只证明机械结构合规，不证明技术决定完整、
仓库事实一致、生产代码质量、测试执行或覆盖率。业务语言、跨系统泳道边界、核心领域模型及
本次新增或修改字段的业务说明完整性、按需幂等设计的语义完整性及 PRD 内容承接由合同自检确认；用户的
方案确认以会话回复为准，脚本不能证明已获确认，也不推断上述语义。

## 红线

- 不创建 `execution-plan.md` 或新的规范阶段。
- 不修改 PRD、生产代码、测试代码、配置数据或治理文档；Context/ADR 由 `domain-modeling` 维护。
- 不把逐文件实施计划冒充设计边界，不保留占位词、待定技术选择或未经 PRD、外部协议或真实仓库事实支持的兼容承诺。
- 不把配置数据 DML、发布、部署、激活、回滚或数据库执行分配给 Execution。
