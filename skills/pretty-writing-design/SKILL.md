# 编写 Java/Spring Design

## 目标

把已批准 PRD 和真实仓库约束转化为供上下游与技术团队评审的技术合同。Design 先呈现结论、流程与边界，再给出权衡、验证、风险和就近追溯；不展开逐文件实施或完整代码。

加载当前阶段模板[assets/design.md](assets/design.md)

## 工作流

### 1. 确认模式与输入

宣布使用 `pretty-writing-design`。用户只要求评估、检查或 Review 时进入只读评审；要求创建或修订时进入写作模式。

写作模式读取已由用户批准的 `docs/pretty/<topic>/prd.md`、共享合同要求的领域上下文和足以支持设计的真实仓库事实。缺失、未批准、含占位或外部结果仍不唯一时返回 PRD。唯一输出为 `docs/pretty/<topic>/design.md`，已有文件原地修订。

### 2. 执行只读评审

读取用户给出的 Design、必要 PRD、源码、测试、配置和领域上下文；不修改、移动或复制文件，不更新领域文档，不生成 Plan。

依次输出：阻塞问题、重要改进、上下游与 Plan 影响、`可进入 Plan / 修正后再进入 Plan`，然后停止。每条发现说明位置、证据或限制、影响和建议。

### 3. 建立事实并关闭技术未知

检查足以支持决策的入口、调用链、职责、领域对象、持久化、外部合同、配置和 UT 边界，区分 PRD 要求、仓库事实和设计选择。

事实能决定时自行查明，无法查明的如接口入参如何映射等使用 `grilling`，一次解决一个高影响技术决策。外部结果不清楚返回 PRD。Design 获批前不能残留会迫使 Plan 决定架构、契约、所有权、一致性或验证声明的未知项。

### 4. 固定合同

- 新增流程、代码设计优先使用`CONTEXT.md`、`CONTEXT-MAP.md` 或 ADR 中的模型、术语、决策。
- 优先采纳质量路由中的质量规范而非codebase中已有代码实现。
- 代码质量遵循全局最优而非单独某个方法、某个类最优而全局出现重复、代码坏味道。
- 不保留 `TODO`、`TBD`、`FIXME`、待定、个人绝对路径或其他占位内容。

### 质量路由
| 触发场景 | 使用                                           |
| --- |------------------------------------------------|
| 发生共享合同定义的领域模型变化 | `domain-modeling`                              |
| 对象职责、封装、聚合、组合或继承变化 | `121-java-object-oriented-design`              |
| 值对象、泛型、类型层次、金额类型或 primitive obsession | `122-java-type-design`                         |
|  服务职责、端口、依赖方向或扩展点变化           | `solid-principles` |
| 模块接口深度、seam、adapter 或测试表面需要设计 | `codebase-design` |
| 已选定模块存在多个实质不同的合理接口形状       | `codebase-design` 的 `DESIGN-IT-TWICE.md` |
| 已证明存在构造、替换、通知或适配变化轴         | `design-patterns` |
### 5. 编写结论先行的 Design

严格使用五章模板：设计结论、方案全景、关键设计与权衡、设计边界、验证与风险。简单设计保留五章但可以很短。

- 删除“覆盖需求”清单。Design 默认覆盖已批准 PRD；是否真正覆盖由章节末尾追溯与校验结果证明，不在开头自我声明。
- 每章先写结论，再展示流程、合同或权衡。正文不以 `REQ/AC/DEC` 编号开头，不使用决策索引，也不让编号充当标题或论证主语。
- 高影响、可独立挑战的选择仍分配连续 `DEC`，但三级标题使用可读的自然语言结论；每个 `DEC` 只在最具体的所属章节最后定义一次，摘要不重复引用。
- 正文只使用 `Class#method`、类型名、配置键或模块短名；存在重名时补模块名。Design 不反复展示完整源码路径，个人绝对路径永远不得进入制品。
- 设计边界主要指对外提供的接口、调用外部的接口、监听外部的MQ、发送外部的MQ、定时任务

设计边界按表格形式呈现yes

| 接口名称/MQ/定时任务        | 参数及获取逻辑 |
|-----------------------------|----------------|
| 加急消息 `Class#method`     | 具体参数       |
| 发送/监听MQ，<TOPIC>        | 消息体         |
| 定时任务名称 `Class#method` | 具体参数       |

按信息结构选择表达形式，并让选中的形式直接作为权威合同：

| 信息结构 | 首选形式 |
| --- | --- |
| 三步以上流程、跨模块调用、事务或异步边界 | Mermaid `flowchart` 或 `sequenceDiagram` |
| 状态迁移 | Mermaid `stateDiagram-v2` |
| 三个以上状态、分支、角色、映射或字段 | Markdown 表格 |
| 筛选、排序、防重、并发或错误处理算法 | fenced 伪码 |
| 简单线性关系或 Mermaid 无法稳定渲染 | ASCII |

Mermaid、Markdown 表格、伪码或 ASCII 可以直接作为权威合同，随后不再用文字重复相同内容。图中只使用业务语义和模块短名，不放完整文件路径、追溯编号或大段代码。不为数量凑图；纯文字主要解释为什么、限制、代价和重新评估条件。

Design 仍需明确职责、依赖方向、输入输出、错误、一致性、兼容、事务、并发、验证限制及剩余风险。只用短签名或伪码澄清合同；不写逐文件任务、完整实现、完整测试、fixture、Mock 操作或执行命令。

### 6. 自审、校验并请求 Review


告知路径、主要设计结论、领域文档/ADR 变更和校验结果，请求一次用户 Review，然后停止。不得自动进入 Plan。

## 红线

- 不替 PRD 决定外部结果。
- 不为展示完整性制造候选、接口、图、模式或决策。
- 不把内部实现细节伪装成技术合同。
- 不让编号、证据链或长路径抢占正文阅读顺序。
- 不以外部环境、独立 Reviewer 或非 UT 测试作为 Plan/Execution 门禁。
- 不在只读评审中修改文件。
