# 编写 Design

把 PRD 和真实仓库事实收敛为可评审、可执行的技术合同。Design 定义外部边界、职责、数据所有权、依赖方向、运行时语义、模型、风险和行为级实施影响；不选择业务结果，不复制完整源码，也不证明真实实现质量。

## 输入与交付

- 读取同目录 `prd.md`、适用 Context/Context Map/ADR、构建配置和受影响真实代码；优先以 PRD 已确认的公共入口和测试为搜索起点，不从全仓重新猜测入口。以这些材料和真实实现为依据，不猜测 API、Schema 或依赖。
- 默认写入 `docs/pretty/<topic>/design.md`，topic 使用小写 kebab-case。完成后停止，请用户 Review；后续由用户调用 `$pretty-executing`，未指定 `Plan` 时直接执行，明确指定 `Plan` 时生成实施计划。
- 交付只报告机械结构校验结果并等待用户 Review；不生成 Design Reviewer receipt，也不启动独立 Reviewer。真实实现质量由后续 `$pretty-executing` 的 Plan 或执行模式证明。

## 仓库调查与 Execution 交接

在标准 PRD → Design → Execution 路径中，Design 只为关闭技术合同缺口做一次受限调查。这里的“完整”指证据足以关闭本次技术合同，不是穷举相邻实现。没有 Design 的 Prompt-only 执行由 Execution 自行完成一次受限调查。

### 默认快速路径

一次“调查批次”指一组可并行执行、共同关闭已声明缺口的只读工具调用，而不是读取一个文件算一轮。默认按以下顺序执行，不增加仓库盘点、调查报告或证据清单：

1. **启动批次**：读取 PRD、模板，以及 PRD 已确认入口直接关联的 Context/ADR、实现和公共测试；先复用同一会话中已读取且未变化的事实。若这些事实已覆盖模板必填合同，跳过本批次。
2. **补证批次**：只处理启动批次后仍会改变业务结果、外部合同、不可逆 Schema、所有权、依赖方向或一致性语义的缺口；独立缺口在同一工具调用中并行取证。搜索按“已知路径或 Symbol → 受影响模块内精确搜索 → 全仓精确搜索”逐级升级，前一级能定位时不得升级，不做目录漫游、相邻方案盘点或同类实现穷举。
3. **立即落稿**：补证后直接创建或更新 `design.md`，随后运行机械校验。除非仍有一个必须由用户决定的阻塞项，否则不得插入第三轮只读调查；校验失败只修正文档，不借机重新调查仓库。

若用户已给出 PRD 路径，且当前会话已有未变化的 PRD 结论、合同决定、公共验证入口和影响锚点，下一次面向任务的工具调用必须写入或更新 `design.md`，不得先做新鲜度确认或确信性搜索。

### 调查收口守卫

- 调查开始时只在会话内部维护合同缺口，不创建额外交接文件。缺口只包括：入口与排除范围、业务规则所有者、外部协议、数据所有权与依赖方向、事务/失败/幂等语义，以及 TASK 所需的公共验证入口和影响锚点。
- 当每个 PRD 需求和验收标准已有 TASK 归属、每类真实公共入口已有一条职责链、外部边界及失败语义已关闭、每个 TASK 已有验证入口和影响锚点，且不存在会改变业务结果、外部合同、不可逆 Schema 或一致性方案的未知项时，调查立即结束并开始写 `design.md`。
- 每次读取或搜索前必须能指出它关闭哪个尚未关闭的合同缺口；不能指出时不执行。一次补证没有关闭或发现新的阻塞项，立即以已有事实落稿。普通类名选择、同类实现盘点、参数调优和非必要运维扩展不得扩大调查。
- 用户回复关闭最后一个阻塞项后立即落稿。仅当回复本身引入新的合同级输入时，允许增加一轮针对该输入的补证；读取完成后立即回到写作。
- 初稿之后只允许为补齐模板必填字段、解决文档内部冲突或核验即将写入的精确锚点做定向新鲜度检查。新发现但不改变本次合同的相邻问题写入风险或非目标，不继续追查。
- 用户明确要求忽略 Git 历史时，不读取提交、分支、标签或历史差异；当前 PRD、外部合同和工作树中的现有实现是唯一调查基线。

调查结果写入模板已有字段，不创建仓库快照、缓存清单或其他交接文件：

- `变更职责链路` 使用真实模块或稳定 symbol，表达一次完整链路；
- `公共验证入口` 使用 `仓库相对路径#symbol` 指向现有或明确新增的公共行为测试入口；
- `影响锚点` 按链路顺序列出 `仓库相对路径#symbol`，至少覆盖真实入口和规则所有者，适用时覆盖 Adapter、持久化点或外部边界；
- `Execution 交付` 列出候选生产、测试、DDL 或项目配置文件的仓库相对路径，并标明所属构建模块；
- 只交接定位和合同，不复制完整源码、行号、Git 哈希或读取证据。

这些精确锚点是后续 Execution 的候选影响范围；Execution 仍须读取即将修改文件的当前内容并做定向新鲜度检查，但锚点有效时不得重新进行全仓调查。

## Design 合同门禁

- 会改变业务结果、外部可见合同、不可逆 Schema、数据所有权、依赖方向或一致性语义的未知项必须在 Design 关闭；业务语义不明返回 PRD，缺少必要用户决策时停止并请求澄清，不能把未知项推给 Execution。类名、文件名、同类实现数量以及可由现有规范直接决定的普通实施细节不构成调查阻塞项，应在 Design 中给出一致选择或列为候选影响锚点。
- 只描述一次真实受影响链路：入口 → caller/callee → Adapter → 持久化或外部系统。设计边界只表达系统与外部参与者、服务、消息基础设施和调度器的合同；内部模块和逐方法调用树属于实施影响。
- 不写完整 Java、完整测试、执行命令、执行结果、覆盖率数字或质量自评。配置数据 DML、事件定义、模板关系、白名单、种子/reference data、激活/禁用/回滚由人工运维负责；结构性 DDL 只能声明为代码库文件交付且不执行。
- Design 不得要求新增无领域归属的通用规范化 Helper（如 `normalizeText`），也不得用 `continue`、空值降级、步骤注释等普通实现指令削弱共享质量规则；例外必须绑定具体 Symbol 和可核查仓库事实。

## ADHD 友好的最小充分表达

将 `$i-have-adhd` 的“结论先行、降低工作记忆负担、抑制旁支”固化为最终 Design 的产物规则，而不是依赖它在当前会话中已启用。用户启用该 Skill 时，它还负责对话和交付消息的形态；“首行给出下一动作”和“五项列表上限”不机械套用于文档，技术合同和 `REQ/AC` 覆盖优先于篇幅。

- 完整性按业务结果可追溯、合同维度已关闭、失败可区分、职责与依赖明确、验证入口和影响锚点可执行来判断，不按解释长度、图表数量或 TASK 数量判断。
- 每个事实只设一个权威落点：设计结论写方案、边界和代价，方案全景写关系，关键设计写决定与依据，设计边界写外部合同，TASK 写结果到交付的追溯，验证与风险只写验证层级、未验证范围和重要风险；其他位置只保留 `REQ/AC`、Symbol、路径或具体标题等追溯引用，不换句话重复语义。
- 使用能承载合同的最小形式：同一语义只选图、表或文字中的一种解释载体；删除不适用的可选小节；图只保留受影响节点，模型和 Schema 只保留相关字段，每个 TASK 字段优先一行并使用 `REQ/AC`、`path#symbol` 和文件路径表达精确关系。
- 共享同一可观察结果、信任边界、失败语义和公共验证入口的需求合并为一个 TASK；任一维度需要独立实现或验证时必须拆分，不能为减少 TASK 数混合不同职责链路。TASK 必填字段仍须明确；引用前文时使用具体标题或表格行，并补充本 TASK 的差异，禁止写“同上”。
- 完整初稿后删除任何不改变设计决定、外部边界、不变量、失败语义、所有权、追溯、验证或风险的句子，包括调查过程、源码复述、教程、通用最佳实践和重复验收描述；删后逐项回查全部 `REQ/AC` 和必填合同维度，删除后需要读者推断的内容必须恢复，不设置会迫使遗漏合同的总字数上限。

## 固定文档结构

最终文档严格使用以下六个二级章节：

1. `设计结论`
2. `方案全景`
3. `关键设计与权衡`
4. `设计边界`
5. `实施影响`
6. `验证与风险`

`实施影响` 必须包含变更职责链路和至少一个结果 TASK。每个 TASK 必须按 [Design 模板](assets/design.md) 提供：`REQ/AC` 对应关系、可观察结果、输入与不变量、可区分失败语义、公共验证入口、影响锚点、验证观察面、Execution 交付和人工运维产物。TASK 按可观察结果垂直拆分，不按 Controller/Service/Repository 横向拆分；每个 PRD 需求和验收标准都要对应，明确非实施项除外并说明原因。

## 文档校验与用户 Review

运行 `scripts/validate_design.py` 做 Design 文档的机械校验，检查章节、TASK 字段、REQ/AC 覆盖、占位内容、Mermaid 和 DDL/DML 归属。它不检查生产代码、测试执行、覆盖率或运行质量。

生成 Design 时，必须依据 PRD、外部协议、Schema 和真实仓库事实，从当前受影响链路中提取并明确以下技术合同。只描述合同层语义；类、方法和模块细节放入“实施影响”。不适用项须明确说明“不适用”及原因，不得保留 TBD 或待定项：

- 入口、外部边界、职责归属、数据所有权和依赖方向；
- 首个输入信任边界、必填/可选/默认语义和不变量；
- 成功结果，以及查询未命中、数据损坏、非法输入和外部故障的可区分语义；
- 查询/命令、副作用、协议可见的类型和返回值边界；
- 公共验证入口和验证观察面；
- 若涉及 DDL/DML，明确 DDL 仅作为代码库文件交付且不执行，配置数据 DML 由人工运维处理且不属于 Execution 交付物。

## 红线

- 不创建 `execution-plan.md` 或新的规范阶段。
- 不修改 PRD、生产代码、测试代码、配置数据或治理文档；Context/ADR 由 `domain-modeling` 维护。
- 不把逐文件实施计划冒充设计边界，不保留占位词、待定技术选择或未经 PRD、外部协议或真实仓库事实支持的兼容承诺。
- 不把配置数据 DML、发布、部署、激活、回滚或数据库执行分配给 Execution。
