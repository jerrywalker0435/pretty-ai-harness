# 端到端测试

本 Skill 面向需要真实环境、真实服务或跨组件验证的端到端测试。它先分析当前项目相对
master 的改动影响面，生成可 Review 的场景和按场景定制的 `e2e-context.json`，经用户确认
并补齐上下文后，才执行实际测试，最后将结果写入 `docs/pretty/<topic>/e2e-test.md`。

## 工作流

严格按以下阶段推进，每次只推进当前阶段：

1. **差异分析**：使用 `git diff master` 分析当前分支相对本地 `master` 的差异，包含工作区和
   暂存区修改；本地不存在 `master` 时使用 `origin/master`。结合代码变更的对外入口和影响面，
   分析直接业务流程，以及确实受影响的幂等、并发、重试、兼容性、数据库、消息队列、缓存和
   定时任务场景。按影响面决定是否纳入这些场景，不为每个类别机械创建测试。
2. **场景 Review**：输出场景清单，包含场景 ID、目标、前置条件、预期结果、依赖、数据副作用、
   所需上下文和建议执行方式。此阶段不执行真实请求、集成测试、上传、并发或远程数据修改。
   必须等待用户 Review。用户可以将场景标记为执行、跳过或修改后执行；只执行最终确认的场景。
3. **上下文准备**：根据最终确认的场景，在 `docs/pretty/<topic>/` 生成或更新
   `e2e-context.json`。字段按当前 Case 的实际需要生成，不使用固定字段全集。上下文可以包含
   环境地址、认证信息、账号、测试数据 ID、上传文件、超时、并发参数和清理选项等。用户直接
   填写测试数据即可，不要求额外 auth 文件。
4. **上下文校验**：读取 `e2e-context.json`，逐个确认已确认场景所需字段存在且格式可用。缺少
   字段或引用的文件不存在时，只报告缺失项并暂停；不得执行任何真实请求、集成测试或远程数据
   修改。上下文完整后仍等待用户明确的执行指令。
5. **执行测试**：只有用户明确要求“执行测试”“开始 E2E”“运行已确认场景”等执行指令时才
   开始。单独回复“OK”“Review 通过”或“继续”不触发真实测试。HTTP 场景统一使用 `curl`；
   Dubbo 和其他协议优先复用已有测试模块，否则按项目语言和框架在 `docs/pretty/<topic>/`
   下生成集成测试脚本并执行。脚本必须使用上下文中的环境和数据，不得猜测缺失输入。
6. **结果报告**：按 `assets/e2e-test.md` 的格式生成 `docs/pretty/<topic>/e2e-test.md`，
记录场景总览、每个场景可独立复制执行的实际命令或脚本、请求与响应、HTTP 状态和业务断言、失败/跳过原因、数据副作用、
清理结果、未验证范围和测试总结。每个独立场景失败后继续执行不依赖它的场景；依赖失败场景
的场景标记为跳过并记录依赖关系和原因。

## 差异和场景边界

- 基线优先使用 `master`，不存在时使用 `origin/master`；差异命令语义等同于 `git diff master`，
  必须包含未提交修改。
- 从变更触及的公共入口、协议、数据写入、异步投递、状态迁移、查询隔离和定时触发点推导场景。
  只有代码影响面支持时才增加幂等、并发、重试、兼容性、数据库、消息队列、缓存或定时任务场景。
- 场景必须体现可观察结果和关键断言，不能只列“调用接口成功”。需要时覆盖成功、业务拒绝、
  查询未命中、重复请求、并发竞争、重试恢复、旧接口兼容和数据隔离。
- 测试数据允许修改测试环境，但每个场景必须声明数据副作用。新建数据使用唯一前缀或唯一标识；
  禁止修改、删除或复用测试开始前已存在的业务数据。测试结束后尽量清理本次创建的数据，并在
  报告中记录清理成功、失败或未执行。
- 涉及生产环境、真实用户身份、并发请求或批量高频请求时，即使场景已 Review，也必须在实际
  执行前再次获得明确确认。没有确认时将场景标为待确认并暂停该场景。

## e2e-context.json

文件路径固定为 `docs/pretty/<topic>/e2e-context.json`。不要预设所有 Case 共用同一 Schema，
根据场景清单生成最小必要结构。例如场景需要环境和请求身份时才生成对应字段，需要上传时才
生成文件字段，需要两名并发用户时才生成多个身份字段。

上下文允许直接保存测试所需的测试数据，包括 token、Cookie、账号密码、测试数据 ID 和文件路径。
它属于用户填写的测试上下文，不复制到其他项目文件。执行前检查：

- JSON 可解析；
- 每个已确认场景声明的字段都存在；
- 路径型字段指向存在且可读的本地文件；
- URL、身份、数据 ID、并发和清理参数满足场景约束；
- 生产、真实身份、并发或高频场景具有本次执行前的明确确认。

字段缺失时，报告场景 ID、字段路径、用途和示例值，等待用户补齐。不要为了绕过缺失字段而
跳过断言、改用猜测值或执行场景的部分请求。

## 执行规则

HTTP 请求使用 `curl`，命令应包含适合当前场景的超时设置，并保留可复现的请求结构。每个场景必须
给出完整、可单独执行的命令或脚本；命令可以直接展示 token、Cookie 等凭证，不要求隐藏或改写凭证。
对于 DNS 解析失败、连接失败、连接超时、连接重置等网络环境错误，首次失败后必须至少重试 3 次，
即持续失败时至少尝试 4 次；一旦成功即可提前结束。默认重试 3 次，间隔依次为 1、2、4 秒，
每次请求都设置超时；耗尽重试后记录环境失败并继续其他独立场景。HTTP、Dubbo 和其他协议均遵循此规则，
每个场景的独立执行命令或脚本必须包含重试逻辑。不能仅依赖 `curl --retry 3`，因为它不覆盖所有
DNS 和连接错误；应在脚本中按传输错误分类重试，避免把业务拒绝或断言失败当作网络错误。
写请求超时或连接中断后，重试前复用同一幂等键或核实上次写入结果，避免重复创建数据；无法确定
是否已生效且无幂等保障时，停止重复写入并记录原因。报告必须记录重试策略、实际尝试次数、
每次错误和最终结果；没有收到服务响应时明确注明，不得伪造业务 JSON 返回体。
执行结果
记录实际 HTTP 状态、响应正文、业务码和关键断言。存在 JSON 响应时，必须在对应场景详情中
增加“返回值 JSON”段落，使用 `json` 代码块并按层级格式化完整返回体；不能只写一行压缩 JSON、
只摘录 `code` 或用“响应同上”代替。Dubbo 和其他协议若返回结构化 JSON，也使用同样格式记录。
每个场景都必须记录完整、格式化的 JSON 返回值；没有 JSON 返回值时，场景必须明确记录实际返回内容及
无法提供 JSON 的原因。响应中的敏感值按结果文档实际需要处理，不得为了展示结果泄露无关凭证。

Dubbo 或其他协议按以下顺序选择执行方式：

1. 复用项目已有的集成测试模块、测试工具和构建入口；
2. 在 `docs/pretty/<topic>/` 生成当前 Case 所需的临时集成测试脚本；
3. 使用项目已有构建命令或运行时执行脚本，并记录命令、退出码、标准输出、标准错误和断言。

生成的临时脚本在测试结束后删除；结果报告保留足以复核的脚本内容或关键代码片段。不得把
临时脚本写入生产源码目录，也不得修改无关项目配置。测试环境数据清理属于场景的一部分，
清理失败必须进入结果报告，不得伪造为通过。

## 交付和校验

正常运行时只创建或更新：

```text
docs/pretty/<topic>/e2e-context.json
docs/pretty/<topic>/e2e-test.md
```

临时集成脚本可以位于同一 topic 目录，执行后删除。结果报告必须参考
[e2e-test 模板](assets/e2e-test.md)，并且至少包含每个实际处理场景的状态：通过、失败、跳过
或按要求暂不执行。没有执行的场景必须有原因，不能以空白替代。

修改本 Skill 的结果校验器时，运行：

```bash
python3 -m unittest discover -s skills/pretty-e2e-test/tests -p 'test_*.py'
```

生成报告后运行：

```bash
python3 skills/pretty-e2e-test/scripts/validate_e2e_test.py \
  docs/pretty/<topic>/e2e-test.md
```
