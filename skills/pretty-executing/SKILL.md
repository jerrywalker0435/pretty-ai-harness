# 生成并执行 Java 实现

本 Skill 面向 Java/Spring 代码实现。它把已批准的 Design、用户当前 Prompt 或已有
`execution-plan.md` 与真实代码仓库结合，生成完整、具体、可落库的生产代码和行为测试。
它不修改 PRD、Design、Context、ADR 或治理文档，不提交、推送、部署或发布。

## 精简辅助：i-have-adhd（可用时默认使用）

开始工作前，若 `$i-have-adhd` 可用则加载并应用其规则；同一会话已加载且仍生效时直接复用。
加载成功后将其用于对话、交付消息以及组织 Plan、执行记录和检查冗余。未安装或无法加载时继续执行，
使用本 Skill 的内置精简规则，不把它作为阻塞条件，也不因此跳过 Plan、执行记录或临时证据。

若已加载该 Skill，对话和交付消息遵循其规则；Plan 和执行记录始终按本模板与下方精简规则保留完整合同，
不机械套用首行操作或五项列表上限，不因此省略 TASK、核心代码、测试或验证证据。


## 变更边界

- Design/Plan 锚点有效时直接读取目标实现；Prompt-only、锚点失效，或已读事实出现重复职责、
  冗余包装等具体复用疑点时，才沿受影响链路及所属模块定向核验可复用实现的定义、调用方和
  必要边界。锚点有效不证明新增概念必要；事实足够时不重复搜索，不扩大为全仓盘点。
- 只修改任务范围内的文件，允许在受影响链路中保持合同的局部简化；最小 diff 不能作为保留
  重复规则、无效分支或多余包装的理由。
- 不进行任务范围外未请求的重构、清理或依赖升级。
- 保持现有 API 和行为，除非任务明确要求改变。

Plan 和 Execution 从首次生成起遵循[简单实现优先](references/quality-principles.md#简单实现优先)：
优先复用现有能力，以更少的概念、调用层次和重复规则完成完整合同。任务范围内、保持合同的
冗余清理和局部简化属于实现授权，直接完成；不以压缩行数、删除必要行为或省略测试换取简洁。

### 统一新增必要性规则

所有新增都遵循“非必要、勿新增”，范围包括生产代码、测试、依赖、配置、脚本、文档、执行记录和可交付
目录中的其他文件。先复用已有承载；只有当前用户授权、Design/Plan 合同或当前工具前置条件要求，且现有
能力无法满足时才新增。新增项必须有当前用途，并能指出其必要的行为、约束、外部协议、验证观察面、
构建前置条件或执行记录要求；未来扩展、形式整洁、数字达标、重复记录和单纯排版偏好都不构成理由。

- 新增类型、方法、分支、转换、抽象和异常必须承载当前独立语义或必要边界；没有独立语义就复用、合并或
  删除，不用包装、转发、工厂、策略或参数对象预留未来变体。
- 新增依赖只有在 JDK、项目已有依赖和少量本地实现都不能合理承载当前复杂度，且合同允许时才可加入；
  新增配置、测试和文档必须分别对应当前行为、构建/运行前置条件或交付追溯需要。
- 临时证据、构建缓存和生成目录只在当前命令确实需要时创建，优先复用已有位置，完成或停止后按既有规则
  清理；不得为了方便额外生成报告、清单、快照、隔离工作树或项目内交接文档。工具自动维护的忽略项只
  在避免把必要缓存纳入版本控制时保留，不把它们当作业务交付。
- 每项新增的必要性写入现有 Plan、Review JSON 或 `execution.md` 对应字段；不为证明“没有复用”另建报告。


## 精简表达与交付

本节将精简表达规则落实到 Plan、执行记录和交付，`$i-have-adhd` 可用时一并应用；代码、测试和质量门禁保持完整。

- 聊天先报结果和产物路径，再报验证及必要限制；不复述需求、逐文件回顾或粘贴完整文件，常规工具调用不逐条解释。
- Plan 按模板保留每个 TASK 的完整核心生产 symbol 和行为测试代码；代码外只写文件动作、依赖和代码不能表达的合同约束，不再用长段落解释代码或复制 Design、测试意图、审查清单。
- 执行记录只写实际落点、行为证据、验证事实和未关闭事项，不复述 PRD、Design 或实施过程。共享的审查、构建和覆盖率结果集中记录一次，不在每个 TASK 重复报告。
- 保留校验器要求的字段和格式：TASK 写各自状态，结论只列 `TASK-ID：状态` 索引及总体状态；变更汇总只列生产路径与 Symbol，未发生事项写“无”。阻塞详情只在“停止证据”展开，其他位置保留具体原因和受影响 TASK。
- 删掉一句后不影响实现、验收、追溯或恢复判断，就删除。交付范围只写验证边界，声明限制引用未验证范围并只补结论限制；不重复列清单，不用省略合同、代码或测试换取简短。



## 输入与优先级

按以下顺序处理输入；冲突不能猜测解决：

1. 当前用户 Prompt：决定目标、范围、模式和本次修改授权。
2. 已批准的 `docs/pretty/<topic>/design.md`：是业务结果、失败语义、不变量、所有权、依赖方向
   和外部边界的权威合同，并通过交付索引定位合同正文与现有仓库入口。
3. `docs/pretty/<topic>/execution-plan.md`：在 Design 合同内提供更具体的 Files、Symbol、测试和
   实现顺序。
4. 真实代码仓库：只用于确认易变事实，包括当前文件内容、路径和签名、依赖 API、Java/JDK、
   构建任务、工作树状态及运行结果。

Design 或 execution plan 不得覆盖用户当前明确的目标和授权。Design/Plan 描述目标状态，
现有代码与目标不同不自动构成合同冲突。已有计划经下述差异分类确认可执行后直接采用。

业务合同与实现建议分别处理：业务结果、失败语义、不变量、所有权、依赖方向、公共/外部协议
及明确的事务、并发、幂等、安全约束必须保持。Files 与锚点用于定位和限定范围；内部类型、方法
拆分和示例代码允许在同一合同和授权范围内等价简化。当前 Prompt、项目强制规则或 Design/Plan
明确要求保留的交付文件、symbol、签名和装配仍是硬约束；仅在图、示例或文件清单中出现不等于必须
保留该实现结构，图中表达的领域语义和边界仍须保持。等价简化不重新调查业务语义，也不改写
上游文档。

发现 Design/Plan 拟新增的概念可能重复时，先用已读事实判断，证据不足才按“变更边界”定向
补查。确认现有能力完整满足合同且新增结构仅属内部实现建议时，直接复用或合并，同步调整
调用方与行为测试。生成或获授权修订 Plan 时写入采用的实现；执行模式只在执行记录说明实际
落点与等价依据。承担独立身份、生命周期、不变量或必要协议边界的概念保留，名称或字段相似
不足以证明可合并。复用会改变合同或违反明确保留要求时，按下方“仓库差异分类”处理，
不以复用为由自行重定义领域语义。

### 仓库差异分类（Plan 与执行共用）

- **预期实现差异**：合同已确定新增或修改的职责、状态迁移、失败语义和边界时，直接实现。
  适用于 Add 和 Modify，也适用于已明确目标但未逐一列出 Symbol 的必要改动；当前仅有旧
  状态处理、重试 Job 或缺少目标方法不构成冲突。不得以旧实现降低已批准的需求范围。
- **定位差异**：路径、名称或签名失效时围绕锚点重定位，并在合同内适配；候选交付清单
  漏列必要文件时沿受影响链路补齐。没有改变合同的命名和普通实现选择由 Execution 决定。
- **合同缺口或矛盾**：完成目标仍需决定未明确的业务结果、字段语义或迁移、外部协议、
  所有权、依赖方向、事务、并发、幂等或安全边界，或已核验事实使既定方案无法成立时，
  只围绕缺口核验直接事实；无法在当前授权和合同内解决才暂停受影响工作并返回 Design。
  已明确并授权的边界变更按合同实施，不因其涉及边界而再次请求确认。

合同阻塞必须引用具体 TASK/合同条款及 `path#symbol` 或协议/Schema 事实，指出缺少或矛盾
的决定、为何无法由现有合同或规范推导、影响哪些 TASK，以及恢复所需的最小决定。仅报告
“仓库尚未实现”或“涉及并发/幂等”不足以停止。不依赖该决定的已授权工作继续完成；停止
记录区分已完成与受阻项，不把部分完成声明为全部交付。


### 质量来源与事实约束

`clean-code-guard` 负责通用代码质量，并作为执行模式[非平凡生产代码](references/quality-principles.md#非平凡生产代码判定)
的阻断质量合同；
[质量补充](references/quality-principles.md)负责执行合同、Java/Spring 语义、注释与运行观测的信息充分性和行为测试。
AGENTS、Trellis 等项目规则决定仓库本地惯例；它们都不能覆盖用户、Design 或 Plan 已明确的业务
合同。`clean-code-guard` 有具体代码证据的违反项默认阻断交付，只有下文允许的质量例外可以关闭。
其中函数行数、参数数量、复杂度和设计模式按[简单实现优先](references/quality-principles.md#简单实现优先)
的适用口径判定，不仅凭数字或形式触发拆分、包装或新增抽象。

真实 API、Schema、Java/JDK、依赖版本和运行结果以仓库事实为准；既有实现不能代替 Design、Plan
或 Prompt 决定本次业务语义。外部或遗留合同确需例外时，必须绑定具体 symbol、不可修改原因，
以及测试、Schema 或签名事实。
输入可以只有 Prompt。若没有可复用的 topic，从 Prompt 确定小写 kebab-case topic；只有名称存在
歧义或会与现有 topic 冲突时才请求确认，否则直接使用并在交付时报告。Design 或 execution plan
已位于 `docs/pretty/<topic>/` 时，使用其所在 topic。

## 模式选择

- 用户明确指定 `Plan` 时进入 Plan 模式；`Plan` 是唯一的计划模式名称。
- 未明确指定 `Plan` 时，默认进入执行模式，直接修改真实代码库。
- 流程只有 Plan 和执行两种输出模式；Design、已有 execution plan 和 Prompt-only 是三种输入
  路径，不是额外模式。

### Plan 模式

Plan 模式只写 `docs/pretty/<topic>/execution-plan.md`，不修改生产代码、测试代码、项目配置或
其他真实实现文件，也不写 `execution.md`。目标文件已存在时停止并报告，除非用户明确要求更新
已有计划。

严格使用 [execution-plan 模板](assets/execution-plan.md)，并生成足够具体的实现内容：

- 按可观察行为垂直拆分 TASK，写出变更链路、Files 和依赖顺序。
- 每个 TASK 写明构建根或模块，并将公共验证入口标记为“现有”或“新增”的
  `仓库相对路径#symbol`，供后续执行直接定位且避免误判新 Symbol 为锚点漂移。
- 为每个新增或修改的生产文件给出完整核心 symbol，包括字段、构造器、注解、方法和配置；
  不展示 import。删除项列明完整路径及 symbol、删除依据和必要的调用方调整，不生成占位代码。
- 同时给出从公共行为入口验证结果、状态或异常的完整测试代码；不以伪测试、调用次数或
  private 方法测试替代行为断言。
- 生产和测试代码块必须按[代码格式化](#代码格式化)中的项目规则排版；Plan 模式只整理文档内
  代码，不对真实实现文件运行写入式格式化。

Plan 完成门禁：每个 TASK 的每个新增或修改的生产文件都必须有完整核心 symbol 代码块，每个
行为测试文件都必须有从公共验证入口开始的完整测试代码块。代码块必须能让执行者直接
据此实现，不得用“实现某方法”“补充断言”、伪代码、测试意图、调用次数断言或省略目录
的 `...` 路径代替。新增文件必须明确类、接口、字段、构造器、注解、公开方法和配置；
修改文件必须明确受影响的现有 symbol 及其完整修改后形态；删除项必须有可核验的删除说明，
保留行为由公共入口测试确认。若一个 TASK 缺少必要的生产代码或删除说明、测试代码、完整
仓库相对路径、公共验证入口或依赖信息，Plan 仍未完成，必须继续调查并补齐，不能交付为完成。

按输入路径执行：

- **Design → Plan**：直接采用 `方案全景 → 技术流程` 和 `实施影响` 中的 TASK 语义，通过文档末尾
  `Executing 交付` 的定位索引找到相关合同、现有影响锚点与公共测试；具体文件动作、测试补充、
  构建模块和实施顺序由本阶段决定，不要求 Design 预先列出。不重建合同或输出前置分析。
  锚点已知后，用一个并行批次读取相关文件当前内容、公共测试、必要直接
  依赖、构建配置、质量补充和仓库规则；不重新读取 PRD、Context 或 ADR 证明 Design 已关闭的知识。
- **Prompt-only → Plan**：只做一次受限的内部 Design-lite 调查，确定可观察结果、失败语义、
  规则所有者、公共测试入口、影响文件和构建模块，直接写入 Plan，不另建 Design 或调查报告。
  Prompt 已给入口时用一个并行批次完成；入口未知时先定向定位，再并行读取受影响链路。若仍需
  决定外部行为、不可逆 Schema、所有权、依赖方向或一致性方案，停止并返回 Design。
- **已有 Plan 修订**：只有用户明确要求更新时才处理，并只重新读取受反馈或上游合同变化影响的
  TASK 和锚点；其余内容不重新调查。

路径、Symbol 或现有行为与目标有差异时，按“仓库差异分类”处理；Add/Modify 的预期差异均
不阻塞成稿。成稿后只执行一次结构检查、静态质量扫描和全量发现 Review；
阻断问题集中修复后只复核受影响的 Plan 片段，不生成额外全量证据。三者属于同一收尾批次。Plan
不执行编译、测试、测试守卫或覆盖率。

Plan 收尾检查至少确认：TASK 数量和依赖顺序完整；所有 Files 使用完整仓库相对路径；
每个新增或修改的生产文件均有核心 symbol 代码块，删除项均有删除说明；每个测试文件均有
完整行为测试代码块；测试从公共入口验证结果、状态或异常；文档中没有 `...` 路径、伪代码或只有意图没有实现的
占位内容。任一项失败都必须修订 Plan 后才能报告完成。

### 执行模式

执行模式直接在当前真实代码库生成代码，不创建隔离工作树或项目内交接文档；质量闭环在
`docs/pretty/<topic>/tmp/` 保留当前执行所需、且不交付不提交的临时证据，供限定修复和最终门禁复核。

**外部验证绝不阻塞实现。** Design 标记为“人工外部验证”的事项不是执行前置条件；不得因其未完成而停止实现、测试或本地交付。继续完成可本地验证的生产代码、行为测试、编译和覆盖率，并记录外部事项为未执行。

开始修改前按输入路径获取范围：

- **Design → Execution**：直接采用 `方案全景 → 技术流程` 和 `实施影响` 中的 Design TASK，通过
  `Executing 交付` 的定位索引找到相关合同、现有影响锚点与公共测试。具体文件动作、测试补充、
  构建模块和实施顺序由执行阶段依据合同与仓库事实确定；索引未列出未来文件或测试不构成合同缺口。
  业务结果、失败语义、不变量、所有权和依赖方向不再从 PRD、Context、ADR 或全仓搜索中重新获取。
- **Plan → Execution**：直接采用已确认 Plan 的 Files、Symbol、测试、构建模块和顺序，并与
  Design 的语义合同对齐；没有 Design 时以 Prompt 和 Plan 中明确的行为约束为准。按前述合同与
  实现建议的区分，允许在既定范围内简化内部结构，并同步调整受影响的调用方与行为测试；实际
  落点写入执行记录。不得重新调查已确定的业务语义或扩大范围。
- **Prompt-only → Execution**：只做一次受限的内部 Design-lite 调查，确定结果、状态迁移、失败
  语义、规则所有者、公共测试入口、影响文件和构建根，不落盘 Design 或 execution plan。Prompt
  已给入口时在预检批次内完成；入口未知时允许一次定向定位。合同级决定仍不明确时返回 PRD 或
  Design，不猜测执行。

范围已知后只执行一个并行预检批次：读取候选生产文件、公共测试、必要直接依赖、构建及格式化配置、
`clean-code-guard`、质量补充及适用 AGENTS/Trellis；同时检查候选文件的未提交修改、路径与
symbol 新鲜度，以及该主题是否已有执行记录。同一调用内这些质量说明只读一次并持续用于后续生成、
Review 和修复。目标新增实现不要求预先存在；行为差异、锚点失效或边界变化统一按“仓库差异
分类”处理，必要定向核验不受预检批次数限制。候选文件已有用户修改时停止；不相关脏文件不
阻塞，也不得触碰。历史执行记录、批次选择和继续执行规则统一见“执行记录与停止条件”。
ADR 只在 Prompt-only 路径或 Design 明确引用的例外需要核验时读取。

将 Design TASK 或 Plan 测试直接投影为简短内部测试清单；Prompt-only 才自行提取不同的成功
结果、失败语义和状态迁移。不给清单分配 ID、状态或证据字段，不输出前置分析，也不创建额外
交接文档。没有现成 Plan 时只在内部安排实现顺序。

按可观察行为逐个切片：先完成当前切片的行为测试，再完成从公共入口到 Module、Adapter 或
持久化的必要生产链路，然后进入下一切片。Design/Plan 列出的全部 TASK 都属于本次执行范围；切片和 TASK 是组织顺序，不是提前收尾条件。完成一个 TASK 后，除非命中明确停止条件，必须继续后续 TASK；“第一阶段完成”“部分代码已实现”或“剩余 TASK 尚未开始”不得作为停止理由，也不得据此生成最终执行记录。跨文件签名、依赖装配或生成代码等事实无法通过静态
检查可靠确认，或者一个切片闭环后需要尽早验证公共行为时，可以执行受影响模块的 `compile` 或
该切片相关的定向测试。中间反馈只使用最小相关模块和测试选择，不运行相关模块全量测试、JaCoCo
或覆盖率验收，也不为保存 RED/GREEN 证据机械触发；代码和命令输入未变化时复用已有结果，失败
修复后可以重跑。最终成功或停止时按 [execution 模板](assets/execution.md) 写入当前批次文件。

### 测试范围

- Plan 和 Execution 不以非 UT 测试或外部环境验证作为前置条件或完成条件。执行范围内的单元/
  行为测试不依赖真实数据库、外部服务或部署环境；协议映射使用本地隔离测试。
- Design 的“人工外部验证”不投影为执行 TASK、测试文件或依赖；真实事务、唯一约束、repository
  查询集成测试、SQL 执行计划及服务/设备联调只写入 `execution.md` 的未验证范围和声明限制。
  本地 mock 测试不证明这些事实；若 Design 将其设为执行门禁，返回 Design 修正验证归属后继续本地任务。

### 未验证事项分类决策

- 可用本地单元/行为测试验证：必须实现并验证。
- 依赖真实数据库、外部服务或部署且标为人工外部验证：跳过外部动作，继续本地实现，记录未验证范围。
- Design 将其设为 Execution 门禁：返回 Design 修正归属，继续不依赖该门禁的本地任务。
- 只有实际执行动作超出当前授权范围时才停止并请求确认。
- 纳入不同的成功结果、业务拒绝、查询未命中、非法或损坏数据、状态迁移、异常分类、远程
  空/失败/异常响应，以及完整外部边界请求等会改变可观察行为的合同。
- 相同公共入口和可观察结果的等价输入优先使用参数化测试，不按输入数量或每个 `if` 增加测试。
- 纯 DTO/Request/Response 的字段、无逻辑 getter/setter、普通构造器，以及 Lombok、编译器或
  其他工具生成的 accessor、`equals/hashCode/toString` 不创建专门测试。字段校验、转换、默认
  值、不变量、自定义相等性或协议语义属于真实行为时仍纳入，并优先从序列化、校验、Mapper
  或业务公共入口观察，不直接测试 accessor。
- 注释、声明和没有独立合同的机械转发不因覆盖率建测试；包含业务逻辑和样板代码的同一文件
  仍整体进入覆盖率范围，不按行手工规避。
- 覆盖率是发现遗漏的反馈，不是测试目标；不得为提高百分比测试 private 方法、无逻辑
  accessor、内部协作者调用次数或复制生产算法。

## 质量驱动实现

在预检批次中完整读取或复用本次会话未变化的 `clean-code-guard` 和
[质量补充](references/quality-principles.md)。`clean-code-guard` 的规则从首次生成到最终交付持续
生效；再根据 Design/Plan、真实受影响链路和计划修改的 symbol、类型、依赖与行为风险选择最小
专项路由。生成后以实际代码增量确认最终路由，不使用无关历史代码或全仓盘点扩大范围。

- 命中路由时，在同一次全量发现 Review 中应用其专项约束；没有命中时继续使用通用基线和质量补充。
- 路由只指导生成和 Review，不要求把路由字段写入 `execution.md`，也不把专项 Skill 的
  流程、命令或阈值复制进本 Skill。
- 只有真实事实证明需要时才增加模块边界、类型设计、Java 运行时或行为测试专项约束。
- Plan 与 Execution 均按[信息充分性原则](references/quality-principles.md#注释与日志的信息充分性)
  主动补充受影响链路中必要的注释与日志，无须需求逐项声明；全量发现 Review 按
  [对应语义审查要求](references/quality-review-contract.md#注释与日志信息充分性核验)检查具体缺口并纳入限定修复。

路由匹配后，在每个行为切片首次生成时直接落实约束。执行模式只保留以下收尾关键路径；Plan
模式使用前文规定的收尾批次，不执行真实项目验证：

1. **格式化与静态批次**：代码和测试全部完成后，先按[代码格式化](#代码格式化)完成本次改动的
   格式化与检查，再并行执行一次质量路由解析和一次机械质量门禁；两者共享相同 Git 基线和
   实际影响文件，不分别扩展扫描范围。
2. **强制质量闭环**：只执行一次覆盖完整实际增量的全量发现 Review，同时应用
   `clean-code-guard`、全部命中专项路由和测试守卫。Reviewer 将每个有具体代码、合同或行为证据的
   问题记录为阻断 finding，至少包含稳定 ID、根因组、规则、`path:line#symbol` 证据、允许修复的
   范围和 `open / fixed / exception` 状态；finding 位置和允许范围必须处于实际影响或明确授权文件
   内，没有证据的偏好不得成为 finding。按
   [质量 Review 合同](references/quality-review-contract.md) 将清单写入 `docs/pretty/<topic>/tmp/`，并在顶层记录实际执行的
   `routes_applied`（非平凡生产变更必须包含 `clean-code-guard`），再用
   `scripts/quality_review_gate.py` 校验结构。测试守卫检查新增/修改测试是否通过公共入口覆盖内部
   清单中的结果、状态和异常，是否包含本次行为产生的查询未命中、解析失败、依赖缺失及远程空/失败/
   异常响应，并拒绝测试禁用、private 方法测试、内部协作者调用次数或复制生产算法。

   同一次 Review 必须按[整体实现简洁性核验](references/quality-review-contract.md#整体实现简洁性核验)
   检查从公共入口到必要边界的完整调用链；有具体证据的冗余进入现有 finding 和限定修复流程。

   Review 还必须检查每个新增或修改方法的控制流终点：方法自然到达末尾时，禁止保留无条件尾部
   `return;`；仅当 `return` 位于仍有后续可执行语句的方法中，或表达明确的提前结束语义时允许。
   该项记录为 `source=clean-code-guard`、`rule="21"` 的 finding，并引用具体 `path:line#symbol`
   和证据；未修复时保持 `open`，由 `quality_review_gate.py --require-closed` 阻断最终验收。

   **CQS 调用链核验**按[质量 Review 合同](references/quality-review-contract.md#cqs-调用链核验)执行：
   Reviewer 必须为本次新增或修改的非 `void` 生产方法生成完整 CQS 记录；未完成方法清单、必要调用链
   或返回值消费核验时，不得将 Review 标为通过。CQS 证据位置涉及的文件也必须纳入 `reviewed_paths`
   和门禁的 `--path` 集合，但只允许沿必要调用链定向扩展，不得扩大为全仓扫描。

   **生产类型必要性核验**按[质量 Review 合同](references/quality-review-contract.md#生产类型必要性核验)
   执行：根据实际 diff 逐一检查新增或修改职责的类型定义及调用方，复用已有读取结果，在临时 JSON
   中填写 `type_necessity_checks`。类型清单由 Reviewer 核对，门禁只验证已申报记录的完整性与
   finding 关联。不得以命名、CQS 合规、Design 指定或纯数据载体身份替代必要性证据。
   Design/Plan 中被发现不必要的类型仍记录 finding；仅属内部实现建议时直接在范围内简化。
   删除会违反明确的保留要求或业务合同时，只有当前用户已授权该变化才能实施；否则保持 open，
   报告约束并停止请求方向，不能仅凭 Design 指定关闭为 exception。

   对当前授权允许修复的 `open` finding 按共同根因分组执行限定修复。命名、异常和局部控制流等问题直接最小修复；
   只有职责、抽象、耦合或方法结构问题才调用 `refactor`，并把输入限制为 finding 证据、允许文件和
   symbol、必须保持的行为及禁止改变的边界。每组最多两次修复尝试；每次后只复核该组 finding、
   实际修改的 symbol 及修复新增的代码，不再次执行全量 Review。受影响文件重跑机械门禁；只有
   签名、装配或可观察行为可能变化时才运行最小相关编译或定向测试，不启动全量测试或 JaCoCo。
   CQS 限定修复按质量 Review 合同执行；返回值仅供日志使用时，优先评估将执行方法改为 `void`，并
   由掌握执行结论的位置记录日志，不得为满足 CQS 新增结果查询、共享状态或额外存储。

   质量例外只能由当前 Prompt、Design、Plan、项目强制规则或不可修改的外部/遗留合同证明，必须
   记录具体 symbol、原因、测试/Schema/签名事实和复查触发条件。两次修复后仍为 `open`、修复需要
   扩大任务范围或改变上游合同时停止。只有全部阻断 finding 均为 `fixed` 或有效 `exception`，即
   `open=0`，并且 `quality_review_gate.py --require-closed` 返回 `0`，才可进入最终验证。
3. **最终验证**：每个受影响构建根在绿路径只执行一次最终验收调用，在同一 Maven/Gradle 调用中
   完成增量编译、相关模块全量测试和 JaCoCo XML。此前的受限编译或定向测试不计入这一次最终
   验收，也不能替代它；最终验收前不得预跑相关模块全量测试或覆盖率。多模块或自定义项目通过
   同一命令的参数合并任务。项目既有全量测试入口已经生成新鲜 JaCoCo XML 时，只读取报告，不
   再次启动测试。只有纯数据载体或生成代码且没有可执行行为时，覆盖率可以不适用，但仍按项目
   需要执行一次最小相关最终编译/测试。多个构建根只有在不共享数据库、端口、生成目录或全局
   状态且资源允许时并行，否则串行；同一构建根的最终验收绝不拆分。
4. **记录**：最终成功或停止时一次性创建并填写当前执行批次记录。质量门禁必须使用
   `clean-code-guard found=<n> fixed=<n> exception=<n> open=<n>`，且四项计数一致；限定修复按
   根因组和 finding ID 记录次数，质量例外记录上述依据。使用 `scripts/validate_execution.py --final`
   对 Design/Plan、TASK、实际生产 diff、Review JSON 和覆盖率 JSON 做最终门禁；填写或修正记录不得
   触发编译、测试、Review、门禁或 JaCoCo。
5. **失败收敛**：最终验收的编译、测试或覆盖率失败时，保留完整失败事实并定位当前已知问题；
   修复后尽可能先用最小范围的 `compile` 或定向测试确认，再重跑同一条最终验收命令。重跑发现
   新的、任务范围内且有明确修复依据的问题时，继续同一收敛循环。固定的是单一最终验收入口，
   不为失败修复设置任意次数上限；但代码、测试、配置和相关外部状态均未变化时不得重跑。只有
   已知失败得到局部确认，或该失败无法局部复现但已有具体修复或外部状态恢复证据时，才能再次
   启动完整验收。覆盖率不足时只为遗漏的可观察行为补测试；无独立行为时简化死分支，纯载体
   误入范围时更正覆盖文件集合。没有新的诊断证据或范围内修复动作时停止。

成功且没有 finding 的固定性能预算是一次并行预检、一次格式化与静态批次、一次全量发现 Review、每个
构建根一次最终全量测试与 JaCoCo、一次执行记录写入与校验。存在 finding 时只增加每组最多两次
限定修复、局部复核以及确有风险时的最小中间反馈，不增加第二次全量 Review。中间反馈只由尚未
确认的编译风险或已闭环切片的行为风险触发，并限制在最小相关范围，同一代码与命令不重复执行。
Design/Plan 快速路径不得增加合同调查；具体复用疑点只允许按“变更边界”定向补证，并纳入
同一次 Review，不单独触发额外构建或 Review。其他额外调查、静态复核、全量测试或覆盖率运行
必须由锚点漂移、校验失败或真实运行失败触发，每次失败路径的完整重跑还必须具备上述进展证据，
不能为了保存 RED、GREEN 或阶段性覆盖率证据而增加。

执行模式的常用辅助命令如下；`<base>` 是开始修改前记录的 Git 基线，输出仅供当前执行判断：

```bash
python3 skills/pretty-executing/scripts/quality_resolver.py --repo . --base <base> --path <affected-java-file> \
  --json --json-output docs/pretty/<topic>/tmp/quality-routes.json
python3 skills/pretty-executing/scripts/quality_contract_gate.py --repo . --base <base> --path <affected-java-file>
python3 skills/pretty-executing/scripts/quality_review_gate.py docs/pretty/<topic>/tmp/quality-review.json --path <affected-java-file> --require-closed
```

`tests/` 仅存放上述辅助脚本的回归测试，不属于正常执行路径；只有修改辅助脚本时才运行：

```bash
python3 -m unittest discover -s skills/pretty-executing/tests -p 'test_*.py'
```

## Java / JaCoCo 增量覆盖率

`scripts/verify_incremental_coverage.py` 仅支持 Java 项目，并自动识别 Maven 或 Gradle：

- 优先使用 `mvnw`/`pom.xml` 或 `gradlew`/`build.gradle(.kts)` 及项目已有 JaCoCo 配置。
- 项目配置了行或分支阈值时分别使用项目阈值；未配置的维度使用默认增量行覆盖率 `90%`、
  分支覆盖率 `80%`；不把阈值提高到 `100%` 来替代行为测试完整性。
- 每次都用重复的 `--path` 显式传入含本次可执行行为增量的生产 Java 文件。纯数据载体、无逻辑
  accessor 和生成代码不作为覆盖目标并在 `execution.md` 的“覆盖率范围”逐项说明；不能仅按
  `dto` 包名排除，混有校验、转换、默认值、不变量或其他行为的文件必须纳入。
- 脚本根据执行开始时的 Git 基线计算所选文件新增或修改的可执行行；`--run` 只用于最终一次
  相关模块全量测试和报告生成。`--report`/`--report-not-before` 只读取已有报告，绝不启动
  测试。只改测试或没有行为生产增量时明确记录“不适用”。
- 发现没有 JaCoCo 报告、报告过期、源文件无法匹配或覆盖率未达阈值时，执行模式先修复并
  重新验证；脚本输出未覆盖行和部分覆盖分支供判断，不据此机械增加测试。仍无法通过则
  停止并报告。

Maven 的 `--run` 默认使用项目根目录下持久保留的 `.pretty/maven-repository/` 作为
`-Dmaven.repo.local`，不写用户目录下的 `~/.m2`，也不在执行结束时删除。脚本在执行 Maven
的目标项目根目录更新 `.gitignore`，缺失时追加 `/.pretty/maven-repository/`，不修改安装
本 Skill 的仓库。若构建必须使用指定的可写仓库，可通过
`--build-arg=-Dmaven.repo.local=<path>` 显式传入；
已有新鲜 XML 时使用 `--report` 只读报告，不启动 Maven。

绿路径唯一一次带测试的命令同时完成相关模块全量测试和 JaCoCo：

```bash
python3 skills/pretty-executing/scripts/verify_incremental_coverage.py \
  --repo . --base <base> --path <behavior-java-file> --run \
  --work-dir docs/pretty/<topic>/tmp \
  --build-arg=-pl --build-arg=<module> --build-arg=-am \
  --test-task=test --jacoco-task=org.jacoco:jacoco-maven-plugin:report \
  --json-output docs/pretty/<topic>/tmp/coverage.json
```

Gradle 多模块项目将任务本身限定到目标模块，例如
`--test-task=:module:test --jacoco-task=:module:jacocoTestReport`；不要同时再传根项目
`test` 任务。

项目自己的全量测试已经生成 JaCoCo XML 时，只读取该报告，不得
使用 `--run`：

```bash
python3 skills/pretty-executing/scripts/verify_incremental_coverage.py \
  --repo . --base <base> --path <behavior-java-file> \
  --report <jacoco-xml-report> --json-output docs/pretty/<topic>/tmp/coverage.json
```

## 执行范围与代码生成约束

### 聚焦实现

代码生成按可观察行为推进，不增加额外文档或验证阶段：

- 同一时刻只实现一个可观察行为切片；锁定该切片的公共入口、规则所有者、必要文件和测试观察面，
  完成生产链路与行为测试后再进入下一切片。内部保留完整任务清单；只在编译性或公共行为仍有
  实际不确定性时运行最小范围的中间反馈，不逐文件启动构建，也不维护中间状态证据。
- 当前行为之外的重构、清理、依赖升级和相邻问题是旁支，只有真实阻塞当前实现时才做最小必要修改。
  完成可见于生产代码、行为测试和最终验证结果，不通过过程状态、RED 证据或重复报告制造进度。

### 代码格式化

- 新增或修改的生产代码、测试代码以及 Plan 中的代码块必须完成格式化后再交付；遵循适用的
  项目规则、`.editorconfig`、格式化工具配置和同模块现有风格，统一缩进、换行、空格、花括号、
  空行及适用的 import 顺序。项目有明确配置时以配置为准，不自行切换代码风格。
- 执行模式优先使用项目已有的格式化命令或工具，并运行对应检查；命令和参数从真实构建配置
  或项目文档确认，不猜测工具已安装。未提供可用工具时按项目规则手工整理并检查 diff，明确
  记录手工核对；项目强制的格式化检查仍必须通过，不以手工整理替代失败的强制检查。
- 格式化限于本次新增或修改的文件，工具支持时进一步限定到改动区域；不得整仓重排或触碰
  无关文件，也不为格式化擅自新增依赖、插件或配置。工具不能限定范围时改用范围内整理，
  保留项目要求的检查。
- 格式化在静态门禁和全量 Review 前完成；后续修复再次修改代码时，只对受影响代码重新
  格式化并检查，再进行局部复核和必要验证。最终编译、测试与覆盖率必须对应格式化后的代码。
- 在 `execution.md` 现有“审查”字段集中记录格式化范围、命令及结果，或手工核对依据与结果，
  不另建报告。格式问题或强制检查失败未解决时不得声明完成；无法修复时按 `VALIDATION_FAILED`
  记录停止证据。

### DDL、DML 与数据库边界

- 表、字段和索引等 DDL 只能作为代码库文件交付，不生成针对 DDL 的测试，不直接执行，也不
  通过迁移工具、应用启动、构建插件或测试间接执行。
- Java 与 DDL 混合变更只测试 Java 的可观察行为；在 `execution.md` 的“未验证范围”记录
  DDL 已交付、未执行、未验证数据库，“声明限制”引用该节说明不能推断数据库变更已生效。
- 配置数据 DML 始终由人工运维处理，不属于本 Skill 的执行交付物。

### 静态检查时机

质量路由、机械门禁和测试守卫都只做静态检查，不隐式启动测试。它们在最终全量测试前统一执行；
静态 finding 本身不触发完整回归，修复后的编译性或行为风险只使用前文规定的最小中间反馈确认。

## 执行记录与停止条件

每个行为 TASK 的结果、实际落点、审查摘要、行为证据、最终验收命令、执行次数及最终退出码、
未验证范围、覆盖率范围、覆盖率和结论，严格按 `assets/execution.md` 填写。记录写入后、向用户声明
完成或停止前必须运行：

```bash
python3 skills/pretty-executing/scripts/validate_execution.py \
  docs/pretty/<topic>/<execution-batch>.md --final \
  --contract docs/pretty/<topic>/design.md --repo . --base <base> \
  --coverage-json docs/pretty/<topic>/tmp/coverage.json \
  --review-json docs/pretty/<topic>/tmp/quality-review.json \
  --routes-json docs/pretty/<topic>/tmp/quality-routes.json \
  --path <reviewed-file>
```

最终记录校验成功或停止记录完成后，删除当前执行在 `docs/pretty/<topic>/tmp/` 中创建的临时
证据和 Gradle init script，并在目录为空时删除 `tmp/`。不得删除持久 Maven 仓库
`.pretty/maven-repository/`。异常退出留下的 topic 临时文件在该 topic 下次执行开始时清理。

首个批次使用 `execution.md`；再次执行先运行
`python3 skills/pretty-executing/scripts/execution_batch.py docs/pretty/<topic>` 选择下一个未占用的批次
文件，旧记录只读。完成门禁要求完整 TASK 集合、每项最终状态、实际生产 diff、格式化完成、质量 `open=0`、最终编译/测试
和覆盖率结果一致；质量路由 JSON、Review 路径、生产 diff 以及执行记录中的覆盖率必须互相匹配。
停止记录同样要求完整 TASK 集合和阻塞证据，但允许保留与停止代码对应的 `open` finding，不得声明完成。
`--path` 必须重复传入本次 Review 的完整路径集合；提供该集合时最终 diff 只在该执行范围内核对，
避免把预先存在的无关脏文件算入本次结果。
覆盖率适用时，构建验证必须记录包含测试和 JaCoCo 的最终 Maven/Gradle 命令；覆盖率不适用时记录最终
编译和测试命令。两者都必须记录执行次数及成功退出码。编译、测试、
覆盖率或单个 TASK 成功只能作为中间验证，不能触发收尾；没有明确阻塞时必须继续后续 TASK。失败
允许修复并重跑；无法修复时才记录带 `停止代码` 和 `停止证据` 的 `停止：<具体阻塞证据>`。
停止记录也必须列出合同中的全部 TASK；已完成项保留实际结果，尚未开始或未闭环的项逐项记录
阻塞事实和依赖关系，不能省略为“剩余任务待处理”或将同一阻塞事实套用于无依赖的 TASK。

编译或测试因本机环境失败时，先区分代码失败与环境失败。Maven 的 `~/.m2`、缓存或临时目录权限
错误必须切换可写 Maven 本地仓库重试；Gradle 缓存或生成目录错误必须切换可写临时目录重试。未完成
恢复尝试不得以“授权不足”或“本机权限”停止；替代目录仍失败时记录完整命令和错误证据。人工外部验证
按前文规则写入未验证范围，不阻塞本地实现、编译、测试或覆盖率。

以下情况才允许停止：按“仓库差异分类”确认存在当前授权和合同内无法解决的缺口或矛盾；候选
修改文件存在用户未提交修改；需要超出已授权合同改变公共接口、数据所有权、依赖方向、事务、
并发、幂等或安全边界；质量 finding 在限定修复后仍无法
关闭；格式化检查或最终编译/测试/覆盖率失败且没有新的诊断证据或任务范围内修复动作；或当前授权明确要求执行
DDL、配置数据 DML、真实数据库操作、部署、发布或人工运维等本 Skill 不执行的外部变更。Design 标记
的人工外部验证本身不属于停止理由。
