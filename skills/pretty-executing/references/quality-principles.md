# Java 代码质量基线

本文件定义执行阶段生成代码与真实增量共同遵守的质量原则。阶段流程见执行 Skill；下方“质量路由”根据真实风险选择生成与 Review 时需要的专项约束。机械规则及默认阈值以 `../scripts/quality_registry.py` 的注册表为机器来源。

## 受影响链路与责任归属

先确认受影响链路，再决定局部修改；已批准 Design 或 Plan 提供有效锚点时直接采用其链路，
只有 Prompt-only 或锚点失效时才定向调查：

```text
入口 → caller → callee → Adapter → 持久化或外部系统
```

范围止于真实受影响链路。识别规则唯一归属、数据所有权、状态迁移、消费者、注册点，以及事务、并发、幂等、安全和兼容边界。相同校验、规范化、默认值、映射或生命周期判断只保留一个知识源。需要改变外部结果、公共 Interface、所有权或依赖方向时，返回上游合同。

## 输入合同与信任边界

- 在值首次进入信任域时建立不变量，内部代码信任已经成立的合同。
- 区分必填、可选、可默认、外部不可信、持久化记录和内部值。
- `trim`、大小写折叠和默认值等规范化只能放在首个信任边界，并由协议、Schema 或既有公共合同证明；内部方法不得为假想脏数据重复规范化，也不得悄悄改变标识符和值对象语义。
- 规范化责任由首次信任边界决定，不由方法名决定。禁止创建或调用 `normalizeText`、`normalizeString`、`cleanText`、`trimText`、`trimToNull` 及同类规范化 Helper；把 `trimToNull` 重命名为 `normalizeTaskCenterText`，但没有改变责任边界，仍属于同一违规。`NORMALIZATION-HELPER` 和 `GENERIC-NORMALIZATION-HELPER` 是不可豁免的机械错误。
- 首次信任边界需要规范化时，优先在该边界的现有入口内直接完成，并由协议、Schema 或既有公共合同证明；领域类型、协议类型或兼容 Adapter 可以拥有有明确合同的转换，但不得把一次转换包装成可在内部重复调用的文本 Helper。内部方法必须信任已经建立的不变量，不得为假想脏数据重复 `hasText`、`trim`、大小写折叠或 `null` 防御。
- 已可信的持久化值、内部值、ID 和 Code 不得重复规范化。对 ID/Code 做 `hasText`、`trim` 或 `null` 兜底必须有明确的边界合同，否则命中 `IDENTIFIER-NORMALIZATION`，未通过 Review 不得交付。
- 备用字段选择必须有 Design、外部协议或 Schema 合同明确说明字段优先级、等价性和缺失语义。禁止新增 `firstNonBlank`、`coalesce`、`fallback*` 或等价的隐式兜底；缺少必填值时不能通过 `null`、空集合、另一个字段或“成功”结果掩盖数据损坏。`IMPLICIT-FIELD-FALLBACK` 是不可豁免的机械错误。
- 同一方法内重复执行文本检查或转换，或在调用端和被调用端重复执行，命中 `REPEATED-NORMALIZATION`，必须由 Review 证明每次操作属于不同且有合同的信任边界；不能仅通过领域化改名规避。
- 只有明确的框架、遗留或外部可空合同允许 `null`，并由注解、文档和测试共同证明；业务方法默认不返回 `null`。
- 同一输入的不变量只在首个信任边界建立一次；内部不得对同一必填对象重复 `== null` 防御，也不得用逐字段空值映射伪造查询未命中。

## 成功结果、失败语义与异常传播

- 成功返回领域结果，失败使用能够表达恢复责任的异常合同。
- 查询缺失、数据损坏、非法外部输入、配置或依赖缺失，以及外部故障使用可区分的失败语义；不得把异常、数据损坏或外部故障转换为 `null`、空集合、状态码或成功。
- 配置缺失、依赖缺失和非法外部输入必须在对应边界快速失败，不能用空值或默认成功掩盖。
- 只捕获能够恢复或映射的具体异常，保留 cause；不解析异常消息控制流程。
- 外部状态码只在 Adapter 完成一次映射，不能以裸 `int`、`String` 或 `boolean` 跨层分派业务行为。

## 查询、命令与副作用

查询返回信息且没有可观察副作用；命令改变状态或执行副作用。名称、返回值和行为必须一致。用例同时读取和修改时，由调用方显式编排两个语义清晰的动作。合法的“命令返回创建结果”等外部合同，必须由 Design、接口或测试事实说明。

## 类型、参数、返回值与协议边界

- 参数只作为输入，不把可变参数改写成输出容器。
- 值对象只用于稳定领域概念、共同不变量、类型混淆、重复校验或高后果错误。
- 不为降低参数数量机械创建 `Param`、`Context`、`Command` 或 `Result`。
- 禁止通用 `success/code/message/data` 结果形状进入业务 Module；协议响应壳只留在 Adapter。
- 精度、长度、格式、可空性和集合语义与 Schema 或外部协议一致。

## 模块职责、依赖与克制抽象

- 每项稳定的领域规则、状态迁移和失败语义只由一个业务模块负责。该模块对外提供完成业务决策所需的最小稳定接口；调用方不得重复实现其中的校验、映射、生命周期判断或异常分类，也不得依赖模块内部步骤、存储细节和协作者。
- 模块内部封装完整规则和实现复杂性，对外暴露的接口较少且稳定；
- 业务模块的依赖通过构造器传入；对象的创建和依赖组装只发生在明确的启动或组装边界，不由业务代码隐式查找或创建外部依赖。
- 默认使用具体类型和组合。只有在以下事实至少满足一项时，才引入 Interface、Factory、Strategy 或注册表：已有第二个生产实现；批准的需求明确要求多个实现或运行时选择；外部协议已经要求该扩展点。
- 优先使用不可变状态、组合和最小可见性，把实现细节限制在所属模块内。不得为尚未出现在批准合同中的场景增加配置开关、扩展点、依赖或死代码。
- 如果实现需要改变公共接口、职责归属、数据所有权或依赖方向，必须返回上游合同重新确认。
## 命名、注释、控制流与事实约束

类、方法、参数和变量使用领域词汇并表达意图。禁止无领域限定的 `execute`、`resolve`、`handle`、`process`、`data`、`result`、`helper`、`manager` 等弱名称；`normal`、`special` 等相对分类词必须能指出互斥分类、划分规则和业务含义，否则改用具体领域状态。名称是否具有领域含义只能由 Reviewer 结合具体 symbol 和调用上下文判断，不新增基于词表的机械报错。

代码以命名和结构自释义，不生成复述查询、判断、调用或保存步骤的注释，也不强制普通实现或测试声明添加 JavaDoc。生产和测试代码均禁止 `// 1.`、`// Step 1`、`// 步骤一`、`// 第一步` 等步骤序号注释。简单测试不添加 Given/When/Then 旁白；只有仓库已有一致惯例且长场景确需分段时才保留。只有代码无法表达的外部原因、兼容限制、协议顺序或算法依据才保留简短英文注释，并说明为什么不能采用更直接的实现；仓库注释惯例和 AGENTS/Trellis 要求不能扩大该范围。

控制流首先追求线性和单一抽象层级。循环顶层允许使用无标签 `continue` 跳过含义明确的不适用元素，但 Reviewer 必须确认它降低嵌套、跳过条件具有业务名称且没有绕过必要副作用；带标签的 `continue` 禁止交付，嵌套循环、多个跳过点或复杂分支中的 `continue` 必须重构。单层三元表达式只用于无副作用且含义直接的值选择；嵌套或同一表达式中重复的三元表达式必须在 Review 中改为清晰控制流。项目已有 Checkstyle、PMD、Sonar 或 IDE 指标时复用其结果；否则由 Reviewer 估算。方法圈复杂度超过 `10` 或嵌套深度超过 `5` 时必须简化，不为此新增正则复杂度计算器或 Java 解析依赖。

## 日志、时间与运行观测

日志服务于故障定位、运营或审计。一次失败只由真正消费异常并终止传播的边界记录一次；映射后继续抛出的层不记录同一失败。记录完整异常及必要的结构化字段，禁止凭证、完整载荷和敏感数据。不得仅因任务触及外部边界就新增日志；只有 Prompt、Design 或现有项目观测合同要求时才修改日志。

禁止用 `System.currentTimeMillis()`、`System.nanoTime()`、`durationMs` 或等价局部变量手工生成耗时日志；性能观测复用现有 tracing、metrics、AOP 或统一埋点。业务时间使用注入的 `Clock` 或仓库既有时间抽象。日志数量、分支日志和所有权由审查共同判断，不能只凭层名决定。

## 质量路由

质量路由优先于把本地实现当作设计标准，并建立在 Design/Plan 的精确影响锚点或 Prompt-only
场景的一次受限调查上。Design/Plan 已关闭的结果、失败、所有权和依赖方向不为路由重新取证；
只读取本次计划修改的 symbol、必要直接依赖和代码增量。只有发现公共接口、跨模块所有权或真实
变化轴等具体信号时才扩展到直接相关实现，不做无关全仓盘点。路由不是“代码改了就加载一个
通用质量 Skill”，而是根据具体风险选择最小原则集合；未命中专项路由时由本文件其他原则兜底。

| 事实或风险 | 精确 Skill | 允许用途 |
| --- | --- | --- |
| Interface、Seam、Depth、Locality、跨模块规则归属 | `$codebase-design` | 受影响链路和模块设计约束 |
| Java 职责、封装、重复、方法或异常合同 | `$121-java-object-oriented-design` | 职责、封装和异常设计约束 |
| primitive obsession、值对象、类型层级、签名混淆 | `$122-java-type-design` | 类型和签名设计约束 |
| 只需聚焦某一个 SOLID 原则 | `$solid-principles` | 对应原则的设计约束；避免与 121 重复加载 |
| 已证明存在多个真实实现或变化轴 | `$design-patterns` | 模式取舍和扩展点设计约束 |
| 已由具体 symbol 证实的弱语义命名、方法粒度或可读性风险 | `$clean-code` | 只读生成约束；不作为通用质量门禁 |
| 已由具体 Java symbol 证实的空值、异常、并发、资源、性能或 API 风险 | `$java-code-review` | 对完整代码提案的定向 Reviewer/Repair；不替代项目验证 |
| 逻辑行为、测试 seam、行为断言或边界替身 | `$tdd` | 优先测试设计约束；不把 TDD 流程复制到 Plan |

执行模式的非平凡生产代码只执行一次合并 Review：以 `clean-code-guard` 为基础，并把所有命中路由的约束合并进去，不为每条路由依次启动重复审查。只有 Review 发现有具体代码、合同或行为依据且确实需要结构调整的问题时才调用 `refactor`；简单局部修复直接集中处理。修复完成后统一复核受影响项。

## 行为测试与验证

测试通过执行合同批准的公共验证入口，观察业务结果、状态、异常或完整边界请求。只替换数据库、网络、时间和随机等系统边界；不 mock 自有内部协作者，不测试 private 方法，不复制实现算法生成期望值，不以调用次数代替主要行为证据。

不得在 `@Disabled`、`@Ignore`、元注解或条件禁用范围新增业务测试，也不得通过构建参数、过滤器或测试发现配置跳过测试。
