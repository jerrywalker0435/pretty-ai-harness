# Java 执行质量补充

本文件补充 `clean-code-guard` 的强制代码约束、执行合同、Java/Spring 语义、注释与运行观测的信息充分性
及行为测试要求，并限定可能诱导形式化拆分的通用建议适用口径，不复述其通用质量规则。
机械规则及默认覆盖率阈值以 `../scripts/quality_registry.py` 为机器来源。

## 简单实现优先

Plan 和 Execution 在完整满足合同与项目必要边界的前提下，优先选择容易沿公共入口理解、引入
更少概念和调用层次的实现。判断整个受影响链路的理解成本，不以单个方法短、diff 小或设计模式
齐全判定简洁；同时遵循 [重构授权与问题分级](../SKILL.md#重构授权与问题分级)，
仅新增单元默认允许重构，旧代码只做必要修改；不追求最少行数，也不扩展为历史代码整理。

- 先复用现有能力，再在现有职责所属位置直接实现。只有当前规则需要独立封装、存在真实复用、
  必须隔离外部边界或确实降低理解成本时，才抽取方法、类型或增加一层调用。
- 新增类型、方法、分支和转换必须有当前用途。仅转发同样的参数、包装后立即拆开且没有独立
  规则、重复解释同一决策的结构应合并或移除；单调用方本身不是违规，必要协议 DTO、值对象、
  端口和具备独立语义的方法仍可保留。
- 方法行数、参数数量和嵌套深度是核验职责、内聚与误用风险的线索，不单独构成阻断证据；圈复杂度
  按下文不超过 5 的硬上限执行。超限时先消除重复决策或简化条件，再按独立业务规则分解；不得靠
  隐藏分支、无语义转发、多层单次调用或无意义参数包装达标。
- 少量、稳定且属于同一规则的封闭分支可直接表达。策略、注册表、工厂和接口必须解决当前
  真实扩展或边界问题；不为尚无消费者的未来变体搭建框架，也不机械替换每个 `if/switch`。
- 在新增单元、本次引入的问题或用户明确指定重构的位置，移除重复校验、重复规范化、无意义映射、
  死分支和无当前用途的代码；历史结构问题仅作非阻断建议。
  判定未使用时核验直接调用、框架注册、反射和外部消费者；必要的协议映射不因形式相似而删除。
- 复用已有错误类型与观测能力；只有调用方确需区分且现有类型无法表达的失败才新增异常或结果
  类型。CQS 修复保持既定操作和一致性语义，不以额外查询、共享状态或存储换取形式合规。

### 新增必要性适用范围

“非必要、勿新增”适用于实现、测试、依赖、配置、脚本、文档和执行产物。先复用当前仓库及本次已读事实；
只有当前合同、用户授权或工具运行前置条件要求，且删除该新增会损失必要行为、约束、验证能力、外部协议
或构建能力时才新增。必要性必须落在已有 Plan、Review JSON 或执行记录字段中，不另建复用清单、调查报告
或审查阶段。构建缓存、临时证据和生成目录只在命令确实需要时创建，并在收尾按执行规则清理。

边界校验、安全措施、避免数据丢失的错误处理、事务/并发/幂等保证及已要求的业务行为必须保留。
重构授权内的等价简化直接实施；新增代码的纯结构优化需连带重构旧代码时仅作建议。
涉及明确保留要求或业务合同变化时按 `../SKILL.md` 的输入优先级和
仓库差异分类处理。上述结构性适用口径用于生成与同一次 Review，不增加候选方案文档、数值
配额、JSON 清单或额外审查阶段。

## 强制代码约束

以下要求适用于 Plan 代码块和 Execution 生成的生产、测试代码。本次新增或实质修改的实现必须满足，
仅注释、格式或等价改名不触发历史实现整改，但新增或修改的命名仍须满足语义要求。不扩展为全仓清理；
本次适用项不能以历史问题、代码短、项目惯例或普通质量例外降级。与不可修改合同冲突时报告具体事实，
由用户决定方向，不自行违反要求或改变合同。

### 圈复杂度不超过 5

- 每个新增或修改实现的方法、构造器、初始化块及 Lambda 独立计数，上限均为 5；修改旧方法时计算
  修改后的完整方法，不能只计算 diff 中增加的分支，也不能以“原来就超过 5”为由放行。
- 使用 McCabe 圈复杂度，不用认知复杂度、嵌套层数或行数替代。统一按入口 1，加每个 `if`、循环
  （`for`/`while`/`do-while`，后者只算一次）、`catch`、非 `default` 的 `case` 分支、三元条件及
  `&&`/`||` 短路点计数；`else if` 按 `if` 计，模式匹配的 `when` 守卫也算条件。分组 case 标签
  共用同一分支时计一次；`else`、`default`、`finally`、普通 `return/throw` 不额外增加。
- Lambda、局部类和匿名类的方法独立核验，不重复计入外层方法；不得通过转移到这些位置漏检分支。
  优先使用项目已有静态分析，核对计数口径；工具不覆盖的语法或计数差异在同一次 Review 中补核。
  无工具时逐单元列出决策点计算，不能以“看起来简单”认定通过。
- 超限属于阻断问题。只在受影响单元及必要调用方内简化重复判断或按业务规则拆分，保持行为、事务、
  并发与失败语义；新拆出的单元也必须满足上限。不能靠忽略告警、修改阈值或删除必要分支通过。

### 全部自主命名表达业务语义

- 包、类、接口、方法、字段、参数、局部变量、常量、枚举及测试等自主命名均说明业务对象、用途、动作或结果；
  必要时带上单位和范围。例如 `pendingOrders`、`paymentAmountInCents`、`canShipOrder`。
  不用缺乏具体语义的 `data`、`info`、`obj`、`tmp`、`flag`、`result` 或 `handle/process` 代替。
- 名称必须与实际职责一致；查询或谓词名称不能掩盖写行为，业务注释不能替代语义命名。纯技术辅助
  命名说明其具体技术用途，不编造业务概念；框架或外部协议固定的名称保持兼容，可自主选择的名称
  仍须符合本节要求，不以固定签名为由保留无意义的参数和局部变量名称。

### 禁止使用 JSONObject

- 禁止任何来源的 `JSONObject`（包括 Fastjson、Fastjson2、Hutool、org.json 等）的引用、构造、
  参数、返回值及使用；全限定名、静态工厂、默认返回 JSONObject 的解析重载，以及用 `Object`/`var`
  隐藏实际类型也不合规。不能只检查 import 或 `new JSONObject`。
- 使用已有且语义匹配的类型、DTO/record 或明确类型的序列化接口承载当前合同；缺少类型时只新增
  必要的数据合同。不以未获授权的 `Map` 替代 JSONObject。

### Map 必须必要且事先获授权

- 新增代码默认使用已有业务类型、必要的明确字段对象或合适的集合。Map 包括其实现和子接口，
  如 `HashMap`、`LinkedHashMap`、`ConcurrentMap`，也包括 `Map.of`、`toMap`、`groupingBy` 等
  产生的结构；即使通过 `var`、返回值或现有 API 间接使用，也不能绕过授权。
- 确需新增 Map 使用时，先形成具体提案：`path#symbol`、键和值的业务语义及拟用类型、用途和生命周期、
  必要性依据、已有类型或其他结构为何不足。动态键、索引性能或外部签名可以作为事实依据，但不自动
  构成授权；不能只写“方便”“灵活”或假设未来扩展。
- 向用户说明上述原因并明确请求该用途的授权。收到授权前，不把该 Map 用法写入 Plan 代码块或真实
  实现；优先完成可采用合理替代方案及不依赖该决定的工作。用户不批准时采用替代方案，确实不可替代
  时保留具体阻塞，不擅自使用。
- 已有针对同一用途和范围的明确授权持续有效；在 Plan 现有约束或执行记录的审查字段记录授权依据，
  不另建审批文档。Design/Plan 中出现 Map、笼统同意实施或不可修改的外部签名不代替明确授权。
  未改动的历史 Map 不要求全仓整改；本次新增用法或扩大既有授权范围仍须先获授权。

### 查询与判断条件禁止调用写方法

- 查询方法、查询表达式及判断条件不得直接或间接调用业务写方法；范围包括 `if`、循环条件、三元条件、
  `&&/||`、`switch` 选择表达式、谓词、Stream 的 `filter/anyMatch/allMatch` 及其委托调用。
  必须核对被调用实现，不能仅凭 `get/find/is/can/check` 等名称推断只读。
- 写行为包括数据库增删改、业务实体或共享状态修改、缓存写入或失效、发消息及有状态变更的外部调用。
  “查询不存在就创建”“判断时刷新状态”“过滤时更新记录”均不合规。构造局部查询结果所需的局部赋值
  和集合填充，以及不改变业务状态的既有日志/观测，不视为业务写；不能借此修改输入对象或共享集合。
- 必要写操作放在明确的命令流程中；先基于只读条件决定是否执行命令，或在命令完成后判断已取得的
  结果。例如 `if (saveOrder(order))` 不合规；在命令流程中先取得 `orderSaveResult` 再判断结果可以，
  但写方法的返回契约仍须满足 CQS 规则。仅把写调用移到查询方法内的局部变量，不能消除查询副作用。
- 调整必须保持原有执行次数、短路求值、事务与幂等边界；不得把原本有条件的写入变成无条件执行，
  也不得通过新增查询、状态副本或共享存储掩盖副作用。

### 禁止 continue 语句

禁止普通 `continue;` 和带标签的 `continue label;`，包括嵌套循环中的使用。按业务条件组织循环体，
必要时提取有独立业务语义的处理方法；保持遍历顺序、每轮处理及副作用次数，不用 `break`、异常或
标记变量机械替换，也不能因消除 continue 使圈复杂度超过 5。

上述要求按[强制约束核验](quality-review-contract.md#强制代码约束核验)纳入同一次 Review；
不新增独立审查阶段，不用词法扫描替代复杂度计数、业务语义、真实类型、授权及调用链核验。

## 禁止使用魔法值

Plan 代码块与 Execution 新增或修改的代码（含测试）不得使用魔法值：数字、字符串、字符等字面量
承载业务或技术约定，却无法从名称、类型及所在上下文直接理解其含义、单位或用途。是否重复出现
不是判定条件；只出现一次的状态码、超时、重试上限、分页大小、比例或特殊标记也须表达语义。

- 优先复用项目、JDK 或已用依赖中语义一致的常量、枚举及类型；缺少时在规则所属位置以最小作用域
  定义有意义的常量。有限状态优先使用现有枚举，时间优先使用 `Duration` 等带单位的类型；只有
  当前需求需要运行时或环境调整时才引入配置，不为消除字面量新增无用途的类型或配置项。
- 名称表达业务用途及必要单位，例如 `PAYMENT_TIMEOUT`、`MAX_RETRY_ATTEMPTS`；`VALUE_1800`、
  `NUMBER_THREE` 等仅复述数值的名称不合格，注释也不能代替必要的语义命名。相同语义复用同一
  定义，数值相同但语义不同不得合并，不堆入无归属的通用 `Constants` 类。
- 字面量可以出现在有明确语义的定义或协议映射中，例如
  `PAYMENT_TIMEOUT = Duration.ofMinutes(30)`、`PENDING_PAYMENT(3)`；外部协议值须保持不变，
  在边界映射为具名的内部语义，不让裸值散落在业务判断中。具体取值来自已确认合同或仓库事实，
  不自行猜测业务阈值、状态含义或单位。
- `count > 0`、循环起始索引 `0` 等上下文已清楚的字面量可以保留；`0`、`1`、`-1` 不是通用豁免，
  用作业务状态或特殊哨兵时仍须命名。测试中已由用例、变量或断言清楚表达的输入与预期值可以
  直接写明；不为了消除字面量而引用被测生产常量计算预期值，导致合同取值变化时测试无法发现。

按[魔法值核验](quality-review-contract.md#魔法值核验)执行语义审查与限定修复，不用正则将所有
字面量判为违规。修改旧方法不要求清理其中未引入或加重的历史魔法值；本次新写、修改语义的
字面量仍须表达含义，不能以所在方法既有为由豁免。

## 受影响链路与合同归属

已批准 Design 或 Plan 提供有效锚点时直接采用其链路；Prompt-only 或锚点失效时定向确认，
已读事实出现具体复用疑点时按 `../SKILL.md` 的“变更边界”补查必要定义、调用方和边界：

```text
入口 → caller → callee → Adapter → 持久化或外部系统
```

- 修改范围止于真实受影响链路，并确认状态迁移、消费者、注册点，以及事务、并发、幂等、安全和兼容边界。
- 每项稳定的领域规则、状态迁移和失败分类只有一个业务所有者；调用方不得重新解释该合同。
- 已授权合同要求的外部结果、公共接口、数据所有权或依赖方向变更直接实施；超出合同或存在
  未关闭的关键决定时，按 `../SKILL.md` 的“仓库差异分类”核验并报告具体缺口。
- 真实仓库用于确认签名、依赖 API、项目惯例和可复用组件，不能代替 Design、Plan 或 Prompt
  决定业务语义。

## Java/Spring 合同语义

### 规范化、可空性与字段选择

- 外部文本只有在协议或 Schema 明确要求时，才在首次接收它的边界完成 `trim`、大小写折叠或默认值转换。
  已可信的内部值、持久化值、ID 和 Code 不再执行 `hasText`、`trim`、大小写转换或空值兜底。
- 领域类型、协议类型或兼容 Adapter 可以拥有合同明确的转换；Helper 名称不能证明转换责任，
  必须根据输入来源、调用链和边界合同判断。
- 备用字段选择必须由 Design、外部协议或 Schema 明确字段优先级、等价性和缺失语义；不能用另一字段
  掩盖必填值缺失或数据损坏。
- `null` 只用于框架、外部协议或遗留签名明确声明的可空合同，并通过注解或测试固定；查询未命中、
  数据损坏和外部失败不得共享同一个空值语义。

### 结果、失败与协议映射

- 查询未命中、数据损坏、非法外部输入、配置或依赖缺失及外部故障必须具有可区分的结果或异常语义。
- 异常在边界映射时保留 cause；不解析异常消息决定控制流。
- 外部状态码只在 Adapter 映射一次，不以裸 `int`、`String` 或 `boolean` 跨层分派业务行为。
- `success/code/message/data` 一类协议响应壳只留在 Adapter；业务 Module 返回领域结果。
- 精度、长度、格式、可空性和集合语义必须与真实 Schema 或外部协议一致。

## 注释与日志的信息充分性

Plan 代码块与 Execution 新增或实质修改的核心业务规则必须有业务说明；隐含知识和运行观测按下文
要求补充，无须 Prompt、Design 逐项声明。先核对已有说明与观测，按规则和信息缺口补齐，不按方法
数量、注释率或日志条数添加，也不扩展为全仓补齐。业务说明依据已确认的需求和合同；语义未明确时
按合同缺口处理，不编造原因或合同。

### 注释表达业务规则与隐含知识

- 核心业务规则按是否决定业务结果判断，包括业务准入条件、状态流转、金额或数量计算、处理顺序、
  去重、跳过及失败处置；即使只有一行代码也适用。普通 getter、简单转发、纯技术装配及无业务含义的
  格式转换不默认添加；仅格式化、移动或等价改名不触发历史业务说明补齐。
- 在规则所属方法用简短中文 JavaDoc 说明业务职责、关键条件与结果，让读者无需展开实现就能理解。
  即使规则可从方法名或多段代码推导，也不能省略业务说明；使用领域术语描述长期成立的规则，
  不复述签名或调用步骤。例如“为已支付订单发放权益；重复支付通知不重复发放”，而非“判断支付状态，
  然后调用发放方法”。
- 同一规则只维护一份说明；规则所属方法或调用方可见接口已有准确 JavaDoc 时复用，其他位置按需引用，
  不沿调用链逐层复制。关键分支只补充方法说明未覆盖的局部例外、限制或非直觉原因。修改旧方法时，
  只补充与本次业务变化相关的必要说明，不借此补齐整个文件或调用链的历史注释。

此外，缺少说明会使维护者误改或调用方误用，而类型、命名、注解不能清楚表达以下信息时，
在知识所属位置或调用方可见的接口处补充注释：

- 业务原因与非直觉约束，例如操作顺序背后的业务原因、事务或并发不变量。
- 隐含字段语义，例如金额单位、时间区间端点、空集合的业务含义。
- 调用合同，例如副作用、事务前提、重试条件及调用方需要区分的失败语义。
- 兼容取舍，包括保留特殊逻辑的依据，以及可核查的移除条件。

不逐行翻译代码、添加步骤编号或写“本次新增”等变更记录，不把 Design 全文搬进注释。注释不能
替代清晰的命名与类型；核心业务说明也不因命名改善而省略。修改相关行为时同步核对并更新或移除
失效注释，保证说明与当前规则一致。

### 日志、时间与运行观测

- 判断标准：出现问题时，已有日志、tracing、metrics 或审计记录能否回答“哪个业务对象、发生了
  什么、为什么”？先核验现有观测是否包含所需信息；足以定位时复用，不重复记录。
- 本次新增或修改的 RPC/HTTP 外部调用、MQ 发送及 MQ 接收（含重试和重复投递），每次尝试都要有
  可关联的日志记录，覆盖成功、失败和超时。优先复用现有拦截器、客户端或消息框架的逐次日志；
  已记录下述必要信息时不在业务代码重复打印。记录安全的请求或消息关键字段、操作或目标、业务
  及链路关联标识、实际结果（如状态码、确认状态或失败类别），只记录必要且可安全输出的响应字段。
  在能确定该次结果的位置记录；发送受理、Broker 确认和消费处理完成须按实际边界区分，不把前一
  阶段记为后一阶段成功。无需机械添加调用前、调用后两条日志，也不记录完整入参或出参。
- 工单创建、状态流转、任务执行等关键业务操作，在现有观测不足时记录最终结果，包括正常成功；
  在掌握执行结论的位置记录必要的业务标识、操作、结果和关联标识。普通查询、方法进入退出和
  内部转换不默认记录。成功日志必须与实际完成边界一致，不把已受理或事务内待提交当作最终成功。
- 影响预期业务结果的跳过、降级或部分成功，在现有观测无法解释时必须记录原因和影响范围。
  级别遵循项目惯例并按实际影响判断：关键操作正常完成通常为 INFO；正常幂等去重或预期内无需
  处理默认不逐条记录（上述外部调用及 MQ 收发除外），必要时用 DEBUG；非预期跳过、启用降级或
  需要关注的部分成功用 WARN；最终操作故障用 ERROR，预期业务拒绝不自动升级为 ERROR。
- 一次失败由终止其传播或完成边界映射的位置记录一次，继续抛出的中间层不重复记录。
  外部调用失败与最终业务失败是不同事件，但同一次外部失败不在传播链上重复记录。记录异常时
  保留完整异常和 cause，不仅输出异常消息。
- 复用项目日志框架和结构化字段惯例，只记录定位所需字段；不序列化整个请求或响应，不记录凭证、
  认证头、完整载荷或敏感数据。
- 耗时观测复用项目已有 tracing、metrics、AOP 或统一埋点，不使用
  `System.currentTimeMillis()`、`System.nanoTime()` 或局部 duration 变量生成日志。
- 业务时间使用注入的 `Clock` 或项目已有时间抽象。

注释与日志的信息缺口按[语义审查要求](quality-review-contract.md#注释与日志信息充分性核验)
进入现有 finding 闭环；不新增数量、比例或正则门禁。

## 机械门禁边界

机械门禁只保留无需理解业务上下文即可判定的 Java/Spring 交付错误：

- `CONTINUE-STATEMENT`
- `VOID_TAIL_RETURN`
- `UNREACHABLE_STATEMENT`
- `EMPTY_CATCH`
- `WHOLE-OBJECT-LOGGING`
- `SENSITIVE-LOGGING`
- `MANUAL-DURATION-LOGGING`

优先使用项目已接入的 Checkstyle/PMD 和编译器规则，并核实实际配置及运行结果；不能仅因存在
配置文件就视为通过。本仓库的辅助门禁提供无新增依赖的受限词法扫描作为补充：

- `CONTINUE-STATEMENT`：拒绝普通及带标签的 continue 语句；忽略注释和字符串中的文本，增量扫描
  检查语句跨度内的改动。Review 仍核对本次实质修改的完整实现，不能因关键字所在行未改动而豁免。
- `VOID_TAIL_RETURN`：检查 `void` 方法体的最后一条直接语句是否为无条件 `return;`；增量扫描仅在
  该 return 语句有改动时报告，不因修改方法内其他行而要求删除历史 return。
- `UNREACHABLE_STATEMENT`：检查同一块内无条件 `return/throw/break/continue` 后的直接语句；
  条件提前返回、下一 `case/default` 不算命中。
- `EMPTY_CATCH`：捕获体仅含空白、注释、空语句或空块时失败。

该扫描不是完整 Java AST/控制流分析；跨分支终止推导、无限循环、复杂标签和 Unicode 转义等仍由
项目编译器、静态分析及全量 Review 核验。带 `--base` 时按新增/修改行限定扫描，纯删除造成的
控制流变化也必须在 Review 和编译中检查。执行模式使用 `--base`，避免全文件扫描扩大整改范围；
`--source` 或省略 `--base` 会扫描完整文件，不据此判断 symbol 是新增还是修改。
方法末尾的冗余 `return;` 通常不会导致编译失败，必须执行对应静态规则。

机械 finding 均为 `error`，命中时脚本返回失败。Plan 扫描完整旧 symbol、格式变化或同一行包含
其他修改时，可能命中历史结构问题；在同一次 Review 中对照基线分级。确属未获授权的历史纯结构
问题时记为 advisory，保留原始扫描结果和退出码，不要求靠重构旧代码使扫描清零；最终是否阻断以
Review 分级为准。正确性问题、本次引入问题及项目强制检查失败不能借此降级。
通用可读性、异常处理和依赖注入由 `clean-code-guard` 判断；复杂度及其他强制项按
[强制代码约束](#强制代码约束)核验；测试禁用由测试守卫判断；import 风格交给项目既有工具，
不以辅助机械扫描通过代替上述核验。

## 非平凡生产代码判定

“非平凡生产代码变更”不是按 diff 行数判断，而是会改变运行时行为、业务或外部合同，或引入需要
质量判断的运行风险与结构变化的生产代码变更。满足以下任一条件即属于非平凡：

- 新增或修改业务分支、校验、状态迁移、查询结果或失败语义；
- 修改公共 API、序列化、Schema、数据库访问或跨服务协议；
- 修改 `null`/异常语义、事务、并发、幂等、权限、安全、依赖、日志、时间或性能行为；
- 新增或调整类、接口、抽象、模块职责、所有权、耦合或依赖方向；
- 修改会影响运行时行为或外部合同的配置。

以下变更在确认没有隐含行为影响时通常属于平凡变更，不单独触发 `clean-code-guard` 全量发现
Review：纯格式或 import 排序、只改注释/文档、纯数据载体或生成代码，以及不影响 API、反射和
序列化的机械重命名。含有字段校验、转换、默认值、不变量或其他逻辑的 DTO/生成文件仍属于非平凡。

同一 diff 只要包含一项非平凡生产变更，整体按非平凡处理；测试代码的质量审查仍由测试守卫负责。

## 质量路由

`clean-code-guard` 是上述非平凡生产代码一次全量发现 Review 的通用基线。路由器只按实际增量选择
它未覆盖的专项能力，不为同一问题加载另一套通用 Clean Code、SOLID、DRY、KISS 或 YAGNI 审查：

| 事实或风险 | 精确 Skill | 允许用途 |
| --- | --- | --- |
| Interface、Seam、Depth、Locality、跨模块规则归属 | `$codebase-design` | 受影响链路和深模块边界 |
| primitive obsession、值对象、类型层级、签名混淆 | `$122-java-type-design` | Java 类型与签名设计 |
| 并发、事务、资源、响应式链路或外部依赖 API 风险 | `$java-code-review` | Java/Spring 运行时专项检查 |
| 逻辑行为、测试 seam、行为断言或边界替身 | `$tdd` | 行为测试设计 |

新增或修改职责的生产类型必须按[类型必要性核验](quality-review-contract.md#生产类型必要性核验)
检查定义、实际调用方和删除影响，并将适用路由规则落实为证据及 finding。字段数、调用方数量不能
代替语义判断；新增纯数据载体也要核验其必要契约，测试和覆盖率豁免不构成类型免审。

所有命中路由与 `clean-code-guard` 在一次全量发现 Review 中执行；后续按
[质量 Review 合同](quality-review-contract.md)，只允许围绕已发现 finding 及其实际修复增量进行
限定复核，不得启动第二次全量 Review。路由和修复均不得扩大 Design、Plan 或 Prompt 确定的影响
范围，也不得把相邻实现直接当作业务合同。

## 行为测试与验证

测试通过执行合同批准的公共入口观察业务结果、状态、异常或完整边界请求。只替换数据库、网络、
时间和随机等系统边界；不 mock 自有内部协作者，不测试 private 方法，不复制生产算法生成期望值，
不以调用次数代替主要行为证据。

不得在 `@Disabled`、`@Ignore`、元注解或条件禁用范围新增业务测试，也不得通过构建参数、过滤器
或测试发现配置跳过测试。
