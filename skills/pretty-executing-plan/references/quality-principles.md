# Execution 代码质量原则

这些原则用于审查真实增量代码、测试、调用链、配置、SQL/Schema 和外部协议。它们是代码设计与生成质量基线，不是质量自评文案。

## 1. 全局设计优先

先分析入口 → caller → callee → Adapter → 持久化/外部系统，再决定局部文件。范围止于受影响链路，不扩张为全仓翻新。明确规则归属、数据所有权、不变量、事务、并发、幂等、重试、性能和安全边界。

## 2. 契约先行、边界校验、内部信任、快速失败

区分必填、可选、默认和外部不可信值。在第一次进入信任域的边界校验/规范化一次；内部依赖已建立的不变量，不重复防御或静默传递 `null`。配置、依赖和非法输入在正确边界快速失败。

## 3. 约定大于配置

优先使用已批准合同、Java/Spring 标准约定和仓库稳定约定。恒定业务规则、猜测性变化轴和错误恢复责任不得做成开关、模式码或动态配置。只有真实环境/部署差异才进入配置，必填配置必须类型化校验并在启动时失败。

## 4. 避免过度防御

禁止用 `record == null ? null : ...`、`orElse(null)`、宽泛 catch 后返回空值或成功结果掩盖契约问题。机器标识符默认拒绝 `null`、空白和首尾空格；历史脏数据必须显式治理，不能由通用 helper 永久掩盖。

## 5. 正常流与异常流分离

避免裸 `int`、`String`、`boolean` 类型码控制跨层流程。成功返回领域结果，真正异常使用明确异常合同；不以异常替代高频正常分支，不解析异常消息或数字错误码决定控制流。

## 6. 查询与命令分离

查询方法只读取并返回信息，不产生业务、持久化、缓存、日志或外部调用等可观察副作用；命令方法负责改变状态或执行副作用，不同时伪装成查询。方法名称、返回值和实际行为必须一致，禁止一个方法同时承担查询和命令职责。

## 7. 参数只作为输入

方法参数不能充当返回参数。禁止在方法内部修改可变参数后再把该参数作为返回结果或输出容器；需要返回新状态时创建明确的新结果、值对象或副本。方法的输入、状态变化和返回值必须具有独立、可理解的语义。

## 8. 领域命名与实现证据优先

新增或修改的 symbol 优先使用批准的领域词汇。`execute`、`resolve`、`handle`、`do`、`action`、`deal` 等弱语义词默认禁止，仅框架合同或真实领域词汇例外。具体实现、真实调用链、类型、配置、SQL/Schema 和有效测试优先于普通注释；权威合同与代码冲突时返回上游。

## 9. 日志是可观测性设计

日志所有权属于真正消费或处置异常并终止其传播的边界；HTTP `@ExceptionHandler`、消息终端或调度终端记录一次。catch 后继续抛出原异常或包装异常的层不得重复记录；不把 `logPrefix`、`enableLog` 或日志上下文塞进业务参数/对象；敏感信息不入日志。

## 10. 参数、结果和值对象有领域语义

不按参数数量流水线创建 `Command`、`Param`、`Context` 或通用 `Result`。只有共同不变量、稳定共同演化的领域概念、跨模块身份、类型混淆或明确边界才封装。不要创建 `Result{success, code, message, data}` 这类通用返回码对象。

## 11. 按证据引入值对象或模式

只有独立不变量、类型混淆、跨模块传播或已证明变化轴才引入值对象、Factory、Strategy、Adapter 等模式。不要为了消灭一次判空而过度封装，不把猜测性未来变化变成抽象层。

## 12. 增量代码必须提供实现证据

实际 diff 必须能与 Plan TASK、稳定 symbol、调用链、公共行为、测试结果和验证范围对应。不能用普通注释、空泛结论、伪造测试或覆盖率数字替代实现证据；未验证的数据库、远端服务、部署和人工联调必须明确声明。
