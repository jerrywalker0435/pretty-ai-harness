# 高质量计划执行门禁

## 执行报告结构

报告标题使用 `# <主题>执行报告`，并按顺序包含：

1. `执行概览`
2. `输入与批准`
3. `执行控制`
4. `工作区与质量基线`
5. `执行引擎`
6. `任务执行证据`
7. `集成单元检查点`
8. `业务切片质量门禁`
9. `测试覆盖率`
10. `代码质量审查`
11. `偏差与阻塞`
12. `最终全量验证`
13. `授权与 Git 操作`
14. `最终质量结论`

每个行为任务记录 `RED 命令/退出码/预期失败/实际摘要`、`GREEN 命令/退出码`、`重构复验命令/退出码`。非行为任务记录任务类型、不适用理由、等价验证命令和退出码。

报告还必须明确：

- Plan、Design、PRD 路径和执行批次；不适用的输入写理由。
- 执行模式、当前状态、当前集成单元、主工作区、主分支、基线/预期 HEAD、洁净检查和自动编排状态。
- 按时间追加的控制事件；每项记录合法 `状态转换`、触发来源和恢复入口。
- 每个执行批次的 `Plan 批次基线哈希`、批准记录、既有成果复核和 `批次结论`；首次批次的既有成果复核可写带理由的不适用。
- 每个任务的 `Plan 只读复验哈希` 和 `Plan 只读复验结论`；最终记录 `Plan 最终哈希` 和 `Plan 只读校验`。
- Worktree 路径、忽略检查和忽略修复；项目内 `.worktrees/` 必须证明报告所记 `主工作区路径` 的根 `.gitignore` 含精确规则 `/.worktrees/`、`grep -Fxq '/.worktrees/' <main-workspace>/.gitignore` 与 `git -C <main-workspace> check-ignore -q .worktrees/` 均通过。
- 基线命令、退出码、测试和覆盖率摘要，以及基线结论。
- 执行引擎选择、子 Agent 使用情况和任务串并行口径。
- 每个集成单元的风险等级、Reviewer 策略、候选提交、候选树、集成映射、五项指纹、Review、候选差异应用、当前分支提交批准、批准内容指纹和阶段耗时。
- 每个审查 Skill 的范围、发现、修复和复查结果。
- `功能完整性核对`、`简洁性与必要性审查`、`可读性与业务表达审查`、`测试完整性保护` 和 `变更范围控制` 的逐项结论与必要证据。
- 覆盖率适用性、统计范围、指标、阈值、实际结果、命令、退出码和报告位置。
- 排除项与 Plan 的逐项一致性；不得只写“按配置执行”。
- 最终回归、编译、覆盖率、验证和 `finish-work` 的新鲜证据。
- 实际偏差、阻塞、用户批准和 Git 操作；没有时明确写“无”。
- 最终结论只允许 `完成`、`未完成` 或 `阻塞`，并列出未闭环项。

`任务执行证据` 内按时间顺序使用 `### 执行批次 <序号>：<说明>`，随后记录批次基线、批准和既有成果复核，再记录该批次的 `### 任务 ...`。恢复或重新批准只能向后追加，不得把新哈希写入旧批次。

批准与复核使用可校验格式：首次批次写 `Plan 批次批准：首次批准（<证据>）` 和 `既有成果复核：不适用（<理由>）`；普通续批次写 `沿用批准（<证据>）`，正式修订后的恢复批次写 `重新批准（<证据>）`，所有后续批次的既有成果复核都必须写 `通过（<证据>）`。`未重新批准`、`待批准`、`未通过` 或空证据均不放行。

## 执行模式与生命周期状态机

- **提交名词边界：** “worktree 候选提交”是隔离 worktree 分支上形成的不可变证据提交；“当前分支本地提交”是候选差异应用到当前工作区、经人工批准后在当前开发分支创建的提交。两者通常使用不同的 commit SHA，不能把前者当作后者的提交授权。
- 默认使用 `单集成单元审批`：一次只实施一个单元，形成候选提交并通过 Review 后，将候选差异应用到当前工作区，等待当前分支提交批准；批准并提交后才开始下一单元。
- 只有人类明确选择时使用 `一次性执行`：各单元仍保持独立候选提交和质量证据，全部完成后统一 Review，将组合差异一次性应用到当前工作区，申请一次当前分支组合提交批准。
- 只在单元尚未开始或已经完成当前分支集成提交的安全检查点切换模式；追加模式变更和批准事件，不覆盖历史。
- 允许状态为 `未开始`、`执行中`、`等待 Review`、`等待当前分支提交批准`、`最终验证中`、`安全暂停`、`立即中断`、`已取消`、`阻塞`、`已完成`。状态事件必须连续，当前状态等于最后一个事件的后状态。
- `安全暂停` 在当前原子步骤结束后停止；`立即中断` 最迟在当前工具调用边界停止；`已取消` 不自动恢复。三者都保留 worktree、文件、测试、候选提交和报告。
- 等待、暂停、中断、取消、阻塞和完成状态必须记录自动编排已停止。暂停期间只有人类明确要求的查看、诊断、测试、代码修改和正式文档修订可执行；禁止自动提交、合并、切换模式、清理或推进下一单元。
- 恢复前复验 Plan、批准批次、主分支/HEAD、洁净状态、worktree、候选提交和五项指纹，从第一个未闭环步骤继续。暂停期间的代码修改使旧候选和相关证据失效；Plan 修改触发重新批准。
- 结构校验允许尚无任务证据的早暂停报告；不得为了通过校验伪造 RED、Review 或覆盖率。`--require-complete` 只接受 `当前状态：已完成` 与 `最终结论：完成`。

## 集成单元、Review 与 Git 门禁

每个已完成单元使用 `### 集成单元 U<n>：<名称>`，并记录以下字段：

- `风险等级`：低或高；`审查策略`：对应单 Reviewer 或双 Reviewer。
- `单元基线提交`、`任务候选提交`、`集成映射提交`、`任务候选树`。
- `报告提交隔离`：证明 Execution Report 未进入任务候选提交；`统一 Review 证据指纹`：一次性模式记录统一审查内容的 Git 对象哈希，默认模式写带理由的不适用。
- `Plan/代码/命令/依赖/环境证据指纹` 和 `验证证据处置`。
- `Reviewer 1 结论`、`Reviewer 2 结论`、`Review 驳回历史`。
- `候选差异应用命令`、`候选差异应用退出码`、`候选差异应用前 HEAD`、`候选差异应用后 HEAD`、`候选差异应用结论`。
- `批准内容指纹`、`当前分支提交信息`、`当前分支提交批准`、`当前分支提交命令`、`当前分支提交退出码`、`当前分支提交前 HEAD`、`当前分支提交后 HEAD`、`当前分支提交结论`。
- `阶段耗时`：至少区分实现、验证、Review、差异应用、提交；`单元结论`。

应用以下语义门禁：

- worktree 候选提交必须是可读取的本地 commit，记录树必须等于 commit 实际树；报告文件不得出现在候选提交中。
- 默认模式的集成映射等于候选提交；候选差异应用前后 HEAD 必须相同且应用前 HEAD 等于单元基线；当前分支提交前 HEAD 等于单元基线，提交后 HEAD 是新的当前分支提交，且其树必须等于候选树，相邻单元的当前分支 HEAD 链连续。
- 一次性并行实现可以产生不同的集成映射提交，但候选与映射必须一一对应、按声明顺序进入同一个最终集成树，且补丁内容等价；组合差异应用前后 HEAD 必须相同，所有单元记录同一统一 Review、批准内容指纹和当前分支组合提交证据。
- 低风险单元由一个独立 Reviewer 顺序完成 Plan 符合性和代码质量审查；高风险单元必须有两个独立 Reviewer。实现者自审不计入。
- Review 驳回时保留旧候选哈希和原因，在未发布 worktree 中追加修正提交，重新验证并 Review；不得覆盖旧证据。
- Review 通过不等于当前分支提交授权。默认模式逐单元批准，一次性模式最终统一批准；没有带证据的人类批准不得应用或提交当前分支。
- 应用候选差异前重新读取主分支、HEAD 和 `git status --porcelain`。主工作区必须洁净；唯一例外是 Harness 自动产生且未暂存的 `.gitignore` 单行 `/.worktrees/` 新增，状态必须只有 ` M .gitignore`，相对 HEAD 只能新增这一行且无删除。其他脏状态、分支/HEAD 漂移或补丁预检失败都立即停止，不自动 stash、rebase、reset、三方合并或解决冲突。
- 候选差异只允许通过二进制补丁预检后 `git apply` 到当前工作区，应用前后 HEAD 必须相同、实际索引必须保持未修改、工作区树必须等于候选树；人工批准后只暂存批准的候选差异文件再创建当前分支本地提交，禁止用 `git add -A` 夹带 `.gitignore` 或其他无关改动，禁止 `--no-verify` 和 `--amend`。始终禁止自动 push、创建 MR、远端合并和删除 worktree。
- 全部最终门禁通过后，Execution Report 形成独立未暂存差异；人工批准后创建独立当前分支证据提交，不得 amend 或混入任务候选提交。证据提交后重新校验时，只允许主分支代码提交 HEAD 的一个直接后继提交，且该提交只能包含当前 Execution Report。

## 分层门禁、并行与证据复用

- 任务级只运行逐行为 TDD 和聚焦测试；集成单元级统一运行代码质量、Reviewer、独立验证和适用切片门禁；最终级运行新鲜全量门禁。
- 默认实现串行。只读检查和互不共享输出、端口或外部状态的验证可并行。一次性模式的并行实现必须由 Plan 证明独立 worktree、文件不重叠、依赖无先后冲突和确定集成顺序。
- 只有 Plan、代码、命令、依赖、环境五项指纹全部匹配时才复用证据，并记录来源和原始退出码。任一变化都重跑；最终全量测试、覆盖率和完成验证始终新鲜运行。
- 阶段耗时用于定位等待、重复门禁和 Agent 调度开销，不得作为跳过门禁或降低 Reviewer 数量的理由。

## Plan 只读与恢复门禁

- 首次修改前使用 `git hash-object -- <plan-file>` 建立批准批次基线；哈希必须是新鲜命令输出，不得手工推测。
- 每个任务只能归属于一个明确执行批次；任务复验哈希必须等于该批次基线，复验通过前不得开始下一任务。
- 最终哈希必须等于最后一个批准批次的基线以及校验时 Plan 文件的实际哈希。
- Plan 哈希一旦变化，当前批次立即阻塞；不得修改 Plan 恢复表面一致，不得继续后续任务，也不得自动清理或回退已有成果。
- 任务末尾复验失败时，任务只能记为实现、测试和质量审查完成但闭环阻断；最后完全闭环任务是它的前一个任务。
- 失败复验必须是其阻塞批次的最后一个任务；旧批次中出现后续任务即违反“变化即停”。完整交付只能由之后正式重新批准的新批次恢复，且最后一个批次必须通过。
- 恢复原内容时，哈希必须重新等于原批次基线；正式修订时必须有人类重新批准，并在同一报告追加新批次、新哈希和既有成果复核。
- 新批次保留所有旧批次证据。失效成果通过新任务调整，不得改写历史记录。
- 每个批次保留自己的 `批次结论`；报告只保留一个代表当前整体状态的 `最终结论`，不得同时保留冲突的最终结论。

## Worktree 安全门禁

- 使用项目内 `.worktrees/` 前，先在承载该目录的主工作区执行 `git check-ignore -q .worktrees/`，并用 `grep -Fxq '/.worktrees/' <main-workspace>/.gitignore` 检查精确项目规则；前者的校验参数必须保留末尾 `/`。
- 任一检查未通过时，在主工作区根 `.gitignore` 自动添加且只添加一次 `/.worktrees/`，两项复验都通过后才能创建 worktree。
- `validate-execution.sh --require-complete` 必须根据报告中的 `主工作区路径` 定位承载 `.worktrees/` 的真实根，读取该处 `.gitignore` 并重新执行 `git check-ignore`；不得误用报告所在 linked worktree 的 `.gitignore`，报告中的“通过”也不能替代实际状态。等待当前分支提交批准的结构报告还必须验证当前 HEAD 未变、索引未暂存且工作区树等于候选树。
- 自动修复 `.gitignore` 不代表提交授权；没有用户明确授权时保留未提交状态。
- 上述未提交修复是主工作区洁净门禁的唯一例外；校验器必须从真实 Git diff 证明只有 `/.worktrees/` 一行新增，不能仅信任报告文本。
- 使用非项目内 worktree 或获准原地执行时，路径、忽略检查和修复字段必须写明不适用理由，不得省略证据。

## TDD 语义门禁

- 每个行为先有正确失败的测试，再有最小生产实现。
- RED 非零退出码来自缺少目标行为，不是编译错误、环境故障或测试错误。
- 测试初次即通过时不得补写虚假的 RED 记录。
- GREEN 后才允许重构；重构不增加未测试行为。
- 已存在的生产实现不作为重写参考；保护用户代码并在实现前基线隔离执行。
- 纯文档、配置和生成任务的等价验证真实对应其失败风险。

## 覆盖率与测试价值门禁

- 任务、业务切片和最终三级证据完整。
- 实际统计范围、指标、阈值、命令和 Plan 完全一致。
- 变更业务代码至少满足批准阈值，核心业务分支都有行为断言。
- 排除项逐项有理由且仅包含无自定义行为代码。
- converter、assembler、mapper、type handler 和本次行为没有被排除。
- 测试验证真实结果而非主要验证 mock；没有空断言、恒真断言或只为覆盖执行的调用。
- 历史失败有同环境基线和批准处置，不被冒充为本次成功。

## 代码与契约质量门禁

- 实际差异逐项追溯到 Plan，没有无来源扩展或遗漏。
- 适用的 Clean Code、Java、SOLID、领域和跨层审查均有证据。
- 发现已经修复，并重新运行受影响测试、覆盖率与审查。
- 全部功能需求、边界行为和非功能约束均已实现；代码简化没有造成需求遗漏。
- 实现是满足当前需求的最简单方案，每个新增抽象、包装、间接层和扩展点都有现实调用方或必要性证据。
- 命名准确、职责清晰、控制流直接、领域术语一致，代码能够直接表达业务意图；不存在含糊命名、重复业务分支或技巧性写法。
- 简洁性调整没有删减必要校验、错误处理、安全措施、可观测性、用户明确行为、测试用例、行为断言或覆盖率要求。
- 整洁性治理仅覆盖本次新增或修改代码及完成需求必需的直接关联代码；必要旧代码调整具备原因、行为保持边界和回归验证。
- 分层依赖、边界转换、错误语义、数据一致性、幂等和并发符合 Design 与项目规范。
- 工作区原有改动被保护，Git 操作没有越过授权边界。
- Plan 在每个任务和最终阶段都通过对应批准批次的内容哈希复验；历史执行批次未被覆盖。
- 项目内 `.worktrees/` 在创建前已被根 `.gitignore` 忽略，自动修复未越过提交授权。

## 完成判定

只有以下条件全部成立才能写 `最终结论：完成`：

- 全部 Plan 任务和验收标准已实现，非目标未被夹带。
- 代码实现质量门禁五项结论全部通过，具体发现均已修复并复验。
- 所有行为有可信 TDD 证据，非行为任务有等价验证证据。
- 定向、切片和最终测试全部通过。
- 业务代码覆盖率达到阈值且排除项一致。
- 全部质量审查、`verification-before-completion` 和 `finish-work` 已闭环。
- 报告通过 `validate-execution.sh --require-complete`。
- 每个任务的 Plan 只读复验、最终 Plan 哈希校验和 Worktree 忽略证据均通过。
- 当前状态为 `已完成`，状态链连续且自动编排已停止。
- 每个集成单元都有真实候选提交、风险自适应 Reviewer、候选差异应用、当前分支提交批准和当前分支提交证据；主分支与预期代码 HEAD 一致，或只多一个仅含当前 Execution Report 的已批准直接后继证据提交；工作区洁净或仅保留经过真实 diff 校验的 `.gitignore` 单行 Harness 修复。
- Execution Report 未混入任务候选提交；最终证据提交独立处理。
- 所有证据复用均具备五项匹配指纹，最终全量门禁使用新鲜输出。
- 没有未批准偏差、未解决阻塞、占位符或敏感信息。

机械校验通过不代表语义通过。任何证据无法由实际命令输出、差异或批准记录证明时，修订报告或标记未完成，不得降低门禁。
