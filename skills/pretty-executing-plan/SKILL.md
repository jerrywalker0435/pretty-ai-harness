# 高质量执行实施计划

## 概述

将已批准 Plan 作为只读合同，通过现有 Superpowers 执行引擎实施，并为 TDD、测试覆盖率、代码质量和最终验证留下可复核证据。没有新鲜证据就没有完成结论。

**核心实现原则：** 在完整实现全部功能需求、边界行为和非功能约束的前提下，交付满足当前需求的最简单实现。生产代码必须命名准确、意图清晰、结构易读并直接表达业务规则；功能正确、测试通过或已经调用质量 Skill，都不能替代简洁性、可读性和业务表达力审查。简洁不得以删减校验、错误处理、安全措施、可观测性、用户明确行为或必要测试为代价。

**提交名词边界：** `worktree 候选提交` 指隔离 worktree 分支上的不可变证据提交；`当前分支本地提交` 指候选差异应用到当前工作区、经人工批准后在当前开发分支创建的提交。两者通常是不同的 commit SHA，候选提交不等于当前分支提交授权。

## 1. 宣布并校验输入

宣布正在使用 `pretty-executing-plan`。要求用户明确指定或确认待执行 Plan。用户要求执行即表示授权在隔离 worktree 中创建 Harness 所需的 worktree 候选提交、一次性模式的本地集成映射提交和最终报告证据提交；不表示授权把候选差异应用到当前工作区、提交当前分支、push、创建 MR 或远端合并。当前分支的每次提交仍须单独获得人工批准。

仓库包含 `.trellis/` 时，**必需子 Skill：** 使用 `before-dev`。读取 Plan 及其引用的已批准 Design、PRD、ADR 和项目规范，但不得修改原 Plan。

执行：

```bash
bash .agents/skills/pretty-writing-plan/scripts/validate-plan.sh <plan-file>
git hash-object -- <plan-file>
```

再按 `pretty-writing-plan/references/quality-gates.md` 语义审查当前 Plan 与代码状态。Plan 必须给出真实的 TDD 步骤、测试与覆盖率范围、行/分支阈值、命令、报告位置、排除项、失败判定和最终回归门禁。

将 `git hash-object` 输出记录为当前 `Plan 批次基线哈希`。Plan 是只读合同，禁止修改正文、任务状态、复选框、完成标记、备注、日期或任何元数据；执行进度、偏差、失败和恢复只写入 Execution Report。每个批次按质量门禁区分首次批准、沿用批准和重新批准，追加基线、批准、既有成果复核与批次结论，不覆盖历史或使用待确认占位。

Plan 必须包含新版 `执行编排合同`，每个任务恰好归属一个集成单元。缺少该合同的旧 Plan 必须停止并路由回 `pretty-writing-plan` 显式迁移、重新校验和重新批准；不得自动把每个任务或整份 Plan 当成集成单元。架构或契约本身有误时先回 `pretty-writing-design`。禁止在执行阶段起草临时附录、猜测命令或静默改变验收口径。Plan 来源不重要，通过相同门禁才可执行。

默认采用“单集成单元审批”：一次只实施当前单元，形成隔离 worktree 上的不可变候选提交后停在 Review。只有用户明确表达“全部做完再统一看”“一次性执行”等意图时才采用“一次性执行”。向用户展示简短自然语言选项，不要求记忆固定命令。模式只能在单元尚未开始或已经完成当前分支集成提交的安全检查点切换，并在报告追加人工批准。

## 2. 保护工作区并建立基线

**必需子 Skill：** 使用 `superpowers:using-git-worktrees` 检测现有隔离。默认模式复用一个长期任务 worktree；一次性模式只有 Plan 已证明并行隔离时才为并行单元创建独立 worktree。用户不授权创建 worktree 时，只有确认现有改动归属且与 Plan 不重叠才可原地继续。不得覆盖、回退或提交无关改动。

使用项目内 `.worktrees/` 前，必须在创建 worktree 之前执行：

```bash
git check-ignore -q .worktrees/
grep -Fxq '/.worktrees/' "$(git rev-parse --show-toplevel)/.gitignore"
```

若任一检查失败，在承载 `.worktrees/` 的主工作区根 `.gitignore` 追加且只追加一次 `/.worktrees/`，复验两项均通过后才能创建 worktree。该准备性修复保留为未提交差异并写入报告，除非用户明确授权；完成校验必须读取报告中的真实主工作区复验，不能只信报告文本。完整例外条件按质量门禁执行。

记录主工作区路径、当前分支和 HEAD，并要求主工作区洁净；唯一例外是经真实 diff 证明只新增一行 `/.worktrees/` 的上述未提交修复。每次应用候选差异和提交当前分支前都复验，发生漂移即停止，不得自动 stash、rebase、reset、创建 merge commit 或夹带用户改动。

完整读取 [references/quality-gates.md](references/quality-gates.md)。修改前按其结构记录工作区、输入、Plan 批次和基线证据，并运行 Plan 指定的测试、编译与覆盖率命令。创建或恢复唯一报告 `docs/pretty/<topic>/YYYY-MM-DD-<topic>-execution.md`，沿用 Plan 主题并只追加批次；不创建旁路状态文件。妨碍独立验证的基线失败必须阻断，且不得新增失败或降低指标。报告只保留必要摘要，禁止秘密、个人信息和大段日志。

## 3. 选择底层执行引擎

只选择一个底层引擎：

- 环境允许子 Agent 且 Plan 任务可安全拆分：**必需子 Skill：** `superpowers:subagent-driven-development`。
- 环境不允许、任务强耦合或用户明确要求单 Agent：**必需子 Skill：** `superpowers:executing-plans`。

两条路径执行同一质量合同。不得直接手工执行以绕开底层引擎。Pretty 状态机是上层权威：默认只把“当前集成单元”交给底层引擎，单元完成后收回控制并停止；明确覆盖底层引擎“连续执行整份 Plan”或“自动进入下一任务批次”的习惯。

默认模式串行实施，只并行执行只读检查和不会共享构建输出、端口、数据库或外部状态的验证。一次性模式只有 Plan 明确文件所有权、独立 worktree、无冲突依赖、集成顺序和跨任务契约时才可并行实现；将并行候选提交按批准顺序映射到本地集成树，并在把组合差异应用到当前工作区后重新运行受影响切片和最终门禁。

覆盖底层引擎的提交习惯：只允许在当前集成单元的候选前门禁通过后创建隔离 worktree 候选提交，提交范围不得包含 Execution Report、无关改动或其他单元文件。该授权不扩展为应用候选差异、提交当前分支、push、建 MR 或远端操作。Agent 报告成功不是证据，主执行者必须检查差异、候选树和新鲜验证输出。

向底层执行引擎和所有子 Agent 明确传递 Plan 只读合同及当前批次基线哈希。任何 Agent 都不得通过勾选 Plan、改任务文本或补充 Plan 来记录进度；主执行者不得接受修改 Plan 后继续执行的结果。

## 4. 逐行为严格执行 TDD

每个功能、缺陷、重构或行为变化，**必需子 Skill：** 使用 `superpowers:test-driven-development`，逐个行为执行：

1. 开始任务前重新计算 Plan 哈希；与当前批次基线不一致时不得开始任务。
2. 编写一个聚焦于可观察行为的失败测试。
3. 运行定向命令，确认因缺少目标行为而正确失败；记录 RED 命令、非零退出码、预期原因和实际摘要。
4. 编写使当前测试通过的最小生产代码。
5. 运行定向测试并记录 GREEN 命令、退出码 `0` 和结果。
6. 仅在 GREEN 后重构，再运行相关测试并记录复验。
7. 重复下一行为，不得先完成生产代码再集中补测试。

生产代码已经存在时，不得把事后测试冒充 TDD，也不得因期限、沉没成本或用户口头放宽而在本工作流中标记通过。保护用户代码，在实施前基线的隔离工作区重新执行；若用户坚持豁免，终止本质量工作流并明确标记为降级实施，不能声称 `pretty-executing-plan` 完成。

纯文档、纯配置或生成文件不制造虚假 RED：记录任务类型、不适用理由、等价校验命令和退出码。同一任务包含业务行为时仍必须 TDD。

## 5. 每个集成单元闭环实现质量并形成候选

完成当前集成单元内全部任务的 GREEN 和重构复验后，**必需子 Skill：** 使用一次覆盖该单元全部差异的 `clean-code-guard`。按 Plan 和证据执行适用的 Java 对象/类型设计、SOLID、领域模型、系统化调试或其他专项检查。不要为同一单元的每个简单任务重复启动完整质量 Agent；任务级 TDD 证据仍逐项保留。

每个集成单元按质量门禁记录 `功能完整性核对`、`简洁性与必要性审查`、`可读性与业务表达审查`、`测试完整性保护` 和 `变更范围控制`。任一项未通过都修复并复验；不夹带与本次交付无关的旧代码重构。

跨层或跨模块业务切片，**必需子 Skill：** 使用 `check-cross-layer`，验证完整数据流、依赖方向、边界转换、调用方和契约一致性。发现不是闭环：修复后重新运行受影响的测试、覆盖率和审查，全部通过才能形成单元候选提交。

每个任务的实现和定向测试结束后，必须再次执行 `git hash-object -- <plan-file>`，在该任务下记录 `Plan 只读复验哈希` 和 `Plan 只读复验结论`。哈希必须等于当时的 `Plan 批次基线哈希`；完成复验前不得开始下一任务。不得只在最终阶段统一复验，也不得手工抄写历史哈希代替新鲜命令输出。单元级质量审查在全部所属任务完成后统一执行。

测试还必须接受语义审查：核心行为有真实断言，错误行为会使测试失败，mock 只用于不可避免边界，不得用无业务断言的测试刷覆盖率。仓库或 Plan 要求变异测试时执行；否则不擅自引入基础设施。

上述候选前门禁全部通过后，重新确认 Plan 哈希，创建隔离 worktree 上的不可变候选提交，并记录单元基线、候选提交、候选树及 Execution Report 未进入候选的证据。报告在长期 worktree 保持未提交，不得混入任务代码提交；候选差异应用和当前分支提交在实际集成时记录。

默认模式在每个候选形成后执行独立 Review：低风险单元由一个 Reviewer 先审查 Plan 符合性、再审查代码质量，高风险单元使用两个 Reviewer。一次性模式按下一节在映射完成后执行统一 Review，并让各单元记录同一个 `统一 Review 证据指纹`；存在高风险单元时统一 Review 使用两个 Reviewer。Reviewer 必须基于不可变候选或集成提交，记录范围、发现、修复和复查，禁止用实现者自审代替。驳回时保留旧候选证据，追加修正提交并生成新候选，不得改写历史。

## 6. 执行人工检查点与当前分支集成

默认模式按以下顺序执行：

1. 形成当前单元候选提交后，将状态切换为 `等待 Review` 并停止自动编排。
2. 独立 Reviewer 通过后，重新验证主分支、HEAD 和洁净状态；使用候选提交相对单元基线的二进制补丁执行 `git apply` 预检和应用。应用必须保持当前分支 HEAD 不变、实际索引不变、候选树与当前工作区树一致，且工作区只包含候选差异。
3. 候选差异成功应用后切换为 `等待当前分支提交批准` 并停止自动编排。记录候选差异指纹、拟用提交信息、应用命令和退出码，向用户展示差异与验证摘要；不要把应用动作称为 Git merge。
4. Review 通过不等于当前分支提交授权。只有用户明确批准当前分支提交，才按批准内容只暂存候选差异文件、正常执行项目 Git Hook，并在当前分支创建一个本地提交；禁止使用会夹带 `.gitignore` 等无关改动的 `git add -A`，也禁止 `--no-verify`、`--amend`、push、创建 MR 或远端操作。提交树必须与已批准候选树一致，失败或内容被 Hook 改写时立即阻塞。
5. 用户要求修改时保留旧候选和证据，回到隔离 worktree 追加修正提交并重新 Review；用户仅拒绝或暂停时保留当前未暂存差异。只有用户明确要求撤回且差异指纹未变化时才允许撤回。当前分支提交完成后才把下一个单元交给底层执行引擎。

一次性模式仍为每个单元保留独立候选提交和单元门禁，但不中途应用到当前工作区。全部单元完成后，在本地集成分支按 Plan 顺序映射候选提交，记录候选提交到集成映射提交的关系；映射冲突、内容漂移或顺序变化都必须停止，不得自动解决。随后运行最终全量门禁和统一 Review，把组合差异一次性应用到当前工作区，切换为 `等待当前分支提交批准`，只申请一次当前分支组合提交批准；批准后创建一个组合本地提交。

始终禁止自动 push、创建 MR、远端合并或删除 worktree。Review 驳回、暂停、取消和 Plan 变化都不得删除已有代码、测试、候选提交或历史报告。

应用候选差异时必须记录 `候选差异应用命令`、`候选差异应用退出码`、`候选差异应用前 HEAD`、`候选差异应用后 HEAD`、`候选差异应用结论` 和 `批准内容指纹`；应用前后 HEAD 必须相同。人工批准后必须记录 `当前分支提交信息`、`当前分支提交命令`、`当前分支提交退出码`、`当前分支提交前 HEAD`、`当前分支提交后 HEAD` 和 `当前分支提交结论`。默认模式每个单元形成一个当前分支提交；一次性模式全部单元形成一个组合提交。Execution Report 不得混入这些代码提交，最终证据提交仍独立处理。

## 7. 执行分层测试、覆盖率与证据复用门禁

- 任务级：保留每个行为的 RED、GREEN、重构复验证据，只运行聚焦命令。
- 集成单元级：运行独立验证、相关模块测试、编译和适用覆盖率校验。
- 最终级：重新运行 Plan 指定的全量回归、报告生成和阈值检查。

按质量门禁记录 Plan、代码、命令、依赖和环境五项指纹；只有全部匹配时才复用，最终全量门禁始终新鲜运行。严格执行 Plan 的覆盖率范围、阈值和排除清单；任何口径变更返回 `pretty-writing-plan`，覆盖不足只能补充有效业务测试。记录各阶段耗时，但不得以耗时为由降低门禁。

## 8. 处理暂停、中断、取消与恢复

把唯一 Execution Report 作为恢复检查点。报告顶部只保留一个当前状态，同时按时间追加 `状态转换`、触发来源、当前单元、未完成操作和恢复入口。不要创建仓库控制脚本，也不要要求用户记忆固定 CLI 命令；识别“先停一下”“马上停”“取消”“继续”“恢复”“都做完再看”等自然语言及同义表达。

使用以下语义：

- **安全暂停：** 完成当前不可再拆的命令或 Git 原子操作，不开始下一步；保存报告后停止自动编排。
- **立即中断：** 尽快中止当前可中断命令，最迟在当前工具调用边界停止；允许任务、验证或报告处于未闭环状态，但必须如实记录。
- **取消执行：** 进入终态，不再自动恢复；保留 worktree、代码、测试、提交和报告，除非用户另行明确授权清理。

暂停期间自动编排和 Git 集成保持停止。只有用户明确要求时才允许查看、诊断、运行测试、修改代码或正式修订文档；这些动作必须追加到控制事件。暂停期间修改代码会使对应候选与验证证据失效，恢复后创建新的修正提交并重新 Review；修改 Plan 会触发 Plan 哈希阻塞和重新批准流程。不得在暂停期间自动应用、提交、合并、切换模式、清理 worktree 或推进下一单元。已应用到当前工作区的未暂存差异必须原样保留。

恢复前重新检查 Plan 哈希与批准批次、主分支和预期 HEAD、工作区状态、已应用差异指纹、worktree/候选提交存在性、依赖与环境指纹、最后一个完整门禁和未闭环操作。只复用五项指纹仍匹配的证据，从第一个未闭环步骤继续，不重做仍有效成果。任何检查不通过都保持暂停或转为阻塞，不得自动 stash、rebase、reset 或修补 Plan。

只使用质量门禁定义的生命周期状态；`--require-complete` 只接受 `已完成`，其他状态如实记录为未完成或阻塞。

## 9. 管理偏差与失败

行号、等价命令参数或文件移动等不改变设计与验收的机械差异，可以修正并记录。架构、职责、API/事件契约、数据、事务、幂等、测试范围、阈值或排除项变化必须停止并返回 Design/Plan 阶段；禁止先偏离、后改文档。

计划范围内且不改变设计的测试失败、覆盖缺口和整洁问题应自动修复并复验。只有需要新决策、新授权、重大扩围或无法继续的真实阻塞才询问用户。任何命令失败、门禁未运行或审查未闭环时，只能报告实际未完成状态。

### Plan 变化时立即停止

任何一次哈希复验与当前批次基线不一致时立即停止，不执行后续任务、不修改 Plan 消除差异，也不回退或清理成果。按质量门禁记录哈希、检测点、最后闭环任务、未闭环项和阻塞结论。只有两种恢复路径：

1. **恢复原基线后继续：** 人类将 Plan 恢复到原批准内容；重新计算哈希并确认等于当前批次基线，复核已有差异和证据后，从第一个未完成任务继续。
2. **正式修订并重新批准后继续：** 返回适用的 PRD、Design 或 Plan 阶段完成修订和人类批准；在同一 Execution Report 追加新执行批次，记录新基线哈希、重新批准和既有成果复核，再从第一个不符合新 Plan 的任务继续。

恢复只追加新批次，不覆盖旧证据。失效成果在新批次通过 TDD 调整；完整交付必须由后续批准批次闭环且最终哈希匹配，报告始终只保留一个当前 `最终结论`。

## 10. 完成前执行最终门禁

全部任务结束后：

1. 重读 Plan，逐项核对需求、任务、验收和非目标。
2. 重新计算 Plan 哈希，记录 `Plan 最终哈希`；它必须同时等于最后一个批准批次的基线哈希和当前 Plan 文件哈希，并记录 `Plan 只读校验：通过`。
3. 重新核对代码实现质量门禁的五项证据，确认全部通过且发现均已修复复验。
4. 运行最终全量测试、编译、覆盖率和仓库专项命令。
5. **必需子 Skill：** 使用 `superpowers:verification-before-completion`，亲自读取新鲜输出和退出码。
6. **必需子 Skill：** 使用 `finish-work`；任何发现都必须修复并复验。
7. 运行：

```bash
bash .agents/skills/pretty-executing-plan/scripts/validate-execution.sh \
  <execution-report> --require-complete
```

8. 按 [references/quality-gates.md](references/quality-gates.md) 执行最终语义审查。
9. 将只包含 Execution Report 的证据差异应用到当前工作区，保持未暂存并请求人工批准；批准后创建独立的当前分支证据提交，不得把报告补入或 amend 到任一任务候选提交。证据提交后允许再次运行完整校验；此时主分支只能比报告记录的代码提交 HEAD 多一个直接后继提交，且该提交只能包含当前 Execution Report，其他 HEAD 漂移仍须拒绝。

机械校验不能证明代码正确。全部门禁通过后，请求用户复审代码和执行报告并停止。只有用户随后要求分支收尾时才使用 `superpowers:finishing-a-development-branch`；它不得自动 push、建 MR、远端合并或删除工作。任何当前分支提交仍遵循本 Skill 的人工批准合同。

## 常见借口与处理

| 借口 | 处理 |
|---|---|
| Plan 已经有测试代码 | 测试文本不是 RED 证据，仍须先运行并观察正确失败。 |
| 先保留现成实现，补测试即可 | 这是事后测试；隔离到实现前基线重新执行。 |
| 时间紧，现场补覆盖率口径 | 口径属于 Plan，返回 `pretty-writing-plan`。 |
| 历史测试本来就失败 | 建立同环境基线并按批准口径比较，不能静默放行。 |
| DTO、converter、mapper 都没价值 | 只允许 Plan 明列的无行为对象；含转换或映射即有行为。 |
| 覆盖率达标说明测试有效 | 覆盖率只证明执行，仍须审查断言和业务行为矩阵。 |
| Agent 说已经完成 | 检查差异、候选提交与新鲜验证，不能信任口头结论。 |
| 改一下 Plan 勾选进度再继续 | Plan 是批准合同；进度只写 Execution Report，哈希变化必须停止。 |
| 重新批准会丢掉之前成果 | 代码、测试、报告和 worktree 全部保留；新批次先复核，再继续或调整。 |
| 底层引擎要求连续执行全部任务 | Pretty 状态机只下发当前集成单元，并在 Review 检查点收回控制。 |
| 用户说不要每个任务都问 | 默认按集成单元而非任务停顿；这不等于授权跳过 Review 或当前分支提交批准。 |
| 为了更快跳过重复验证 | 只在五项指纹一致时复用；最终全量门禁始终新鲜运行。 |
| 暂停只是暂时不回复用户 | 暂停必须停止自动编排、写入可恢复控制事件并保留所有成果。 |

## 危险信号

- 未校验 Plan/编排合同就修改代码，或修改 Plan 消除偏差。
- Plan 哈希变化、暂停、中断或取消后仍推进任务、应用或提交。
- 候选前门禁未通过就提交，Reviewer 未基于候选，或 Review 未通过仍应用/提交当前分支。
- RED 不可信、门禁缺失、指纹失配或覆盖不足时仍继续。
- 未获人工批准、工作区差异指纹漂移或 HEAD 漂移时应用/提交当前分支，或使用自动冲突解决。
- 报告混入候选、历史证据被覆盖、敏感信息或占位符进入报告。
- 为精简而删减必要行为/测试，或借整洁之名夹带无关重构。
- 任一门禁未闭环仍宣称完成。

出现危险信号时立即停止、修正并重新执行受影响门禁。
