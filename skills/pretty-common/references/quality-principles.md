# Java 代码与设计质量基线

本文件只定义 Plan 代码提案与 Execution 真实增量共同遵守的质量原则。阶段流程见各 Skill，风险路由见 [quality-routing.md](quality-routing.md)，审查证据见 [quality-review-protocol.md](quality-review-protocol.md)，机械规则及阈值以 `../scripts/quality_contract_gate.py` 的规则注册表为准。

## QP-01 完整链路与规则归属

先确认受影响链路，再决定局部修改：

```text
入口 → caller → callee → Adapter → 持久化或外部系统
```

范围止于真实受影响链路。识别规则唯一归属、数据所有权、状态迁移、消费者、注册点及事务、并发、幂等、安全和兼容边界。相同校验、规范化、默认值、映射或生命周期判断只保留一个知识源。需要改变外部结果、Interface、所有权或依赖方向时返回上游设计。

## QP-02 契约先行与边界信任

- 在值首次进入信任域时建立不变量，内部代码信任已经成立的合同。
- `trim`、大小写折叠和默认值等规范化只能放在首个信任边界，并由协议、Schema 或既有公共合同证明；内部方法不得为假想脏数据重复规范化，也不得悄悄改变标识符和值对象语义。
- 区分必填、可选、可默认、外部不可信、持久化记录和内部值。
- 查询缺失、数据损坏与外部故障使用不同语义；业务方法默认不返回 `null`。
- 只有明确的框架、遗留或外部可空合同允许 `null`，并由注解、文档和测试共同证明。
- 配置缺失、依赖缺失和非法外部输入在对应边界快速失败，不用空值或默认成功掩盖。

## QP-03 约定优先

优先级为：已批准合同、Java/Spring 标准约定、仓库稳定约定、真实运行差异所需配置。稳定业务规则不做成模式码、SpEL 或配置开关；可部署配置集中到有领域含义并可校验的配置类型。Java 版本与依赖 API 必须以真实构建配置和已安装版本为准。

## QP-04 正常流与失败流

- 成功返回领域结果，失败使用能表达恢复责任的异常合同。
- 只捕获能够恢复或映射的具体异常，保留 cause；不解析异常消息控制流程。
- 不把异常、数据损坏或外部故障转换为 `null`、空集合、状态码或成功。
- 外部状态码在 Adapter 一次映射，不能以裸 `int`、`String` 或 `boolean` 跨层分派业务行为。
- 控制流首先追求清楚；复杂跳转、嵌套和三元表达式必须接受结构审查。

## QP-05 查询与命令

查询返回信息且没有可观察副作用；命令改变状态或执行副作用。名称、返回值和行为必须一致。用例同时读取和修改时，由调用方显式编排两个有清晰语义的动作。合法的“命令返回创建结果”等外部合同必须由具体证据说明。

## QP-06 命名、注释与实现事实

类、方法、参数和变量使用领域词汇并表达意图。避免无领域限定的 `execute`、`resolve`、`handle`、`process`、`data`、`result`、`helper`、`manager` 等弱名称；`normal`、`special` 等相对分类词必须能指出互斥分类、划分规则和业务含义，否则改用具体领域状态。注释只解释代码无法表达的原因、外部限制或算法依据，不复述实现，也不掩盖长方法和复杂职责。仓库若要求某类声明存在注释，只豁免“是否存在”，不豁免注释内容的必要性和准确性。

事实证据顺序为：

```text
批准合同 → 真实实现和调用链 → 类型、注解、Schema、配置与有效测试 → 普通注释
```

## QP-07 日志所有权

日志服务于故障定位、运营或审计。一次失败只由真正消费异常并终止传播的边界记录一次；映射后继续抛出的层不记录同一失败。记录完整异常及必要结构化字段，禁止凭证、完整载荷和敏感数据。日志数量、分支日志和所有权由审查共同判断，不能只凭层名决定。

## QP-08 类型、参数与返回值

- 参数只作为输入，不把可变参数改写成输出容器。
- 值对象只用于稳定领域概念、共同不变量、类型混淆、重复校验或高后果错误。
- 不为降低参数数量机械创建 `Param`、`Context`、`Command` 或 `Result`。
- 禁止通用 `success/code/message/data` 结果形状进入业务 Module；协议响应壳只留在 Adapter。
- 精度、长度、格式、可空性和集合语义与 Schema 或外部协议一致。

## QP-09 深 Module 与克制抽象

稳定规则放入有深度的 Module，让调用方学习更少的状态、参数和错误。依赖通过构造器或明确创建边界传入。只有真实变化轴、第二个实现或批准的扩展合同才引入 Interface、Factory、Strategy 或注册表。优先组合、不可变状态、最小可见性和局部性，不为假想需求增加开关、依赖或死代码。

## QP-10 行为测试

测试通过已批准的公共 Seam 观察业务结果、状态、异常或完整边界请求。只替换数据库、网络、时间和随机等系统边界，不 mock 自有内部协作者，不测试 private 方法，不复制实现算法生成期望值，不以调用次数代替主要行为证据。不得禁用、跳过或弱化测试换取通过。SQL、DDL、索引和迁移脚本用目标数据库引擎的解析、迁移、查询计划或后置条件验证，不把 SQL 文本断言包装成 Java 单元测试；只有调用 SQL 的 Java 行为本身需要 Java 测试。

## QP-11 AI 生成完整性

生成代码前读取目标文件、相邻实现、仓库规则和真实依赖版本。禁止臆造 API、硬编码成功、生产 fixture、半实现、无调用者的抽象、无价值新依赖以及从相似代码复制后猜测语义。边界、空值、范围和顺序问题必须从合同重新推导并由测试固定。
