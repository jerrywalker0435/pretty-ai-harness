# Java 代码与设计质量基线

本文件是 `pretty-writing-plan` 与 `pretty-executing-plan` 共用的代码和设计质量基线。前者将它应用于完整代码提案的生成、扫描和语义复核，后者将它应用于真实增量代码；各阶段的质量路由、验证、证据和交付规则由各自 Skill 定义。本文件不定义阶段流程、质量评分或执行状态。

## 1. 全局设计优先

先分析受影响的完整链路，再决定局部修改范围：

```text
入口 → caller → callee → Adapter → 持久化/外部系统
```

范围止于受影响链路，不扩张为全仓翻新。必须识别：

- 已批准的业务结果、外部合同和兼容边界；
- 规则的唯一归属、数据所有权、不变量和状态迁移；
- 重复的校验、规范化、默认值、映射、异常转换、防重和生命周期判断；
- 事务、并发、幂等、重试、性能和安全边界；
- 哪些 symbol 需要一起变更，哪些可以独立交付。

若收敛规则会改变已批准 Interface、所有权、依赖方向、业务结果或长期扩展点，返回上游设计，不在局部实现中静默取舍。

## 2. 契约先行、边界校验、内部信任

每个值先分类：必填、可选、可默认、外部不可信、持久化记录或已建立不变量的内部值。分类决定其类型、校验位置和失败语义。

- 在值第一次进入信任域的边界建立不变量；同一规则只校验/规范化一次。
- 进入信任域后，内部 Module 依赖已建立的契约，不重复添加不可能触发的 null、类型或 truthiness 防御。
- 必填依赖由构造器或创建边界立即拒绝；配置缺失在启动/装配边界失败。
- 查询无结果必须有明确的缺失语义；按合同使用 `Optional`、空集合或明确缺失类型，不能把“未找到”“数据损坏”“外部故障”统一变成 `null`。命令无结果使用 `void`。
- 新增或修改的业务方法默认不得返回 `null`；异常、数据损坏和外部故障不得统一返回 `null`。
- 只有框架、遗留接口或明确的可空外部契约允许返回 `null`，且必须以 `@Nullable`、文档和测试明确缺失语义。
- 规范化、默认值、容错恢复和校验是四种不同动作，不能塞进一个通用 helper。
- 机器标识符、状态码、数据库键和幂等键默认拒绝 `null`、空白和首尾空格。只有批准的人工输入合同才可在外部边界规范化一次。

不要用以下形式隐藏不同的失败语义：

```java
normalizeText(record == null ? null : record.getTaskPublishId());
```

禁止通过 catch 后返回 `null`、`orElse(null)` 或链式判空掩盖契约问题。

记录不存在、字段缺失和空白输入应在正确边界分别表达。历史脏数据不能由通用 `normalizeText` 永久掩盖；应通过迁移、专用兼容 Adapter 或上游修复治理。

## 3. 约定大于配置

优先级为：

```text
已批准合同 → Java/Spring 标准约定 → 仓库稳定约定 → 真实运行时差异所需的显式配置
```

- 包结构、组件发现、构造器注入、资源命名、配置绑定和 Adapter 位置优先遵循稳定约定；不为单一用例新建注册表、动态映射或自定义装配层。
- 所有环境中不变的业务规则、不变量、失败语义和数据所有权属于代码与领域契约，不做成开关、字符串模式码、SpEL 或数据库参数。
- 只有部署者确实需要在不重新构建的情况下改变的值才进入配置，例如外部端点、凭证引用、超时、配额或已批准的发布开关。
- 相关配置用有领域语义的 `@ConfigurationProperties` 集中绑定，使用类型和 Bean Validation 建立不变量；避免散落的 `@Value` 字符串、`Map<String, Object>` 和调用时解析。
- 必填配置缺失或非法时在启动/装配边界快速失败，不用空字符串、零或默认端点静默恢复。可选默认值必须安全、语义明确且只定义一次。
- 配置分支若实际上代表多个业务算法或责任所有者，确认变化轴和 Interface，不用 `mode=1` 之类类型码隐藏设计决策。
- Java 8 兼容性由项目编译 Gate 负责确认：Maven 使用项目实际的 `source`、`target` 或 `release` 配置，Gradle 使用对应的 Java toolchain/compatibility 配置；不通过正则扫描源码猜测编译兼容性。

## 4. 正常业务流与异常流分离

避免使用裸 `int`、`String`、`boolean` 作为跨层行为分派、成功失败或错误原因的类型码。外部状态码在 Adapter 处一次映射成领域结果或明确异常。

- 成功返回真正的领域结果；任务不存在、状态冲突、非法输入、数据损坏和外部故障使用能表达恢复责任的异常合同。
- 不用异常控制高频正常分支、循环或普通搜索未命中。
- 新增或修改的 Java 代码（生产、测试及 Plan 中的代码提案）禁止使用 `continue`；通过正向条件分支、提取方法或拆分循环表达流程，避免跳过逻辑隐藏控制流。
- 不解析异常消息或数字错误码决定控制流。
- 只捕获能够恢复或映射的具体异常类型；不 catch `Exception`/`RuntimeException` 只为换名、打日志或返回空集合、默认值、“成功”。映射边界异常时保留原始 cause 和必要上下文，编程缺陷继续传播。
- 简单三元表达式可以表达清晰的二选一；禁止用三元表达式传播 `null`，避免 `Optional.isPresent()`/`get()` 与 `null` 组合，也将嵌套或同一语句中的多个三元视为可读性风险。共享机械 Gate 只阻断空值传播，后两类输出 warning。

有限且本身是业务事实的状态可以使用 `enum` 或值对象；避免类型码不等于消灭所有状态模型。

## 5. 查询与命令分离

查询方法只读取并返回信息，不产生业务、持久化、缓存、日志、消息、调度或其他外部可观察副作用；命令方法负责改变状态或执行副作用，不同时伪装成查询。方法名称、返回值和实际行为必须一致。若一个用例既需要读取又需要改变状态，拆成语义明确的查询和命令，并在调用方显式编排顺序。

## 6. 领域命名、自释义代码与实现事实

新增或修改的类、方法、参数和变量必须优先使用领域词汇，表达动作、结果或规则。`execute`、`resolve`、`handle`、`do`、`action`、`deal` 等弱语义名称默认禁止；框架/第三方 Interface 合同或真实领域词汇才可例外。

代码应通过命名、类型和结构表达意图。注释只解释不能从代码推导出的原因、外部约束、兼容性或算法依据；禁止逐行叙述代码、解释显而易见的逻辑，或用注释掩盖长方法、弱命名和复杂职责。代码与注释冲突时，以实现事实为准并修正过时注释。

共享机械 Gate 对新增或修改的方法阻断超过一个连续的行内/块注释；方法外的许可证和公共 API Javadoc 不计入该规则。注释数量是确定性门禁，注释是否真正解释“为什么”仍由语义审查判断。

调查事实时的证据顺序是：

```text
批准的合同 → 具体实现和真实调用链 → 类型/注解/SQL/Schema/配置/有效测试 → 普通注释
```

公共 Javadoc、外部协议或批准设计与实现冲突时，视为合同偏差，不能静默选择一方。

## 7. 日志是独立的可观测性设计

日志只记录对定位故障、运营状态或审计有明确价值的信息。日志所有权由“本边界是否真正消费或处置异常并终止其传播”决定，不由 Controller、Service 或 Adapter 的层级名称决定。一次失败只由一个所有者记录一次。

- HTTP 请求由把异常映射成响应的 `@ExceptionHandler`/Advice 消费并记录；只负责调用业务 Module 的 Controller 方法不拥有失败日志。
- 消息消费由最终确认、拒绝、进入死信或耗尽重试的终端边界记录；调度任务由阻止异常继续传播的终端包装记录。
- Adapter 只有在本层完成重试、降级或 fallback 并消费异常时才记录。若只是把协议异常映射为领域异常并继续抛出，只保留 cause 和必要上下文，不记录同一失败。
- catch 后继续抛出原异常或包装异常的层不拥有最终记录责任。禁止 Controller `catch RuntimeException` 后 log-and-rethrow，也禁止 Adapter “映射、记录、再抛出”后由上层重复记录。
- 未被应用代码消费的异常交给框架默认终端处理，不为了“确保有日志”增加宽泛 catch。
- 结构化字段优先：稳定事件名、必要业务标识、外部系统、重试次数和耗时。
- 记录完整异常对象，不只记录 `getMessage()`；禁止凭证、完整载荷和敏感个人数据。
- `traceId` 等关联信息由 tracing/MDC/消息基础设施传播，不作为领域方法的独立日志参数。
- 如果字段影响幂等、审计或业务责任，它是领域数据，不得伪装成日志参数；审计要求应使用明确审计事件/记录。
- 共享机械 Gate 对新增或修改的方法默认最多允许两个常规 logger 调用；显式 `if/else` 或 `switch` 的每个分支都记录日志时阻断。异常终端、审计和边界消费日志仍必须遵守唯一记录所有权，并由语义审查确认必要性。

## 8. 参数、返回值和值对象

新增或修改的方法参数超过 6 个时视为设计风险。优先通过表达共同不变量的领域对象或值对象收敛参数；不得为了降低数量机械创建 `Param`、`Context` 或 `Command`。若外部 Interface 合同固定，应在边界 Adapter 隔离其参数形状，不把膨胀签名扩散到业务 Module。

方法参数只作为输入。禁止在方法内部修改可变参数后再把该参数作为返回结果或输出容器；需要返回新状态时创建具有独立语义的新结果、值对象或副本。输入、状态变化和返回值必须能分别表达其领域含义。

不按参数数量或分层习惯流水线创建 `Command`、`Param`、`Context`、`Request`、`Result`。只有以下情况才建立参数/值对象：

- 多个字段共同维护一个不变量；
- 它代表稳定的领域概念并跨越真实边界；
- 相同 Java 类型容易传反，且类型本身不能表达关系；
- 该合同会作为整体共同演化。

禁止通用返回码对象：

```java
record Result(boolean success, int code, String message, Object data) {}
```

优先使用领域结果、明确异常、`Optional`（仅表达明确的返回缺失语义）或 `void`。HTTP/消息统一响应壳只能留在协议 Adapter，不得渗透到业务 Module。

值对象的触发门槛是跨模块传播、独立不变量、类型混淆、重复校验或错误值会造成一致性/安全/不可逆副作用；不要为了消灭一次判空制造类型泛滥。

## 9. Module、Interface 与模式

- 让稳定业务规则归属于有深度的 Module：调用方知道的参数、状态和错误越少越好。
- 新增或修改的方法体超过 100 行时视为设计风险，必须按业务意图拆分为职责单一的步骤；不得通过注释、空白行或继续堆叠分支规避长方法问题。
- 依赖通过构造器注入；稳定规则不在方法内部 `new` Gateway、Repository、Clock 或随机源。
- 只有真实变化轴或第二个实现存在时才引入 Seam、Factory、Strategy、Adapter 等模式。
- 优先组合、不可变状态和最小可见性；不要为了几行复用建立继承层次。
- 规则只在一个归属点实现；删除一个调用方后不应让复杂度重新散落到其他调用方。
