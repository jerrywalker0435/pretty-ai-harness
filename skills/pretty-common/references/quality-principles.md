# Java 代码质量基线

本文件定义执行阶段生成代码与真实增量共同遵守的质量原则。阶段流程见执行 Skill，风险路由见 [quality-routing.md](quality-routing.md)，审查证据见 [quality-review-protocol.md](quality-review-protocol.md)，运行授权见 [runtime-authorization.md](runtime-authorization.md)，机械规则及阈值以 `../scripts/quality_registry.py` 的注册表为唯一来源。

## QP-01 完整链路与规则归属

先确认受影响链路，再决定局部修改：

```text
入口 → caller → callee → Adapter → 持久化或外部系统
```

范围止于真实受影响链路。识别规则唯一归属、数据所有权、状态迁移、消费者、注册点及事务、并发、幂等、安全和兼容边界。相同校验、规范化、默认值、映射或生命周期判断只保留一个知识源。需要改变外部结果、Interface、所有权或依赖方向时返回上游合同。

## QP-02 契约先行与边界信任

- 在值首次进入信任域时建立不变量，内部代码信任已经成立的合同。
- `trim`、大小写折叠和默认值等规范化只能放在首个信任边界，并由协议、Schema 或既有公共合同证明；内部方法不得为假想脏数据重复规范化，也不得悄悄改变标识符和值对象语义。
- 禁止创建或调用 `normalizeText`、`normalizeString`、`cleanText`、`trimText`、`trimToNull` 及同类无领域归属的通用文本规范化 Helper；规范化、默认值、容错恢复和校验不得合并成模糊操作。确需转换时，由首个信任边界的领域类型、协议类型或兼容 Adapter 以具体合同命名并建立一次不变量。`GENERIC-NORMALIZATION-HELPER` 是不可豁免的机械错误；领域边界内的直接规范化仍由 `NORMALIZATION-OWNERSHIP` 审查合同与值语义。
- 区分必填、可选、可默认、外部不可信、持久化记录和内部值。
- 查询缺失、数据损坏与外部故障使用不同语义；业务方法默认不返回 `null`。
- 只有明确的框架、遗留或外部可空合同允许 `null`，并由注解、文档和测试共同证明。
- 配置缺失、依赖缺失和非法外部输入在对应边界快速失败，不用空值或默认成功掩盖。
- 同一输入的不变量只在首个信任边界建立一次；内部不得对同一必填对象重复 `== null` 防御，也不得用逐字段空值映射伪造查询未命中。

## QP-03 约定优先

在用户已明确当前任务边界后，规范优先级依次为：已批准执行合同、Pretty 共享质量规则、专项 Skill 的非强制建议、真实仓库既有惯例、AGENTS、Trellis。该顺序只解决真实冲突，不决定风险路由、审查强度或适用规则；共享规则始终适用，风险由 Quality Resolver 根据执行合同与仓库事实派生，Writer 不得自报、删除或降级。执行合同中的普通实现偏好不能伪装成业务合同覆盖共享规则，外部或遗留合同确需例外时必须绑定具体 Symbol、不可修改原因和测试、Schema 或签名事实。真实 API、Schema、依赖版本和运行结果是不可伪造的事实约束，不参与普通排序竞争；既有实现方式是低优先级惯例，不能压过 Pretty 规则或适用的专项建议。稳定业务规则不做成模式码、SpEL 或配置开关。Java 版本与依赖 API 必须以真实构建配置和已安装版本为准。

## QP-04 正常流与失败流

- 成功返回领域结果，失败使用能表达恢复责任的异常合同。
- 只捕获能够恢复或映射的具体异常，保留 cause；不解析异常消息控制流程。
- 不把异常、数据损坏或外部故障转换为 `null`、空集合、状态码或成功。
- 外部状态码在 Adapter 一次映射，不能以裸 `int`、`String` 或 `boolean` 跨层分派业务行为。
- 控制流首先追求清楚；交付增量禁止 `continue`，复杂跳转、嵌套和三元表达式必须接受结构审查。

## QP-05 查询与命令

查询返回信息且没有可观察副作用；命令改变状态或执行副作用。名称、返回值和行为必须一致。用例同时读取和修改时，由调用方显式编排两个有清晰语义的动作。合法的“命令返回创建结果”等外部合同必须由具体证据说明。

## QP-06 命名、注释与实现事实

类、方法、参数和变量使用领域词汇并表达意图。禁止无领域限定的 `execute`、`resolve`、`handle`、`process`、`data`、`result`、`helper`、`manager` 等弱名称；`normal`、`special` 等相对分类词必须能指出互斥分类、划分规则和业务含义，否则改用具体领域状态。代码以命名和结构自释义，不生成复述查询、判断、调用或保存步骤的注释，也不强制普通实现或测试声明添加 JavaDoc。只有代码无法表达的外部原因、兼容限制或算法依据才保留简短英文注释；仓库注释惯例和 AGENTS/Trellis 要求不能扩大该范围。

事实证据顺序为：

```text
批准合同 → 真实实现和调用链 → 类型、注解、Schema、配置与有效测试 → 普通注释
```

## QP-07 日志所有权

日志服务于故障定位、运营或审计。一次失败只由真正消费异常并终止传播的边界记录一次；映射后继续抛出的层不记录同一失败。记录完整异常及必要结构化字段，禁止凭证、完整载荷和敏感数据。禁止用 `System.currentTimeMillis()`、`System.nanoTime()`、`durationMs` 或等价局部变量手工生成耗时日志；性能观测复用现有 tracing、metrics、AOP 或统一埋点。业务时间使用注入的 `Clock` 或仓库既有时间抽象。日志数量、分支日志和所有权由审查共同判断，不能只凭层名决定。

## QP-08 类型、参数与返回值

- 参数只作为输入，不把可变参数改写成输出容器。
- 值对象只用于稳定领域概念、共同不变量、类型混淆、重复校验或高后果错误。
- 不为降低参数数量机械创建 `Param`、`Context`、`Command` 或 `Result`。
- 禁止通用 `success/code/message/data` 结果形状进入业务 Module；协议响应壳只留在 Adapter。
- 精度、长度、格式、可空性和集合语义与 Schema 或外部协议一致。

## QP-09 深 Module 与克制抽象

稳定规则放入有深度的 Module，让调用方学习更少的状态、参数和错误。依赖通过构造器或明确创建边界传入。只有真实变化轴、第二个实现或批准的扩展合同才引入 Interface、Factory、Strategy 或注册表。优先组合、不可变状态、最小可见性和局部性，不为假想需求增加开关、依赖或死代码。

## QP-10 行为测试

测试通过执行合同批准的公共验证入口观察业务结果、状态、异常或完整边界请求。只替换数据库、网络、时间和随机等系统边界，不 mock 自有内部协作者，不测试 private 方法，不复制实现算法生成期望值，不以调用次数代替主要行为证据。不得在 `@Disabled`、`@Ignore`、元注解或条件禁用范围新增业务测试，也不得通过构建参数、过滤器或测试发现配置跳过测试；最终报告必须由新鲜测试报告证明新增/修改测试实际执行。表、字段和索引等 DDL 只作为代码库文件交付，不生成测试，不直接执行，也不通过迁移工具、应用启动、构建插件或测试间接执行；Java 与 DDL 混合变更只测试 Java 可观察行为，并在 Execution 报告中明确写明 DDL 已交付、未执行、未进行数据库验证。配置数据 DML 始终由人工运维处理，不属于执行交付物。

## QP-11 AI 生成完整性

生成代码前读取目标文件、相邻实现和真实依赖版本。AGENTS、Trellis、ADR 和项目治理文档只作上下文，不能自行触发同步任务或扩大写集。禁止臆造 API、硬编码成功、生产 fixture、半实现、无调用者的抽象、无价值新依赖以及从相似代码复制后猜测语义。边界、空值、范围和顺序问题必须从合同重新推导并由测试固定。

生成质量与候选证明是两项职责：Writer 在首次落笔和每个行为切片中主动满足本基线，机械扫描用于即时反馈，不得等最终 Gate 才集中清理；冻结后的完整 Git Diff Gate、真实测试和独立 Reviewer 只证明最终候选，不替代生成过程中的质量控制。
