# 高质量 PRD 语义门禁

## 证据与范围

- 从用户视角陈述可见问题和目标结果，不写入未经批准的实现假设。
- 使用仓库领域语言，遵循适用的 ADR、契约、依赖方向和兼容性约束。
- 区分已确认需求与假设；发布前解决所有重大假设。
- 明确包含和排除的行为，防止范围漂移。

## 需求澄清与领域上下文

- 已明确区分仓库事实、已确认需求、假设和阻塞性未决问题。
- `grilling` 一次只解决一个需求决策，已回答问题没有被重复盘问。
- 所有阻塞性未决问题在需求方案综合前清零。
- 已确认的领域术语、稳定关系和定义不可分割的不变量已即时同步到正确的 Context。
- 没有领域变化时未修改 Context，并明确记录“无”。
- Context 只包含紧凑领域定义和禁用同义词，没有需求范围、验收标准、流程、接口、数据库或其他实现细节。
- 用户、Context 和代码冲突已经展示证据并由用户明确裁决，Context 与 PRD 使用同一批准口径。
- ADR 只在难以逆转、缺少背景会令人困惑且存在真实方案权衡时创建。
- PRD 的 `补充说明` 记录 Context 文件、术语变化、用户批准和 ADR 结果，且与实际差异一致。

## 行为与契约

- 按需覆盖主流程、无效输入、空结果、边界值、失败行为、重试或无重试、幂等、并发、兼容性和可观测性。
- 行为依赖角色或调用方时，明确参与者和权限差异。
- 描述数据所有权和跨边界行为，不写易失效的路径或推测性抽象。
- API、事件、持久化、外部调用、状态流转和迁移在范围内时，记录外部可观察行为、业务约束和验收口径；技术形状留给 Design。

## 测试决策

- 选择最高实际可行的既有公开测试缝；新增测试缝时说明理由。
- 测试外部可观察行为，不绑定私有实现细节。
- 将主流程、边界、无效输入和失败行为映射到测试决策。
- 有仓库证据时指出相关模块或既有测试风格，但不得把 PRD 写成实施计划。

## 验收标准

- 每条标准必须可观察、无歧义且可独立验证。
- 覆盖全部范围内业务规则及重要失败和边界行为。
- 除非实现形状本身是已批准契约，否则避免“新增某个类”等实施任务。
- 避免无法度量的“快速”“正确”“友好”等主观描述。

## 中文一致性

- 除不可翻译的技术标识外，文档标题、章节标题和叙述正文必须使用中文。
- 用户故事必须采用“作为……，我希望……，以便……”格式，并完整表达角色、能力和收益。
- 不允许出现 `As a`、`As an`、`I want`、`so that` 等英文模板固定句式。
- 不允许中英文用户故事模板混排。
- 八个固定章节必须与 `SKILL.md` 中的中文名称完全一致。

## 阻塞式自审

交付前，必须用仓库证据或已批准对话对以下问题全部回答“是”：

- 解决方案是否覆盖每类已识别参与者的问题？
- 每条已批准业务规则是否出现在用户故事、实施决策、测试决策或验收标准中？
- 错误、空结果、边界、兼容性和外部影响是否按需解决？
- 领域术语是否符合项目约束，且没有越界产出技术架构、端口、schema、事务边界或具体类型设计？
- 是否仅有一份明确的权威本地 PRD？
- Design 编写者能否在不猜测业务行为的前提下比较技术方案？
- 测试人员能否在不读取未来实现内部细节的前提下导出断言？
- 文档是否不存在占位符、矛盾、外部 Issue 发布指令和隐藏实施工作？
- 文档是否不存在英文模板残留或中英固定句式混排？
- 是否实际完成了 `grilling` 澄清审计，并且阻塞性未决问题为零？
- 是否实际使用 `domain-modeling` 同步了已批准领域语言，或有证据说明无变化？
- `领域上下文同步` 记录是否与 Context/ADR 实际差异及用户批准一致？
- Context 是否保持为领域词汇表，没有混入 PRD 或 Design 内容？

任一答案为“否”时，修订 PRD，并重新执行机械和语义门禁。
