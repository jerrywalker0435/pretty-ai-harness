# 编写高质量 PRD

## 概述

将需求构想转化为一份经过批准、基于仓库证据且全中文的本地 PRD；也可在不改变需求语义时修复既有 PRD 的机械合同。先判定分支，再只执行该分支需要的门禁。

新建或实质修订 PRD 时，存在阻塞性需求决策才使用 `grilling`；涉及领域术语、稳定关系或不变量变化才使用 `domain-modeling`。

新建 PRD 或改变用户价值、业务规则、可观察行为、范围、非目标或验收口径时，**必需子 Skill：** 使用 `superpowers:brainstorming` 完成需求方案比较和批准。

## 快速路由

| 分支 | 判定 | 下一步动作 |
|---|---|---|
| 机械审查 | 只调整路径、章节顺序、固定字段、中文格式，或使用已有批准证据替换占位符，不改变任何需求语义 | 读取文档合同，核对精确机械差异，必要时修订原文件，运行机械与适用语义门禁，然后请求文件复审 |
| 新建或实质修订 | 新建 PRD，或改变用户价值、业务规则、行为、范围、非目标、验收口径或领域语言 | 完成证据清单、条件澄清、条件领域同步和需求方案批准，再修订并校验 |

机械审查先列出预期的精确机械差异，并对照修订前后内容证明需求语义不变；差异为空时不重写文件，只报告文档已符合合同并请求复审。占位符没有可引用的既有批准内容，或发现任何需要改变需求语义的情况时，停止该分支，向用户说明影响并切换到新建或实质修订分支。完成标准是所选分支的全部门禁有可核验证据，而不是调用固定数量的子 Skill。

## 1. 加载约束与证据

声明正在使用 `pretty-writing-prd` 完成需求发现、综合和质量门禁。

如果仓库包含 `.trellis/` 且当前会话尚未初始化，**必需子 Skill：** 使用 `start`。最终决策前读取适用的项目规范、领域语言、ADR、既有契约和相邻测试。

建立有边界的证据清单，覆盖本分支需要的入口、业务流、领域规则、跨边界契约、持久化或外部影响、既有测试缝和兼容性约束。每个清单项必须有仓库来源、已批准输入或明确阻塞结论；全部闭环后停止广泛探索。关键证据无法从仓库获得时，只询问一个聚焦问题，不得虚构。

## 2. 执行需求澄清与领域上下文门禁

每次都建立澄清审计，明确区分：

- 仓库事实；
- 用户已确认需求；
- 尚未验证的假设；
- 阻塞性未决问题。

先完成澄清审计。存在阻塞性未决问题时，**必需子 Skill：** 完整读取并使用 `grilling`，一次只解决一个需求决策并给出推荐答案，覆盖范围、角色、业务规则、主流程、边界、失败行为、兼容性和验收口径。没有未决问题时记录“阻塞性未决问题：无”，不调用 `grilling`，也不重复盘问已确认内容。

审计发现领域术语、稳定关系或定义不可分割的不变量需要新增、修订或裁决时，**必需子 Skill：** 使用 `domain-modeling`：

1. 对照现有 `CONTEXT.md` 挑战模糊、重载或冲突术语，并与代码和测试事实交叉验证。
2. 单个领域术语、稳定关系或定义不可分割的不变量获得用户明确确认后，立即按 `domain-modeling` 格式更新 Context，不等待完整 PRD。
3. 未决问题、假设、需求范围、验收标准、流程步骤、接口字段、查询方式、事务、重试和其他实现决策不得写入 Context。
4. 没有领域语言变化时不得为了留痕修改 Context，记录“领域上下文变化：无”。
5. 后续澄清推翻已写结论时，立即同步修正 Context 并记录原因。
6. 只有决策难以逆转、缺少背景会令人困惑且存在真实方案权衡时才创建 ADR。

用户表述、Context 和代码行为冲突时，展示三方证据并用 `grilling` 获得一个明确目标口径。Context 过期则在单项批准后立即修订；代码偏离则把代码作为当前行为证据，把批准结论作为目标业务语义写入 PRD。冲突未解决时不得生成正式 PRD，也不得自动以最新口述、现有文档或运行代码中的任一方为准。

`grilling` 和 `domain-modeling` 只完成澄清与领域语言沉淀，不生成 PRD 或 Design。机械审查分支确认需求语义和 Context 均不变化后，按已列出的非空机械差异修订原文件；没有差异时不落盘。其他分支在阻塞性未决问题清零且 Context 同步完成后进入需求方案综合。

## 3. 完整执行 brainstorming

新建或实质修订分支调用并遵循 `superpowers:brainstorming`，必须包含：

1. 复用已完成的仓库探索与澄清结论，不重复询问已确认问题。
2. 只有发现新的阻塞性歧义时才返回上一门禁逐项解决。
3. 提供两到三个方案、权衡和推荐项。
4. 按适当粒度分节呈现需求方案并逐节批准。
5. 获得用户对完整需求方案的明确整体批准。

已回答的问题无需重复。新建或实质修订分支在批准前不得编写最终 PRD、生成计划或实施代码；机械审查分支不制造虚假的需求方案或批准。

PRD 阶段只确定用户价值、业务规则、可观察行为、范围、非目标和验收口径，不产出技术架构、模块职责、端口、数据库 schema、事务边界、具体类或方法设计；这些内容交由 `pretty-writing-design`。

## 4. 综合需求结论

新建或实质修订分支在完整需求方案批准后，综合澄清结论、仓库证据和测试缝选择，起草最终 PRD。机械审查分支沿用既有批准结论，只修订原文件的机械合同。调用过 `superpowers:brainstorming` 时，以下规则覆盖其默认终态：

- 不调用 `superpowers:writing-plans` 或 `pretty-writing-plan`。
- 不使用 Issue Tracker，不应用 `ready-for-agent`。
- 不使用英文标题或英文用户故事句式；必须采用本 Skill 定义的中文结构。

## 5. 发布一份中文本地 PRD

唯一权威文档写入：

```text
docs/pretty/<topic>/YYYY-MM-DD-<topic>-prd.md
```

`<topic>` 必须使用小写 kebab-case，且目录名必须与文件名中的 `<topic>` 完全一致。同一主题的 PRD、Design、Plan 和 Execution Report 必须聚合在同一个 `docs/pretty/<topic>/` 目录；日期使用 PRD 首次创建日期，后续修订不得改名。

文档标题、章节标题、正文、用户故事和验收标准必须使用中文。事件编码、API、类库、代码标识等不宜翻译的技术名称可保留原文。不得残留英文模板固定句式。

起草或机械修订前，完整读取 [references/quality-gates.md](references/quality-gates.md) 的“文档合同”，按其唯一章节顺序、用户故事格式和领域上下文同步结构生成。该 reference 是固定文档结构的单一真相源。

使用项目领域语言，优先描述外部可观察行为并选择最高可行的既有测试缝。不要写易失效的具体实现文件路径、大段代码、技术架构、端口、数据库 schema、事务边界或具体类型形状。

本阶段不得为同一主题创建第二份 PRD、Issue、任务文档或实施计划。

## 6. 执行质量门禁

完整读取 [references/quality-gates.md](references/quality-gates.md)，执行所有适用的语义门禁。

运行：

```bash
bash <skill-dir>/scripts/validate-prd.sh <prd-file>
```

机械校验不能代替语义批准。机械校验通过后，继续审查需求覆盖、一致性、架构对齐、可测试性、范围和验收标准。任何失败都必须先修复，再重新运行对应门禁。不得交付失败、含糊或中英模板混排的 PRD。

## 7. 停在用户复审门禁

请求用户复审已写入的本地 PRD。用户要求修改时，修订并重新执行机械和语义门禁。

用户只要求 PRD 时，到此停止。不得生成设计、实施计划或修改生产代码。用户后续明确要求设计时，将其作为新请求交由 `pretty-writing-design` 处理；只有已批准 Design 才能继续交由 `pretty-writing-plan`。

## 禁止事项

- 在新建或实质修订分支跳过需求方案批准。
- 存在阻塞性未决问题却不使用 `grilling`，或没有未决问题仍制造重复盘问。
- 没有领域变化仍仪式性调用 `domain-modeling`，或发生变化却未同步 Context。
- 把改变需求语义的修订伪装成机械审查。
- 把假设、需求细节、验收标准或实现决策写入 Context。
- 遇到用户、Context 和代码冲突时自动选择一方或把 Context 同步推迟到 PRD 之后。
- 把零散讨论当成完整需求方案批准。
- 跟随 `brainstorming` 进入计划 Skill。
- 同时产生 PRD 和设计文档。
- 机械校验通过后跳过语义审查。
- 保留 `TODO`、`TBD`、占位符、矛盾或不可测试的验收条件。
- 输出英文章节标题、`As a/an`、`I want`、`so that` 等模板残留。
- PRD 请求完成后继续规划或实施。
