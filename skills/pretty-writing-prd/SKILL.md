# 编写 PRD

把用户目标、业务规则和必要仓库事实整理成可由用户确认的 PRD。PRD 的 `REQ/AC` 只锁定外部
可观察结果、业务规则和验收语义，不选择技术实现、不创建 ADR、不进入 Design 或 Execution。
文末的“Design 交接”只保存为确认当前行为而读取到的仓库定位快照，不改变需求语义或指定未来
实现。

加载当前阶段模板 [assets/prd.md](assets/prd.md)。

## 精简辅助：i-have-adhd（可用时默认使用）

开始工作前，若 `$i-have-adhd` 可用则加载并应用其规则；同一会话已加载且仍生效时直接复用。
加载成功后将其用于对话、交付消息以及组织正文和检查冗余。未安装或无法加载时继续执行，
使用本 Skill 的内置精简规则，不把它作为阻塞条件。

若已加载该 Skill，对话和交付消息遵循其规则；PRD 正文始终按本模板与下方精简规则保留完整业务语义，
不机械套用首行操作或五项列表上限，不因此省略 `REQ/AC`。

## 新增必要性与复用边界

本 Skill 遵循“非必要、勿新增”：先复用已有 topic、`prd.md`、章节、业务术语和已确认的领域上下文，
只有当前需求合同或明确的领域建模门禁要求，且现有承载无法表达时才新增内容。每项新增都必须有当前
用途，并能说明它承载独立的业务语义、外部边界、验收需要或领域上下文；不能为完整性观感、未来变体、
排版偏好或记录调查过程新增故事、图、表、清单、报告或文件。新增内容放入已有交付结构，不另建复用
清单、调查报告或审查阶段。

领域建模命中门禁时，`CONTEXT.md`、`CONTEXT-MAP.md` 或 ADR 只按 `domain-modeling` 的必要性规则
创建或更新；没有需要记录的领域事实就不创建。校验脚本、临时文件和其他辅助产物只在当前命令确实
需要时使用，并在不再需要时清理；它们不属于 PRD 交付物。

## 1. 模式和输入

用户要求创建、完善或修订时进入写作模式。PRD Skill 只负责写作和修订，用户负责最终 Review。

PRD Skill 的主文档只写：

```text
docs/pretty/<topic>/prd.md
```

`<topic>` 使用小写 kebab-case；已有文件原地修订。读取用户需求、适用仓库规则、足以说明当前外部行为的入口和测试事实，以及共享领域上下文。Bug 至少确认复现条件、当前结果、期望结果和回归边界；行为保持型重构至少确认问题、行为保持约束和可验证成功标准。为确认当前行为而读取公共入口或测试时，按“Design 交接”记录已获得的定位；不得为填写定位而额外搜索。

仓库读取采用渐进范围：先读取仓库规则和领域上下文，只在确认当前外部行为、复现条件或验收观察面需要时，继续读取公共入口及其现有行为测试。事实已经充分时立即停止，不在 PRD 阶段遍历内部 caller/callee、建立实现调用图、盘点候选修改文件或全仓搜索技术方案；这些工作由 Design 承担。同一会话中已经读取且未发生修改的入口、测试和规则直接复用，不重复调用工具读取。

这不限制领域建模门禁产生配套领域文档：命中门禁时，由 `domain-modeling` 负责读取或更新 `CONTEXT.md`、`CONTEXT-MAP.md`，并按其规则处理相关 ADR。PRD Skill 不直接修改这些文件；它们不属于 PRD 正文，但属于交付前必须完成的领域上下文工作。

### Design 交接：仓库定位快照

该章节按本次调查是否触发而保留；只在已经读取到相应事实时填写定位。规则是“有则必记、无则不查”：

- 本次为确认当前行为读取过公共入口或行为测试时，`定位状态` 写为“已核验”，并按相关
  `REQ/AC` 记录每个已获得的 `仓库相对路径#symbol`；入口和测试只记录当前仓库事实，不只写类名。
- 一个入口/测试组合占一行；同一 `REQ/AC` 有多个已读取入口时分行记录，不把内部调用链展开到表中。
- 一行中只有入口或测试已读取时，未读取的一列写“未获取”；整张表至少包含一个真实定位。
- 本次不需要读取入口或测试时直接删除该章节，不输出空表或“未获取”状态，且不得为填表额外搜索。
- 只记录公共行为入口和公共行为测试。不得记录 caller/callee、Adapter、候选修改文件、新类、
  数据库方案或其他 Design 决策。
- Design 将快照作为已知入口的定位起点，并在自己的预检批次中核验新鲜度；快照失效时只围绕
  失效项定向重定位，不能据此把普通重命名或迁移当成需求冲突。

## 2. 写作中的不确定性

### 2.1 领域建模门禁（强制）

在写 PRD 前检查以下信号：

- 新增或重定义业务术语、事件、实体或角色；
- 新增状态、生命周期或状态转换；
- 新增身份、幂等键、归属或唯一性规则；
- 新增跨事件、工单、参与人等上下文的关系；
- 使用“当前有效、最新、历史、失效”等需要统一口径的词语；
- 一个业务规则同时影响两个以上领域上下文。

命中任一信号时，必须调用 `domain-modeling`，不能仅阅读其规范。该 Skill 不可用时停止，不使用本地替代流程。

调用后必须由 `domain-modeling` 完成：

1. 读取现有 `CONTEXT.md`、`CONTEXT-MAP.md` 和相关 ADR；
2. 识别并澄清新增或冲突的领域术语；
3. 术语确认后立即更新已有 `CONTEXT.md`；
4. 没有 `CONTEXT.md` 时，按其格式创建根目录 `CONTEXT.md`；多上下文关系按其规则维护 `CONTEXT-MAP.md`；
5. 仍存在外部语义选择时，停止写作并调用 `grilling`；
6. 未完成领域建模或上下文更新时，不得交付 PRD，也不得请求 Review。

`CONTEXT.md` 只记录领域词汇、关系和不变量，不记录类名、数据库、接口或技术方案。PRD 阶段不强制创建 ADR；ADR 是否需要由 `domain-modeling` 按既定条件判断，技术决策仍由 Design 阶段承接。

未命中上述信号时才允许跳过 `domain-modeling`，并在交付说明中记录跳过原因。

### 2.2 外部语义不确定性

读取用户需求描述和必要仓库事实后，区分“当前代码事实”和“用户希望达到的外部结果”。如果存在影响外部行为或需求语义的不确定性，立即调用 `grilling` 与用户澄清：一次只处理一个决策，并给出推荐答案。

- 不自行猜测、消除或掩盖不确定性；
- 不把尚未由用户确认的选择写入最终 PRD；
- 用户澄清前不继续生成依赖该决定的需求或验收标准；
- 纯技术实现细节不写入 PRD，交由 Design 决定；
- 未命中领域建模门禁时才允许跳过 `domain-modeling`，并在交付说明中记录跳过原因；命中门禁时必须先完成领域建模，再继续写作；
- PRD 不创建 ADR。技术决策是否需要 ADR 由 Design 阶段处理。

“最简单、可逆的实现”不是 PRD 阶段的决策规则。PRD 只确认外部行为；实现方案留给 Design。

## 3. 编写 PRD

### ADHD 友好的最小充分表达

本节将精简表达规则落实到 PRD 正文，写作和交付前均须检查；`$i-have-adhd` 可用时一并应用。

- 背景默认一段，目标每项一句；场景只写角色、触发和结果，不铺陈故事。只为不同角色、触发或结果增加场景，不设故事数量下限。
- 规则只在 `REQ` 完整定义；场景只概述结果，`AC` 只给足以验证该规则的具体条件与预期结果，不复制整段规则。场景和验收仍须用业务语言独立读懂，不用编号代替语义。
- 一条独立规则一个 `REQ`；同一结果的不同输入合并在一个 `AC` 下。公共约束集中定义，相关需求引用；独立变化或独立验收的语义必须拆开。
- 同一说明不同时配段落、表格和图；图只补充文字难以说清的分支，不再配逐节点说明。未触发的可选章节删除，不写“无变化”“不涉及”的解释段落。
- 交付前删除不影响业务决定、外部结果、边界或验收判断的句子，包括调查过程、价值套话和同义复述；保留必要的状态、失败、并发与兼容语义，不靠省略合同或固定总字数换取简短。

- 每条需求只表达一个外部行为或业务规则；
- 覆盖主流程、重要边界、失败、状态、时序、重复、并发和兼容语义；
- 将业务约束写入相关需求或验收标准；只有跨多个需求且无法自然归属时，才增加可选的 `业务约束`；
- 不写未澄清的问题、待用户选择项或占位内容；
- 除“Design 交接”中的当前 `path#symbol` 定位快照外，不写类、方法、模块职责、数据库 Schema、
  事务实现、设计模式、完整代码或实施任务。

简单需求使用短场景列表；复杂需求按不同角色、触发或结果增加必要场景，不因出现幂等、并发或异步就扩写故事。`REQ-*` / `AC-*` 是唯一需求合同。

“用户与场景”用自然语言写清主体、背景、触发和结果；标题、正文、表格及附注均不出现或链接需求/验收编号。编号追踪保留在需求、验收标准或 Design 交接中。

验收标题及 `Given/When/Then` 使用具体业务条件、动作和可验证结果，不用 REQ 编号、链接或附注代替描述。保留 `AC-*` 编号，需求关联单独写“关联需求：REQ-001”。例如：Given 已预占 3 份菜品，When 退掉 1 份，Then 释放 1 份预占并保留其余 2 份。

复杂业务可以增加可选的“核心用例流程”图示，但必须满足：

- 只表达业务流程，不表达技术实现流程；
- 使用业务角色、业务动作、业务分支和业务结果；
- 不出现类、方法、模块、数据库、Adapter、事务或设计模式；
- 流程图只作解释视图，不能替代 `REQ/AC`；
- 简单需求不强行增加流程图。

## 4. 自审、校验、请求 Review

写作完成后进行作者自审，确认问题、目标、场景、`REQ/AC`、领域语言以及成功/失败边界一致，没有实现泄漏、不确定选择或占位内容。自审不等同于用户 Review。

- [ ] “用户与场景”不含需求编号或验收编号，每个场景无需跳转即可读懂业务触发和结果。
- [ ] 验收场景标题及 `Given/When/Then` 使用实际业务语义，不用 REQ 编号替代条件、行为或结果；需求关联单独列出，每个场景无需查阅关联需求即可执行验收。

领域建模门禁自审：

- [ ] 已执行领域建模门禁，并记录命中或跳过原因；
- [ ] 命中领域信号时确实调用了 `domain-modeling`；
- [ ] 新术语已写入或确认无需写入 `CONTEXT.md`；
- [ ] 未把未确认的领域语义写入 PRD；
- [ ] 命中门禁时，领域建模和上下文更新已完成，才允许请求 Review。

Design 交接自审：

- [ ] 已读取公共入口或测试时，交接表覆盖已获得的 `REQ/AC → path#symbol` 定位；
- [ ] 未读取时删除交接章节，且没有为填写交接额外搜索；
- [ ] 交接只含当前公共入口/测试事实，没有混入未来实现选择。

标准路径运行本 Skill 提供的机械校验：

```bash
python3 <pretty-writing-prd>/scripts/validate_prd.py \
  docs/pretty/<topic>/prd.md
```

仅在修改校验器时运行其回归测试；正常 PRD 写作不增加测试阶段：

```bash
python3 -m unittest discover -s <pretty-writing-prd>/tests -p 'test_*.py'
```

交付只报 PRD 路径、校验结果和领域建模门禁状态；命中时附实际变更文档，跳过时一句说明原因。
需要用户判断的决定或限制单独指出，其余信息留在正文，不逐章回顾。请求用户 Review 后停止，不自动进入 Design。

## 红线

- 不把实现选择写进 PRD；
- 不将未澄清的外部行为写入 PRD；
- Design 交接只能记录已读取的当前公共入口/测试定位，不得借此引入实现方案；
- 不创建 ADR；
- 不把业务故事变成第二套需求合同；
- 不把业务流程图写成技术实现流程图；
- 不自动进入 Design 或 Execution。
