# 编写 Java/Spring PRD

## 目标

把用户目标、业务规则和仓库事实整理成可由产品、研发和测试共同确认的 PRD，或只读判断现有 PRD 是否足以进入 Design。PRD 只锁定外部可观察结果，不选择技术实现。

**REQUIRED SUB-SKILL：** 完整读取并使用 `pretty-java-spring-core` 的共享合同与 PRD 模板。本 Skill 是本阶段唯一流程控制器。

## 工作流

### 1. 确认模式与输入

宣布使用 `pretty-writing-prd`。用户只要求评估、检查或 Review 时进入只读评审；要求创建、完善、改写或修订时进入写作模式。

写作模式只使用：

```text
docs/pretty/<topic>/prd.md
```

`<topic>` 使用小写 kebab-case；已有文件原地修订。读取适用仓库规则、当前入口、可观察行为、相关测试和共享合同要求的领域上下文。Bug 至少确认复现条件、当前结果、期望结果和回归边界；行为保持重构至少确认问题、行为保持约束和可验证成功标准。

### 2. 执行只读评审

接受用户给出的 PRD 路径，只读取文档、必要仓库事实和领域上下文；不修改、移动或复制文件，不更新 `CONTEXT.md`、`CONTEXT-MAP.md` 或 ADR，不创建评审稿或下游制品。

使用“不同结果测试”：若两种合理实现都满足当前 PRD，却产生不同外部结果，则 PRD 不完整。重点检查身份与集合、选择与顺序、状态与生命周期、时间、可靠性、失败与竞态；关键词只触发语义检查，不自动判错。

依次输出并停止：阻塞问题、建议改进、下游影响、`可进入 Design / 修正后再进入 Design`。标准路径可运行 PRD 链校验；非标准路径仍可评审，但不迁移或复制。高影响歧义只报告推荐解决方向；用户授权修订后才使用 `grilling`。

### 3. 关闭写作模式中的结果未知

- 仓库事实自行调查；当前行为只有在兼容合同、领域规则或用户意图要求时才固化。
- 外部等价的非阻塞细节采用最简单可逆方案。
- 核心术语、业务身份、生命周期、状态、不变量、归属或关系发生歧义并影响需求时，**REQUIRED SUB-SKILL：** 使用 `domain-modeling`，同步对应领域语言；PRD 不创建 ADR。
- 只有共享合同中的四项条件同时成立时，才使用 `grilling`；一次只解决一个决策并给出推荐答案。

### 4. 编写 PRD

使用共享模板并替换全部占位内容：

- `REQ-001` 起连续编号，每条只表达一个外部行为或业务规则。
- `AC-001` 起连续编号，每条关联 `REQ` 并写成可观察结果。
- 覆盖主流程、重要边界、失败、状态、时序、重复、并发和兼容语义。
- 不写类、方法、模块职责、schema、事务、设计模式、完整代码或实施任务。

简单需求用短场景列表。出现多个真实角色/系统触点、状态分支、多步骤、失败隔离、幂等、并发或异步结果，或仅靠 `REQ/AC` 难以理解时，生成 3–6 个具象业务故事；每个故事关联已有 `REQ/AC`，不新增 `US`。故事只是解释视图，`REQ/AC` 是唯一需求合同。

### 5. 自审、校验并请求 Review

确认问题、目标、场景、`REQ/AC`、领域语言及成功/失败边界一致，没有实现泄漏或占位内容。运行：

```bash
python3 <pretty-java-spring-core-dir>/scripts/validate-pretty-docs.py \
  docs/pretty/<topic> --through prd
```

告知路径、需求和验收数量、领域文档变更与校验结果，请求一次用户 Review，然后停止。不得自动进入 Design。

## 红线

- 不制造虚假选项或无结果差异的盘问。
- 不以机械校验代替需求判断。
- 不让业务故事成为第二套合同。
- 不在只读评审中修改任何文件。
- 不记录审批元数据或跨阶段修订包。
