# 编写 Java/Spring PRD

## 目标

把用户目标、业务规则和仓库事实整理成清晰的 PRD。PRD 只描述外部结果、范围和业务语义，不选择技术实现。

**REQUIRED SUB-SKILL：** 使用 `pretty-java-spring-core` 的共享约定和 PRD 模板。本 Skill 负责 PRD 阶段的工作方式。

## 工作流

### 1. 确认模式与输入

宣布使用 `pretty-writing-prd`。用户要求评估、检查或 Review 时只读处理；用户要求创建、完善或修订时进入写作模式。

写作模式使用：

```text
docs/pretty/<topic>/prd.md
```

`<topic>` 使用小写 kebab-case；已有文件原地修订。读取用户意图、当前行为、适用仓库规则和相关领域上下文。Bug 至少确认复现条件、当前结果、期望结果和回归边界；行为保持重构至少确认问题和行为保持要求。

### 2. 执行只读评审

接受用户给出的 PRD 路径，只读取文档和必要仓库事实；不修改、移动或复制文件，不更新领域文档，不创建其他阶段文档。

检查两种合理实现是否可能产生不同的外部结果。重点关注身份与集合、选择与顺序、状态与生命周期、时间、可靠性、失败、重复和并发；关键词只触发进一步理解，不自动判错。

输出阻塞问题、建议改进和是否适合进入 Design，然后停止。高影响歧义只报告推荐解决方向；用户明确要求继续讨论时才使用 `grilling`。

### 3. 处理未知并写作

- 仓库事实自行调查；只有兼容合同、领域规则或用户意图能够支持时才固化当前行为。
- 不影响外部结果的细节采用最简单、可逆的方案。
- 核心术语、业务身份、生命周期、状态、不变量、归属或关系存在歧义时，使用 `domain-modeling` 同步领域语言。
- 使用共享模板，按自然语言和场景描述背景、目标、范围、用户、主流程、重要边界、失败和业务规则。
- 不写类、方法、模块职责、schema、事务、设计模式、完整代码或实施步骤。

简单需求使用短场景列表；复杂需求再补充少量完整业务故事，不重复维护两套规则。

### 4. 收尾

替换全部占位内容，确认问题、目标、场景和业务规则前后一致。告知文档路径和主要内容，请求用户 Review 后停止，不自动进入 Design。

## 红线

- 不制造没有实际结果差异的选项。
- 不把技术实现写进 PRD。
- 不在只读评审中修改任何文件。
- 不把业务故事写成另一套规则。
