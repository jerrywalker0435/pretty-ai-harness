# Plan 阶段的 TDD 测试设计

本文件只定义如何在 `plan.md` 中设计测试；它不执行测试，也不把设计提案伪装成真实 TDD 证据。

## 铁律

行为生产代码必须先有一个会因目标行为缺失而失败的 UT 设计。Plan 中按以下顺序展示：

```text
一个行为的 UT -> 预期正确 RED -> 当前切片最小 GREEN -> 保持 GREEN 的必要整理
```

测试若在修复前就通过，说明它覆盖了已有行为、入口错误或断言无效；必须修正测试设计，不得把“预期通过”当 RED。测试若因编译、fixture、依赖或环境错误而失败，也不算正确 RED。

## 行为测试要求

- 使用 public 行为入口；不要为测试暴露 private 方法。
- 一个测试只证明一个可观察行为；名称说明结果，不写“test1”或“works”。
- 使用真实被测规则、领域对象和纯内存协作者；只有边界外依赖才 fake/stub/mock。
- 断言业务结果、状态变化、异常合同或完整边界请求；不要以 mock 调用次数/顺序作为主要成功标准。
- 先覆盖主路径，再覆盖会改变结果的边界、异常、幂等、并发或兼容分支。
- 重复输入只使用参数化测试或紧凑数据表；公共 fixture 可在同一测试类中集中定义。
- 测试必须快速、独立、可重复、自验证，不启动 Spring，不访问真实/嵌入式基础设施。

## Plan 中必须展示的内容

每个行为 TASK 的核心测试代码必须让 Reviewer 直接看出：

1. 被测 public 入口和真实输入。
2. fixture、边界替身及其注入位置。
3. 目标行为缺失时为什么会断言失败。
4. 独立的业务预期，而不是从实现复制出来的预期。
5. 正常、边界和失败路径中哪些已覆盖，哪些属于不适用。

代码无法表达的重要限制才补一句说明。不要用六段式文案代替测试代码，也不要只写“补单测”“测试边界条件”。

## 测试栈与命令

- 先读取 `pom.xml`、`build.gradle`、CI 和现有测试，使用真实 JUnit/Mockito/AssertJ 版本和命名。
- 没有现成测试栈时，Java 默认 JUnit 5；只有需要隔离边界协作者才用 Mockito。
- Plan 必须给出精确的 focused test、相关回归和构建/静态检查命令；不能写“运行相关测试”。
- 命令只从真实仓库配置提取，Plan 阶段不执行。无法确认命令时停止或降低声明，不能留 `<command>` 等占位符。

## 行为保持重构

先列出已有行为的稳定入口和关键断言，再设计不改变外部结果的重构。重构本身不制造虚假的 RED；只有发现缺失的行为覆盖时，才为该缺口设计真实失败测试。

## 禁止的捷径

- 先写生产代码、再补回归测试。
- 用手动验证替代可重复 UT。
- 因为“只是一个条件”而跳过 RED 设计。
- 用集成、契约、E2E、Spring slice、Testcontainers 或真实数据库掩盖单元边界不清。
- 用一堆 mock 证明协作过程，却没有业务结果断言。
- 用测试专用生产方法、反射或扩大可见性绕过错误 Interface。
- 用覆盖率数字替代边界和失败路径。

“测试以后补”“实现很简单”“集成测试更真实”“仓库没有测试所以不用写”都不是例外；它们说明需要回到 Interface 和 UT 边界重新设计。
