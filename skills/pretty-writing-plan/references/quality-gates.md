# 高质量实施计划门禁

## 输入门禁

- 输入必须是已批准且通过门禁的 Design；缺失、未批准或仍有阻塞项时返回 `pretty-writing-design`。
- Plan 不得补写或改变需求与设计，也不得用实施细节绕过批准。

## 中文输出

- 计划标题、章节、任务、步骤、说明、预期结果和执行交接必须使用中文。
- 代码标识、路径、命令、技术名称、Skill 名称和协议字段允许保留英文。
- 拒绝 `Implementation Plan`、`Goal`、`Architecture`、`Tech Stack`、`Task`、`Files`、`Step`、`Run`、`Expected` 等英文模板标签。
- 机械校验通过后仍须语义审查，拒绝代码块之外的成段英文自然语言说明。

## Skill 选择

| 任务证据 | 计划生成要求 | 执行要求 |
|---|---|---|
| 任意多步骤实施 | 加载仓库规则并使用 `superpowers:writing-plans` | 必须使用 `pretty-executing-plan`，并执行 TDD、维护执行报告、检查覆盖率、审查任务和精确验证 |
| 修改 Java 类/接口/服务/网关/适配器职责 | 必须使用 `121-java-object-oriented-design`，记录发现和计划修正 | `java-code-review` |
| 修改 Java DTO/Entity/PO/VO/枚举/命令/查询/结果/类型边界 | 必须使用 `122-java-type-design`，记录命名、空值、层次和签名发现 | `java-code-review` |
| 新增或修改行为 | 实施前定义可观察行为并编写完整失败测试 | `superpowers:test-driven-development` |
| 修复缺陷 | 确立根因和可复现的回归测试 | `superpowers:systematic-debugging`，然后执行 TDD |
| 新增/修改端口、领域/应用服务、依赖方向或职责拆分 | 必须使用 `solid-principles`，起草任务前修正违规 | `clean-code-guard`、`java-code-review` |
| 跨层或跨模块流程 | 读取仓库跨层指南，追踪生产者、转换、契约、消费者、持久化和副作用 | `check-cross-layer` |
| 修改领域术语、状态、不变量、聚合归属或业务规则 | 必须使用 `domain-modeling` 和 `solid-principles`，定义术语、不变量、归属和端口 | 领域测试和 `solid-principles` |
| 保持行为不变的重构 | 说明保留的行为和回归边界 | `refactor`、回归测试、`clean-code-guard` |
| 测试覆盖薄弱 | 列出缺失行为和正确测试层级 | `improve-ut` |

只选择有任务或仓库证据支持的条件性 Skill。每个“必须”触发条件都是确定性的：必须在计划生成阶段执行，不能推迟到实施阶段。

## 计划生成 Skill 审计门禁

`## 计划生成质量审查` 必须置于倒数第二，紧邻 `## 执行交接说明`，并具备以下三类记录：

- `实际使用的计划生成 Skill`：逐项记录 Skill、触发证据和审查范围。
- `质量发现与计划修正`：记录具体发现和对应修正；只有列出已审查证据时，才允许写“无阻塞问题”。
- `最终审查结论`：明确全部发现是否已经修正、复验，是否仍有阻塞项。

如果计划只是列出未来执行 Skill、声称使用却没有发现、遗漏确定性的 Java/领域触发条件，或遗留未解决的阻塞发现，则拒绝该计划。机械结构存在只是必要条件而非充分条件；语义审查必须把审计记录与仓库证据进行对照。

## 文档顺序与任务标识

标题和 Agent 执行要求之后，顶级章节必须且只能按以下顺序出现：

1. `输入、目标与边界`
2. `具体实施任务`
3. `集成单元与执行编排`
4. `需求到任务追溯`
5. `跨层验收矩阵`
6. `代码实现质量门禁`
7. `测试与覆盖率门禁`
8. `计划生成质量审查`
9. `执行交接说明`

任务标题固定为 `### 任务<n>-<任务名称>`。编号从 `1` 连续递增；名称使用不含 Markdown、路径、命令、状态或换行的中文动宾短语。所有审查型引用使用反引号包裹的完整标识 `任务<n>-<任务名称>`，并与标题完全一致；`任务<n>` 仍是稳定机器主键。

每个任务正文必须自包含局部实现与验证，不依赖后置门禁解释代码、TDD 命令或预期。需求追溯必须同时覆盖全部需求与全部任务。跨层验收矩阵按端到端业务链路组织；不适用时必须保留章节并给出基于文件和调用链的具体理由。

`## 执行交接说明` 严格置底，且只允许以 `Plan 路径`、`校验状态`、`未决项`、`下一步选择` 四个加粗字段记录交接摘要。`Plan 路径` 必须与当前权威文件的 `docs/pretty/<topic>/YYYY-MM-DD-<topic>-plan.md` 相对路径完全一致；没有未决项时显式写“无”，不得重复任务、矩阵或门禁正文。

## 集成单元与执行编排

在全部实施任务之后定义唯一的 `## 集成单元与执行编排`。任务描述怎样实现，集成单元描述怎样安全交付；不要让执行器临时猜测边界。

**提交名词边界：** `worktree 候选提交` 是隔离 worktree 分支上的不可变证据提交；`当前分支本地提交` 是候选差异应用到当前工作区、经人工批准后在当前开发分支创建的提交。两者通常是不同的 commit SHA，候选提交不等于当前分支提交授权。

使用以下固定结构：

```markdown
## 集成单元与执行编排

**默认执行模式：** 单集成单元审批

**可选执行模式：** 一次性执行

**模式切换条件：** 仅允许在单元尚未开始或单元已经完成当前分支集成提交的安全检查点切换，并重新记录人工批准。

**旧 Plan 迁移：** 旧格式 Plan 必须由 `pretty-writing-plan` 显式迁移、重新校验并获得人工批准，禁止执行阶段自动推断。

### 集成单元 U1：<名称>

- **包含任务：**
  - `任务1-<任务名称>`
  - `任务2-<任务名称>`
- **前置依赖：** 无
- **集成顺序：** 1
- **风险等级：** 低
- **审查策略：** 单 Reviewer
- **文件所有权：** `<path>`、`<test-path>`
- **交付类型：** 原子任务组
- **原子组理由：** <这些连续任务无法独立构建或验证的具体原因>
- **独立验证：** `<真实命令>`
- **并行实现：** 禁止
- **并行隔离证据：** 不适用（默认模式串行实现）
- **集成检查点：** 隔离 worktree 候选提交 -> 人工 Review -> 将候选差异应用到当前工作区（保持未暂存） -> 人工批准当前分支提交 -> 当前分支本地提交
```

应用以下合同：

- 使用连续正整数标识任务，使用按声明顺序排列的 `U1`、`U2` 等标识集成单元。`包含任务` 必须使用嵌套列表，一行一个完整任务标识；每个任务恰好归属一个单元，名称必须与标题一致。
- 只引用此前已经声明的前置单元，使依赖顺序可执行且无环。
- 只包含一个可独立构建、验证和回滚任务的单元声明为“独立任务”，并为原子组理由写带原因的不适用；只有包含至少两个不能拆分交付的连续任务时，才声明为“原子任务组”并给出真实原因。
- 列出单元负责修改的全部生产、测试、配置和迁移文件。纯验证单元没有文件时写带原因的不适用。语义审查还要检查并行单元之间没有文件所有权冲突。
- 将低风险单元设置为“单 Reviewer”，由一个独立 Reviewer 顺序完成 Plan 符合性和代码质量审查；将高风险、跨边界、安全、数据迁移或难回滚单元设置为“双 Reviewer”。
- 默认禁止并行实现。允许时必须使用 `允许（<理由>）`，且并行隔离证据必须同时说明独立 worktree、文件不重叠、依赖无先后冲突和确定的集成顺序。只读检查可并行；会共享构建目录、端口、数据库或外部状态的验证不得并行。
- 默认逐单元在隔离 worktree 产生候选提交并停在人工 Review。Review 通过后将候选差异应用到当前工作区，停在当前分支提交批准；批准后才创建当前分支本地提交。只有人类在安全检查点选择一次性执行时，才连续产生彼此独立的单元候选提交，在最终全量门禁和统一 Review 后一次性应用组合差异并申请一次当前分支组合提交批准。
- 只允许在单元尚未开始或已经完成当前分支集成提交时切换模式。模式切换不修改历史证据，必须在 Execution Report 追加控制事件和人工批准。
- 将 Plan 作为只读批准合同。执行进度、暂停、Review、候选提交、驳回、差异应用和当前分支提交证据只进入 Execution Report。
- 拒绝旧 Plan 的隐式兼容。先迁移全部章节、任务标识和引用，重新校验并获得人工批准，再由新的执行批次复核既有成果。

## 生成门禁

计划交付前必须通过所有适用门禁。

### 范围与架构

- 每项需求至少映射到一个任务和一个验收检查；每个任务也必须映射到需求、非功能约束或交付保障目标。
- 列出准确文件，并为每个变更文件赋予一个清晰职责。
- 保持仓库依赖方向和边界转换。
- 端到端追踪外部调用、持久化、事件、配置和消费者。
- 适用时识别兼容性、迁移、回滚、幂等、并发和可观测性风险。
- 优先采用仓库既有模式；任何新抽象都必须说明理由。
- 完整覆盖全部功能需求、边界行为和非功能约束；功能完整性是代码简化不可突破的底线。

### 代码与契约质量

- 保持各任务中的命名、类型、方法签名、字段和转换一致。
- 为新类型和测试提供完整、可编译的代码。
- 为现有代码提供完整替换方法或精确差异。
- 只有机械性重复才允许使用完整表格，并逐项列出所有受影响位置。
- 每个代码片段都必须体现项目语言和运行时规则。
- 具体说明校验、错误语义、空值处理和边界行为。
- 拒绝推测性泛化、未使用的扩展点和无关清理。
- 优先采用满足当前需求的最简单实现，拒绝没有现实调用方或必要性证据的抽象、包装和间接层。
- 使用准确命名、清晰职责、直接控制流和统一领域术语表达业务意图；拒绝含糊命名、重复业务分支和技巧性写法。
- 简洁不得以删减校验、错误处理、安全措施、可观测性、用户明确行为、必要测试或行为断言为代价。
- 只治理本次新增或修改代码及完成需求必需的直接关联代码；必要旧代码调整须说明原因、行为保持边界和回归验证。
- `## 代码实现质量门禁` 必须在任务、编排和验收矩阵之后，以表格记录功能完整性、简洁性与必要性、可读性与业务表达、测试完整性保护和变更范围控制的具体审查结论；每行关联真实完整任务标识，不得只复制原则性结论。

### 测试质量

- 每个任务声明 `任务类型：业务行为` 或 `任务类型：非行为（<理由>）`。
- 每个行为变更都从一个聚焦的失败测试开始。
- 给出准确命令和预期失败原因。
- 只实现足以通过该测试的行为。
- 给出通过测试的命令和预期干净结果。
- 按需覆盖正常路径、边界、非法输入、失败传播和回归风险。
- 优先测试真实行为；只在不可避免的边界使用 mock。
- 非行为任务给出与其风险相符的等价验证命令和预期结果。

### 测试覆盖率

- 每个行为任务内部完整执行 RED、验证 RED、GREEN、验证 GREEN、重构和再验证；禁止末尾集中补测试。
- 在任务和验收矩阵之后提供“测试与覆盖率门禁”，写明覆盖率范围、行/分支指标、阈值、命令、报告位置、成功预期和失败判定，并包含 `任务级验证`、`集成单元级验证`、`最终覆盖率与全量回归` 三个三级章节。
- 优先采用仓库或需求中的更严格阈值；均不存在时，变更业务代码行覆盖率至少 `80%`、分支覆盖率至少 `70%`，核心业务分支必须全部有行为测试。
- 逐项列出覆盖率排除对象和理由。只允许排除纯数据载体、生成访问器、纯常量、纯配置绑定、启动类、生成代码、无逻辑简单异常和标记接口。
- 不得排除含校验、转换、默认值、派生字段、状态判断、映射、回退、领域规则或自定义访问逻辑的类型，也不得排除 converter、assembler、mapper 默认方法、type handler 和本次变更行为。
- 覆盖率不足时补充有效业务测试并重新验证，禁止通过扩大排除范围刷绿。
- 仓库没有覆盖率工具时，把引入并配置工具列为实施任务；存在重大范围冲突时阻塞并询问用户。

### 执行与验证

- 通过 `pretty-executing-plan` 路由执行；底层 Superpowers 引擎在执行阶段选择，不得绕过项目包装 Skill。
- 使用足够细小的任务步骤，并将它们组织为可独立提交、审查和回滚的集成单元或有理由的原子任务组。
- 添加任务级 TDD、集成单元级质量审查与验证、最终级新鲜全量门禁。
- 将质量 Skill 标记为必需，并准确说明调用时机。
- 要求修正发现并重新运行受影响的检查。
- 使用仓库中真实有效的命令，并说明预期输出。
- 任何完成声明前都必须取得最新证据。
- 允许复用验证证据时，要求 Plan、代码、命令、依赖和环境五项指纹完全一致；最终全量门禁始终重新运行。

## 阻塞式自审

交付前，用证据回答以下所有问题：

- 每项需求是否都映射到实施和验证？
- 所有路径、符号、命令和预期结果是否真实准确？
- 每个行为变更是否依次遵循 RED、GREEN、REFACTOR？
- 所有任务之间的签名和类型是否一致？
- 计划是否明确体现项目架构和兼容性规则？
- 计划是否在功能完整的前提下选择满足当前需求的最简单实现？
- 代码示例是否命名准确、结构易读并直接表达业务意图，且没有不必要抽象、重复业务分支或技巧性写法？
- 简化是否保留必要校验、错误处理、安全、可观测性、用户明确行为和测试完整性？
- 整洁性调整是否严格限定在本次变更及其必要关联范围？
- 是否覆盖适用的调用方、契约、转换器、持久化和外部适配器？
- 所有确定性的计划生成 Skill 是否已经执行，而不是被推迟？
- 质量审查是否记录触发证据、审查范围、发现和计划修正？
- 拟议 Java 职责和类型边界是否体现 `121`、`122` 和 SOLID 审查发现？
- 是否具备任务级、集成单元级和最终质量门禁？
- 是否包含唯一集成单元与执行编排章节，且每个任务恰好归属一个集成单元？
- 顶级章节是否严格按代码优先顺序排列，任务编号、名称和全部引用是否一致？
- 需求与任务是否双向追溯，跨层矩阵是否按业务链路验收或有具体不适用理由？
- 每个单元是否具备可执行的依赖顺序、风险 Reviewer、文件所有权、独立验证和人工集成检查点？
- 原子任务组是否真的不可拆分，并说明原因？
- 并行实现是否仅用于一次性模式，且具备 worktree、文件、依赖和集成顺序隔离证据？
- 旧 Plan 是否被显式迁移、重新校验和重新批准，而不是被自动猜测？
- 计划是否没有占位符、省略号和模糊委派？
- 除允许保留的技术标识和命令外，计划自然语言是否全部为中文？
- 计划是否定义覆盖率范围、指标、阈值、命令、报告位置、成功预期和失败判定？
- 覆盖率排除项是否明确、有理由且仅限无行为代码？

任一答案为否时，修订计划。如果无法安全取得证据，应询问用户，不得降低门禁。
