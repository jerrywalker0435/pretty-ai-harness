# Java 计划质量原则

本文件是 `pretty-writing-plan` 的本地质量基线。它是可执行摘要，不复制外部文档；只保留会改变 Plan 代码提案、任务边界或测试设计的规则。

## 1. 先定义整体问题

先写清楚：

- 已批准的外部结果和不能改变的兼容合同。
- 受影响业务链路：入口、caller、callee、Adapter、持久化和外部系统。
- 业务规则的唯一归属、数据所有权、状态与不变量。
- 真实变化轴：算法、创建、适配、通知、生命周期、并发或协议。
- 验证边界：哪一层可以用快速 UT 证明，哪些属于未验证的外部能力。

不要从“应该修改哪个类”开始。类只是链路中的一个位置。

## 2. Codebase Design：设计 Deep Module

### 词汇

- **Module**：有 Interface 和 Implementation 的任意规模单元，可以是函数、类、包或跨层切片。
- **Interface**：调用方必须知道的全部内容，包括类型签名、不变量、顺序、错误、配置和性能特征。
- **Depth**：一个简单 Interface 能为调用方提供多少行为；小 Interface 隐藏复杂实现时，Module 更深。
- **Seam**：可以替换行为而不必修改调用位置的 Interface 所在处。
- **Adapter**：在 Seam 上满足 Interface 的具体实现，描述角色而不是内部复杂度。
- **Locality**：变化、缺陷、知识和验证是否集中在一个归属点。
- **Leverage**：一个 Module 的规则是否能被多个调用方和测试复用。

### 检查

1. 是否能减少 public 方法、参数和调用方必须理解的状态？
2. 是否把复杂规则藏在一个深 Module，而不是复制到多个调用方？
3. 是否让测试和生产调用穿过同一个 Interface？若测试必须穿透私有实现，Interface 可能放错位置。
4. 是否真的存在两个实现或一个现实变化轴？只有一个 Adapter 时，不为假设变化引入 Seam。
5. 依赖是否由构造器注入，而不是在规则内部 `new` 具体边界对象？
6. 纯计算是否返回结果而不是暗中修改全局状态？

删除测试或调用方能否让复杂度重新散落到多个位置，是判断抽象是否有 Leverage 的线索。

## 3. OOD、SOLID 与 Clean Code

### 对象与职责

- 每个类和方法围绕一个变化原因；避免 God Class、Feature Envy、Inappropriate Intimacy、Data Clumps 和 Shotgun Surgery。
- 隐藏可变状态；优先组合而不是继承；继承关系必须保持可替换性。
- 使用构造器注入和最小可见性；不要为测试暴露生产专用方法。
- 方法参数、返回值和异常合同要能表达不变量；集合优先返回空集合而非 `null`，是否使用 `Optional` 取决于边界语义。
- 命名表达意图；方法只在同一抽象层次做一件事；不要靠注释解释本应由代码表达的设计。

### SOLID 诊断

| 原则 | Plan 要问的问题 |
| --- | --- |
| SRP | 该 Module 是否同时因协议、业务规则、持久化和通知变化？变化原因是否能集中？ |
| OCP | 是否存在已确认的变化轴？扩展点是否比条件分支更便宜，还是会制造空泛抽象？ |
| LSP | 替代实现是否遵守相同前置条件、结果和异常合同？是否靠 `UnsupportedOperationException` 伪装继承？ |
| ISP | Interface 是否迫使调用方依赖不用的方法或状态？能否收窄调用方负担？ |
| DIP | 稳定业务规则是否依赖具体基础设施？边界依赖是否通过清晰 Seam 注入？ |

不要为了形式满足 SOLID。先证明问题会造成重复、耦合、变化扩散或测试困难。

## 4. 语义重复与全局优化

文本搜索只是线索。按以下问题判断语义重复：

- 是否对同一身份、状态、金额、权限、时间或幂等规则做了不同实现？
- 是否在多个层重复 trim、默认值、校验、映射、排序、防重或异常转换？
- 同一外部输入是否在不同入口经过不同规范化，导致调用顺序改变结果？
- 多个类是否各自拥有同一数据的写入、缓存、状态迁移或生命周期判断？
- 修改一条规则是否需要同步改多个位置？如果需要，归属可能错误。

绘制最小 caller → callee → Adapter → 外部边界关系，标出重复语义、归属候选和测试穿越的 Seam。代码写法不同但变化原因相同，仍是潜在重复；文本相似但职责和变化原因不同，不要强行合并。

全局优化只覆盖受影响链路。抽取共享 Module 前要检查 Interface 深度、调用方复杂度、迁移风险、兼容性和是否确有第二个实现；不要把局部重构扩张为全仓翻新。

## 5. 设计模式选择

模式是对已证明变化轴的命名，不是质量目标。

| 已证明的问题 | 可考虑的形状 | 先排除的误用 |
| --- | --- | --- |
| 多个算法在运行时互换 | Strategy | 仅有一个算法或只新增一个分支时不预建体系 |
| 创建过程复杂且参数多 | Builder 或静态工厂 | 简单构造不要套 Builder |
| 创建者与具体类型确实解耦 | Factory | 已知具体类型时不要 Factory everywhere |
| 需要接入不兼容外部 Interface | Adapter | 不为本方内部层层包装 |
| 行为按组合动态增加 | Decorator/组合 | 不制造难以调试的深链 |
| 多方订阅明确事件 | Observer/事件 | 不用隐式通知隐藏关键流程 |
| 多个实现共享稳定算法骨架 | Template Method 或组合 | 不为复用几行代码建立继承层次 |

Spring Bean 的构造和生命周期由容器管理时，通常不需要额外 Factory。Singleton 不是默认答案；优先构造器注入和显式依赖。

当有两个以上实质不同的 Interface 方案时，比较 Interface 复杂度、Depth、Locality、测试表面、重复收敛、迁移和失败风险；只有一个现实方案时不制造候选。

## 6. Java/Spring 设计检查

- 先确认 Java、Spring、构建和测试版本；只使用可编译的语言特性。
- Controller 负责协议转换、输入校验和响应映射；业务规则有明确归属。
- 构造器注入，稳定规则不直接创建 Gateway、Repository、Clock 或随机源。
- DTO、领域对象和持久化对象只在真实边界分离，不做逐层复制。
- 金额使用适当精度；身份、状态、单位和约束不要长期以裸 `String/int` 在链路中漂移。
- 明确事务、幂等、并发、锁、重试、分页、批量、N+1 和查询规模的影响。
- 异常保留原因与上下文，外部错误映射稳定；日志不泄露凭证、个人信息和完整敏感载荷。
- 优先不可变对象、静态工厂、Builder 或值对象，但只有在实际复杂度值得时采用。
