## 1. 全局设计优先

先定义受影响的完整链路，再决定改哪些文件：

```text
入口 → caller → callee → Adapter → 持久化/外部系统
```

必须识别：

- 已批准的业务结果、外部合同和兼容边界。
- 规则的唯一归属、数据所有权、不变量和状态迁移。
- 重复的校验、规范化、默认值、映射、异常转换、防重和生命周期判断。
- 事务、并发、幂等、重试、性能和安全边界。
- 哪些 symbol 需要一起变更，哪些可以独立交付。

“全局”止于受影响链路，不等于全仓重构。若收敛规则会改变已批准 Interface、所有权、依赖方向、业务结果或长期扩展点，返回 Design/PRD。

## 2. 质量路由优先于本地实现参考

最小事实扫描只用于判断风险和选择质量 Skill；在路由完成前，不得把旧代码风格当成方案。主 Agent 读取适用的本地最新 Skill，并把建议转成代码约束；外部 Skill 缺失时使用本文件和其他本地参考。

质量建议冲突时按以下顺序裁决：

1. 已批准 PRD/Design、外部合同和兼容性。
2. 正确性、安全性、数据一致性、事务、并发和可编译性。
3. 全局链路的规则归属、Interface、Seam、Locality 和可测试性。
4. 专项质量 Skill 建议。
5. 本地偶然风格和最小改动便利。

## 3. 契约先行、边界校验、内部信任

每个值先分类：必填、可选、可默认、外部不可信、持久化记录或已建立不变量的内部值。分类决定其类型、校验位置和失败语义。

- 在值第一次进入信任域的边界建立不变量；同一规则只校验/规范化一次。
- 进入信任域后，内部 Module 依赖已建立的契约，不重复添加不可能触发的 null、类型或 truthiness 防御。
- 必填依赖由构造器或创建边界立即拒绝；配置缺失在启动/装配边界失败。
- 可选值必须有明确的缺失语义；不要把“未找到”“数据损坏”“外部故障”都变成 `null`。
- 规范化、默认值、容错恢复和校验是四种不同动作，不能塞进一个通用 helper。
- 机器标识符、状态码、数据库键和幂等键默认拒绝 `null`、空白和首尾空格。只有批准的人工输入合同才可在外部边界规范化一次。

反例：

```java
normalizeText(record == null ? null : record.getTaskPublishId());
```

这段代码同时隐藏了“记录不存在”“字段缺失”和“空白输入”三种语义。应在正确的边界分别表达：记录必存在则抛 `NotFound`，标识由值对象建立不变量，内部调用直接使用合法值。

历史脏数据不能由通用 `normalizeText` 永久掩盖。先调查数据约束和写入方，再通过迁移、专用兼容 Adapter 或上游修复治理；临时兼容必须有范围、可观测性和移除条件。

## 4. 约定大于配置

约定大于配置的目标是缩小可变状态和决策面，不是照抄仓库中的偶然写法，也不是用隐式魔法取代契约。优先级为：

```text
已批准合同 → Java/Spring 标准约定 → 仓库稳定约定 → 真实运行时差异所需的显式配置
```

- 包结构、组件发现、构造器注入、资源命名、配置绑定和 Adapter 位置优先遵循与已批准 Design 一致的稳定约定；不为单一用例新建注册表、动态映射或自定义装配层。
- 所有环境中不变的业务规则、不变量、失败语义和数据所有权属于代码与领域契约，不做成开关、字符串模式码、SpEL 或数据库参数。
- 只有部署者确实需要在不重新构建的情况下改变的值才进入配置，例如外部端点、凭证引用、超时、配额或已批准的发布开关。不为“以后可能”增加配置。
- 相关配置用有领域语义的 `@ConfigurationProperties` 集中绑定，使用类型和 Bean Validation 建立不变量；避免散落的 `@Value` 字符串、`Map<String, Object>` 和调用时解析。
- 必填配置缺失或非法时在启动/装配边界快速失败，不在首次业务调用时才报错，不用空字符串、零或默认端点静默恢复。可选默认值必须安全、语义明确且只定义一次。
- 配置分支若实际上代表多个业务算法或责任所有者，先返回 Design 确认变化轴和 Interface，不用 `mode=1` 之类类型码隐藏设计决策。

Plan 若新增或修改配置，必须同时展示配置类型、校验、唯一消费者和完整配置内容。若稳定仓库约定与已批准合同冲突，以合同为准并返回 Design 确认偏离，不因“项目一直这样”继续错误。

## 5. 正常业务流与异常流分离

避免使用裸 `int`、`String`、`boolean` 作为跨层行为分派、成功失败或错误原因的类型码。外部状态码在 Adapter 处一次映射成领域结果或明确异常。

- 成功返回真正的领域结果；无结果时用 `void` 或合同明确的缺失类型。
- 任务不存在、状态冲突、非法输入、数据损坏和外部故障使用能表达恢复责任的异常合同。
- 不用异常控制高频正常分支、循环或普通搜索未命中。
- 不解析异常消息或数字错误码决定控制流。
- 只捕获能够恢复或映射的具体异常类型；不 catch `Exception`/`RuntimeException` 只为换名、打日志或返回 `null`、空集合、默认值、“成功”。映射边界异常时保留原始 cause 和必要上下文，编程缺陷继续传播。

有限且本身是业务事实的状态可以使用 `enum` 或值对象；避免类型码不等于消灭所有状态模型。

## 6. 领域命名与代码证据

新增或修改的类、方法、参数和变量必须优先使用 PRD/Design 中的领域词汇，表达动作、结果或规则。`execute`、`resolve`、`handle`、`do`、`action`、`deal` 等弱语义名称默认禁止；框架/第三方 Interface 合同或真实领域词汇才可例外。

调查事实时的证据顺序是：

```text
批准的合同 → 具体实现和真实调用链 → 类型/注解/SQL/Schema/配置/有效测试 → 普通注释
```

普通注释与实现冲突时，以实现作为当前行为事实，并将注释视为陈旧线索。公共 Javadoc、外部协议或批准 Design 与实现冲突时，视为合同偏差并返回上游，不能静默选择一方。

## 7. 日志是独立的可观测性设计

日志只记录对定位故障、运营状态或审计有明确价值的信息。日志所有权由“本边界是否真正消费或处置异常并终止其传播”决定，不由 Controller、Service 或 Adapter 的层级名称决定。一次失败只由一个所有者记录一次。

- HTTP 请求由把异常映射成响应的 `@ExceptionHandler`/Advice 消费并记录；只负责调用业务 Module 的 Controller 方法不拥有失败日志。
- 消息消费由最终确认、拒绝、进入死信或耗尽重试的终端边界记录；调度任务由阻止异常继续传播的终端包装记录。
- Adapter 只有在本层完成重试、降级或 fallback 并消费异常时才记录。若只是把协议异常映射为领域异常并继续抛出，只保留 cause 和必要上下文，不记录同一失败。
- catch 后继续抛出原异常或包装异常的层不拥有最终记录责任。禁止 Controller `catch RuntimeException` 后 log-and-rethrow，也禁止 Adapter “映射、记录、再抛出”后由上层重复记录。
- 未被应用代码消费的异常交给框架默认终端处理，不为了“确保有日志”增加宽泛 catch。重试尝试、状态迁移和审计是不同事件；确需记录时使用不同的稳定事件名，不伪装成第二条最终失败日志。
- 领域 Module 仅在作出重要状态迁移、恢复或审计决策时记录，不记录随后继续传播的技术异常。
- 结构化字段优先：稳定事件名、必要业务标识、外部系统、重试次数和耗时。
- 记录完整异常对象，不只记录 `getMessage()`；禁止凭证、完整载荷和敏感个人数据。
- `traceId` 等关联信息由 tracing/MDC/消息基础设施传播，不作为领域方法的独立日志参数。
- 如果字段影响幂等、审计或业务责任，它是领域数据，不得伪装成日志参数；审计要求应使用明确审计事件/记录。

若已批准 Design 同时要求 Controller catch 后记录并继续抛出、又要求 Advice 映射该异常，视为日志所有权合同冲突并返回 Design；不得用两处日志实现，也不得静默删除任一要求。

## 8. 参数、返回值和值对象

不按参数数量或分层习惯流水线创建 `Command`、`Param`、`Context`、`Request`、`Result`。只有以下情况才建立参数/值对象：

- 多个字段共同维护一个不变量。
- 它代表稳定的领域概念并跨越真实边界。
- 相同 Java 类型容易传反，且类型本身不能表达关系。
- 该合同会作为整体共同演化，且已获 PRD/Design 支持。

禁止通用返回码对象：

```java
record Result(boolean success, int code, String message, Object data) {}
```

优先使用领域结果、明确异常、`Optional`（仅表达明确的返回缺失语义）或 `void`。HTTP/消息统一响应壳只能留在协议 Adapter，不得渗透到业务 Module。

值对象的触发门槛是跨模块传播、独立不变量、类型混淆、重复校验或错误值会造成一致性/安全/不可逆副作用；不要为了消灭一次判空制造类型泛滥。

## 9. Module、Interface 与模式

- 让稳定业务规则归属于有深度的 Module：调用方知道的参数、状态和错误越少越好。
- 依赖通过构造器注入；稳定规则不在方法内部 `new` Gateway、Repository、Clock 或随机源。
- 只有真实变化轴或第二个实现存在时才引入 Seam、Factory、Strategy、Adapter 等模式。
- 优先组合、不可变状态和最小可见性；不要为了几行复用建立继承层次。
- 规则只在一个归属点实现；删除一个调用方后不应让复杂度重新散落到其他调用方。

## 10. Plan 中的代码证据

每个逻辑实现型 TASK 的代码必须让读者看出：

- public 行为入口、输入类型、输出类型和异常合同。
- 校验/规范化建立不变量的唯一边界。
- 正常流、异常流和副作用顺序。
- 真实外部协作者的最小替身及业务结果断言。
- 哪些本地重复被收敛，哪些兼容限制仍保留。
- 领域类型与 Schema 或外部协议的长度、精度、格式和可空性约束一致；不能只展示一个看似正确的类型而遗漏数据库或协议上限。

路径/symbol 表与代码块必须双向一致：每个列出的逻辑 symbol 都要展示最终完整实现或明确的文件删除；每个代码块中新建/修改的 symbol 也必须出现在表中。链路依赖的 Adapter、配置绑定、协议请求/响应、异常映射或数据写入不得只留 Interface、一句说明或“后续补充”。若 symbol 是已核实且无需修改的现有实现，可只在变更链路中引用，不放入变更表。

Plan 不执行测试、不写 RED/GREEN/覆盖率或验证命令；测试代码只是实现提案，Execution 负责最终测试实现与验证。
