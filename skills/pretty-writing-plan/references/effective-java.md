# Effective Java 设计检查清单

本文件是面向 Plan 的原创精简检查清单，不替代书籍，也不复制其原文。只在 Java 代码提案中使用与当前变更相关的条目。

## 创建与生命周期

- 用静态工厂表达有意义的创建语义；构造器简单且参数不易混淆时不要强行包装。
- 参数多、可选项多且不变量需要集中校验时考虑 Builder；否则保持最小构造 API。
- 依赖由构造器显式传入；不要隐藏在静态单例、Service Locator 或方法内部 `new` 中。
- 不要为避免一次小对象创建而牺牲可读性；只有昂贵、重复或可复用的不可变对象才考虑缓存。
- 单例不是默认的生命周期设计；Spring 默认单例也不能掩盖隐藏依赖或共享可变状态。

## 不可变性与封装

- 能不可变就不可变：状态私有、构造后不变、类不被意外扩展、输入和输出不泄露可变引用。
- 对可变输入做防御性复制，对外返回只读视图或副本；确认复制成本和线程安全含义。
- 不暴露 public 字段，不让 DTO、领域对象和持久化对象跨越不该跨越的边界。
- 优先组合而不是继承；继承会暴露父类实现和生命周期时，使用组合/委托。
- `equals`、`hashCode`、排序和身份语义必须一致；值对象要明确哪些字段构成身份。

## 类型与集合

- 面向接口使用集合和参数类型，但不要为了抽象改变调用方合同。
- 不使用 raw type；让泛型表达边界，并消除不安全转换和无依据的 `Object`。
- 用领域类型表达身份、金额、单位、状态和约束，避免 primitive obsession；确认新类型真的减少链路复杂度。
- 不返回 `null` 集合；空集合与“无值”的 Optional/结果类型按外部语义区分。
- 不以 `Optional` 作为字段、序列化载荷或所有参数的普遍包装；它应表达明确的返回缺失语义。
- 金额和精确业务计算使用适当精度类型，不能用 `double` 代替需要精确舍入的值。

## 方法、异常与资源

- 参数校验在信任边界尽早完成，异常类型和消息说明参数、状态或外部操作上下文。
- 不用异常控制普通分支；不吞异常、不捕获过宽类型、不丢失 cause。
- 选择能表达恢复责任的异常合同；不要为了少写声明而隐藏可恢复失败。
- 资源由拥有它的 Module 关闭；用 try-with-resources 或等价生命周期保证，避免在 finally 丢失原始异常。
- 不返回“成功”但留下未完成副作用；幂等、事务和重试要写进 Interface 或实现限制。

## Lambda、Stream 与并发

- Lambda 和 Stream 只在提高意图表达时使用；复杂副作用、调试和异常处理优先普通循环/方法。
- 不在 Stream 中隐藏 I/O、事务、共享可变状态或顺序依赖。
- 不共享可变状态；并发安全来自不可变数据、清晰锁/事务边界或显式并发策略。
- `parallelStream`、缓存、异步和重试都必须有真实性能/可靠性问题作为依据，并有确定性测试边界。

## Plan 证据

对每个命中的条目，在 TASK 的“质量审查”中说明：

1. 当前链路事实和风险。
2. 采用的设计如何改善封装、可变性、类型、异常或资源生命周期。
3. 哪些建议被拒绝，以及拒绝是否因为 YAGNI、兼容性、性能或可测试性。
4. 对应 UT 如何证明业务结果、边界和失败路径。

不要为了展示清单而在每个 Plan 强行引入值对象、Builder、泛型包装或模式。有效的设计是更少的调用方知识、更集中的规则和更可靠的验证。
