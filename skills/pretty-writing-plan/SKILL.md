# 编写 Java/Spring Plan

## 目标

把已批准的 PRD、Design 和真实源码转化为约束性实施合同与可审查实现提案。Plan 先给出行为任务及近完整生产/测试代码，使其既能指导 Execution，也能支持实施前人工 CR；Plan 本身不修改源码、不执行 TDD、不编排 Git。

**REQUIRED SUB-SKILL：** 完整读取并使用 `pretty-java-spring-core` 的共享合同、Plan 模板和 Java/Spring 质量检查。本 Skill 是本阶段唯一流程控制器。

## 工作流

### 1. 确认模式与输入

宣布使用 `pretty-writing-plan`。用户只要求评估、检查或 Review 时进入只读评审；要求创建或修订时进入写作模式。

写作模式读取同一标准目录下已由用户批准的 `prd.md`、`design.md`、共享合同要求的领域上下文和真实源码。缺失、未批准、含占位或互相矛盾时返回最早受影响阶段。Plan 不改变 `REQ/AC/DEC`，唯一输出为 `docs/pretty/<topic>/plan.md`，已有文件原地修订。

### 2. 执行只读评审

只接受 `docs/pretty/<topic>/plan.md`；同目录必须存在 PRD、Design，并能定位真实源码。非标准路径不接受、不迁移、不复制。

严格不修改文件、不生成 Execution、不开始实施。核对真实源码、上游合同、TASK、拟议生产/测试代码、基线、覆盖率和声明边界。依次输出并停止：阻塞问题、重要改进、代码事实与上下游偏差、执行与验证影响、`可进入 Execution / 修正后再进入 Execution`。

### 3. 核实代码事实并分流未知

读取完成变更所需的生产源码、调用方、现有测试、构建配置、仓库规则和 JaCoCo 政策，确认真实相对路径、symbol、类型、签名、依赖和命令。

- 区分已核实代码事实、上游约束和拟议实现；不虚构文件、API、命令或结果。
- Plan 不调用 `grilling`：业务结果未知返回 PRD；职责、边界、合同、所有权、一致性或决策未知返回 Design；低风险外部等价实现给出推荐提案。
- Plan 只消费领域文档，不调用 `domain-modeling`，不得更新 `CONTEXT.md`、`CONTEXT-MAP.md` 或 ADR。
- 数据库、外部服务、凭证、部署或 Reviewer 是否存在可以保持运行时未知，不阻塞 Plan。

### 4. 审查拟议实现

按共享合同路由真实命中的质量能力。对职责、依赖、契约、算法、异常、事务、SQL、安全、兼容和可测试性执行风险导向 CR。改变职责、依赖方向、所有权、事务、跨模块合同或长期扩展点时返回 Design；改变业务结果时返回 PRD。不为测试暴露生产方法，不引入无现实用途抽象。

### 5. 编写结论与代码先行的 Plan

严格使用五章模板：实施结论、实施任务、文件变更总览、测试与验证、共享约束和代码事实。事实、输入路径和证据不得先于实施结论与任务。

`TASK-001` 起连续编号，按可验证行为或独立风险垂直切分。任务标题先写可读行为名称，编号放在标题末尾，例如 `### 首次事件不进入规则（TASK-001）`。`TASK` 作为 Execution 身份保留；`REQ/AC/DEC` 只在任务末尾的一行追溯中出现。

每个行为任务按以下顺序就地展示：

1. 一句话说明可观察结果和必要实现限制。
2. 文件变更表：完整仓库相对路径、symbol、修改目的。除可执行命令外，完整仓库相对路径只出现一次；后续正文只使用 `Class#method` 或短类型名。编译、测试、搜索和覆盖率等命令为保证可复制，可以再次包含精确路径。
3. 核心生产代码：完整签名、依赖、返回值、算法、异常和关键分支。
4. 核心测试代码：主路径和高风险边界的完整测试方法。
5. 必要的机械修改、任务依赖和完成证据。
6. 最后一行简单追溯，例如 `> 追溯：REQ-001、AC-001、DEC-001。`

行为任务必须同时包含“核心生产代码”和“核心测试代码”。代码应接近可编译，不用 `...`、伪码或纯文案隐藏关键逻辑。主路径以及 SQL、事务、并发、兼容、异常等高风险分支完整展开；仅输入值不同的场景使用参数化测试或紧凑参数表。相同 fixture、builder、import、getter、Lombok、普通 DTO/映射和机械常量不重复粘贴，可用一份公共 fixture、短签名或完整机械变更表表达。

纯 DDL、配置、文档、改名或批量机械修改可以使用“完整机械变更”替代生产/测试代码对，但必须给出完整变更内容和确定性验证，不制造无价值 Java 或 UT。Plan 保持单一 `plan.md`，不创建 `.java` 草稿或代码附件，也不退化为逐文件完整候选补丁。

文件变更总览在任务之后汇总 TASK、模块和新增/修改/删除范围，不重复代码。共享约束和决定性代码事实后置，只记录影响多个任务的内容；任务专属事实放在所属任务中。

### 6. 用 `tdd` 审查测试代码提案

新增/改变行为或 Bug 修复时，**REQUIRED SUB-SKILL：** 使用 `tdd` 审查拟议测试代码质量，但 Plan 不创建测试文件、不执行 RED/GREEN、不声称 TDD 已发生。

测试代码必须让人工 Reviewer 直接看出：被测 public 行为入口、fixture、mock/fake/stub 边界、目标行为缺失时的失败原因，以及业务结果、状态变化或完整边界请求断言。不得再用 Given-When-Then、独立预期值、mock 边界、预期 RED、最小 GREEN 等六段式文案代替测试代码。只有代码无法表达的重要限制才补一句说明。

强制 UT-only：不得提议新增或扩展集成、契约、端到端、Spring slice、`@SpringBootTest`、`@WebMvcTest`、`@DataJpaTest`、Testcontainers、嵌入式数据库或本地基础设施测试。边界外协作者可以替换，被测规则使用真实对象；断言不以调用次数或顺序为主要成功标准。

### 7. 定义基线、最终验证与覆盖率

Execution 基线只包含可控的受影响模块编译、相关现有 UT、必要快速静态检查和将修改的测试入口，不默认全仓或外部环境检查。

最终验证默认包含受影响模块编译、本次全部新/改 UT、直接相关回归 UT、快速静态检查和适用覆盖率。优先继承仓库覆盖率政策；无政策时，可由 UT 覆盖的新增或实质修改 Java 行为默认行 90%、分支 80%。列出 Pretty 外未验证范围和严格声明限制。

### 8. 自审、校验并请求 Review

确认连续 TASK、任务末尾追溯、完整文件表、行为任务生产/测试代码对、机械任务完整内容、真实命令、覆盖率政策与声明限制一致；没有开头编号链、重复长路径、六段式测试文案、占位、个人路径或上游越权。运行：

```bash
python3 <pretty-java-spring-core-dir>/scripts/validate-pretty-docs.py \
  docs/pretty/<topic> --through plan
```

告知路径、任务数量、核心代码 CR 结论、测试入口、覆盖率政策和校验结果，请求一次用户 Review，然后停止。用户批准 Plan 后才可进入 Execution。

## 红线

- 不用文件名或 Design 示例冒充已核实源码。
- 不退化为只有意图和测试文案的任务清单。
- 不把 Plan 写成逐文件完整补丁或创建代码附件。
- 不按技术层横向切分 TASK。
- 不执行 RED/GREEN，不修改生产或测试文件，不改变上游合同。
- 不新增或扩展非 UT 测试。
