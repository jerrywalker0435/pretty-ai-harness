# 编写 Java/Spring Implementation Plan

本 Skill 把已批准的 PRD、Design 和真实仓库事实整理成供人审查实现质量的 `plan.md`；AI Agent 是第二读者和后续执行者。它是 Plan 的唯一编排者和最终作者；`../pretty-common/references/quality-principles.md` 是每次创建或修订都必须应用的共同质量基线，外部质量 Skill 只按事实精确路由，并将命中的原则转成代码设计约束。质量原则不作为独立评分、报告或生成后的补救审查，最终只体现在受影响链路、约束、生产代码和测试代码中。

**硬规则：先确认合同并完成全仓广度盘点；应用共享质量基线，按事实精确路由专项 Skill，设计并深读完整受影响链路；命中的原则必须直接约束代码提案，发现新风险时增量路由并重写。全仓盘点用于发现入口、消费者和注册点，不等于全仓重构或逐文件深读。只让一个类变干净、却让整条链路继续重复，不算完成。**

## 目标与边界

- 只处理 Java/Spring 新功能、Bug 修复和行为保持型重构。
- 只修改标准路径下的 `docs/pretty/<topic>/plan.md`；不修改生产代码、测试代码、PRD、Design 或项目 Git 状态。
- Plan 是实现代码提案和只读输入，不是实现动作。Execution 负责自行推导并执行编译、测试、覆盖率、静态检查和集成验证。
- Plan 保留核心生产代码和行为测试代码提案，但不写 TDD 流程、验证命令、覆盖率目标、执行结果、checkbox、状态、完成证据或结尾总结。
- 不在最终 Plan 中写外部 Skill 名称、路径、安装要求或调用过程。
- 不保留 `REQ/AC/DEC` 追溯。`TASK-001` 等编号只用于稳定的实施任务身份。
- 轻量与完整只改变分析编排和协作方式，不改变必要的受影响链路、代码级实现设计、测试设计或质量约束。
- 非轻量任务同样不得生成重复性报告；子 Agent 或外部草稿只提供中间事实，最终只提炼新增结论和证据到 `plan.md`。

## 模式与输入门禁

先根据用户意图进入一个模式：

- **创建**：新建标准路径下的 `plan.md`。
- **修订**：原地更新已有标准 `plan.md`，保留用户无关改动。
- **只读评审**：只读取并报告问题，不生成或修改 Plan。

只接受 `docs/pretty/<topic>/plan.md`，其中 `<topic>` 必须匹配 `^[a-z0-9]+(?:-[a-z0-9]+)*$`。创建或修订前必须同时满足：

1. 同一目录存在 `prd.md` 和 `design.md`。
2. 用户在当前对话中明确表示 PRD 与 Design 已批准、通过或进入 Plan。
3. 文档没有会改变业务结果、外部合同、模块 Interface、所有权、依赖方向、一致性或长期扩展点的未决问题。

文件存在、内容完整或先前评审结论不能代替用户批准。门禁不满足时停止，不创建空 Plan、不猜测路径或代码；业务结果未知返回 PRD，技术合同未知返回 Design。

## 自动编排强度

不按文件数量或代码行数判断任务大小，而按变更拓扑和风险在内部选择轻量或完整编排。用户无需手动选择；无法明确判断时按完整编排处理。编排级别及判定依据只用于内部路由，不写入最终 `plan.md`。

命中任一条件即使用**完整编排**：

- 修改 HTTP、MQ、定时任务或其他外部边界；
- 修改持久化、Schema、迁移、事务或数据一致性；
- 涉及跨模块、跨领域上下文、多个入口或多个消费者；
- 新增或改变领域术语、状态、身份、幂等或生命周期规则；
- 涉及安全、权限、并发、重试、补偿、兼容或降级；
- 存在多个独立验收路径、动态注册或不明确的实现边界。

只有单一受影响链路、单一入口/消费者且未命中上述条件时，才使用**轻量编排**。两种编排都必须完成全仓广度盘点、受影响链路深读、达到逐行可审查粒度的代码级实现设计、测试设计和基础质量/契约 Gate；轻量编排不得用摘要、伪代码或只列文件替代完整变更 symbol。轻量编排只允许减少子 Agent、Superpowers、额外只读复核、多层任务拆分和重复性产物；专项 Skill 一旦被风险触发仍必须调用。

## 强制执行顺序

严格按以下顺序工作：

1. **确认合同**：读取用户请求、已批准 PRD/Design，确认目标、非目标、外部结果和不可改变的边界。
2. **全仓广度盘点**：盘点仓库结构、Java/Spring 与构建版本、模块依赖、路由/注解入口、依赖注入注册、实现注册点、共享类型、配置、Schema、外部协议和测试位置。使用检索和拓扑事实发现入口与消费者，不要求逐文件深读；此时不要把本地实现当成设计答案。
3. **自动确定编排强度**：依据上节触发条件在内部判定轻量或完整；不确定时选择完整，不把级别或判定依据写入最终 Plan。
4. **读取质量基线并初始路由**：完整读取 `../pretty-common/references/quality-principles.md`，根据全仓盘点事实选择其中适用的原则；再加载下表中命中的精确 Skill。主 Agent 必须在设计代码前读取并应用命中的原则；存在逻辑实现型 TASK 时，优先读取 `$tdd`，只吸收其测试边界、行为断言和替身原则；`$tdd` 不可用时，生成测试代码前读取 `references/test-design.md`。使用本地最新版本，不安装、升级、锁定或注册版本。
5. **完整受影响链路**：确定入口、所有有证据的 caller/callee、Adapter、持久化/外部系统、规则唯一归属、数据所有权、依赖方向、事务/并发/幂等边界和 TASK 切分。全仓盘点的范围可以很广，但实现设计范围止于受影响链路。
6. **阅读具体实现**：深入阅读真实调用方、被调用方、Adapter、映射、异常和副作用代码，以及全仓盘点发现的共享契约和消费者；注释只作线索，不能替代实现证据。用本地代码确认兼容性、迁移路径和可落地 symbol。
7. **增量路由与生成落实**：深读中发现新的职责、类型、异常、配置、查询/命令或设计模式风险时，重新选择适用原则和专项 Skill；将其结论落实到约束、生产代码、测试代码或任务拆分中，不保留只读建议。
8. **可选草稿**：仅完整编排且存在多 TASK、跨模块、迁移或多个决策性 symbol 时，才把 `$superpowers:writing-plans` 当作草稿生成器；草稿不能直接交付，且本 Skill 规则优先。轻量编排直接生成，不生成同内容的草稿报告。
9. **契约与质量落实**：逐项回看最终代码提案是否遵守已选原则，包括边界契约、失败语义、命名、日志、参数/返回类型、查询/命令职责、规则归属、全局重复和兼容性；有问题就重写，不在 Plan 中写审查自评或重复报告。
10. **高风险复核**：仅完整编排且存在跨模块、事务/并发、数据迁移、外部高风险或多个真实方案时，最多增加一个只读复核 Agent。它只返回问题，不写最终文件；结论必须合并进 Plan，不附加重复报告。
11. **写入并校验**：只写标准 `plan.md`，运行本目录校验器；完成后停止并请求用户 Review，不执行项目验证或 Git 动作。

全程只在内部维护一份“内部合同事实集”：包含已批准的业务/技术决定、实际构建版本、数据库方言、外部协议、调用链路、可落地 symbol 和已命中的质量原则。它不是独立报告；人工 Review 所需的关键事实必须就近汇总到受影响图或 TASK，而不是另建重复产物。它用来阻止误将旧事实、探针草稿、未应用的质量建议或猜测当成合同。写入前逐项反查：Files 清单、代码块和图示必须能回指到该事实集、命中的原则或已读取的具体实现；不得自行替换版本、技术栈、数据库方言或协议。任一项无法反查或与合同冲突，返回 Design/PRD；不以“可以后续补充”或校验器通过为由继续。

本地资源按需加载，不一次性把所有参考放入上下文：

| 资源 | 读取时机 |
| --- | --- |
| `../pretty-common/references/quality-principles.md` | 每次创建/修订都必须完整读取，作为精确路由前的共同生成基线 |
| `references/test-design.md` | 出现逻辑实现型 TASK 且 `$tdd` 不可用时，在生成测试代码前读取 |
| `assets/plan.md` | 创建 Plan 或把旧 Plan 重构为当前合同时使用 |

## 精确质量路由

质量路由优先于把本地实现当作设计标准，但必须建立在全仓广度盘点和必要的受影响链路深读之后。路由不是“代码改了就加载一个通用质量 Skill”，而是根据已发现的具体风险选择最小的原则集合；命中的 Skill 是生成代码时的设计输入，不是生成后的独立评分或报告。深读发现新风险时必须增量路由。

| 事实或风险 | 精确 Skill | 允许用途 |
| --- | --- | --- |
| Interface、Seam、Depth、Locality、跨模块规则归属 | `$codebase-design` | 受影响链路和模块设计约束 |
| Java 职责、封装、重复、方法或异常合同 | `$121-java-object-oriented-design` | 职责、封装和异常设计约束 |
| primitive obsession、值对象、类型层级、签名混淆 | `$122-java-type-design` | 类型和签名设计约束 |
| 只需聚焦某一个 SOLID 原则 | `$solid-principles` | 对应原则的设计约束；避免与 121 重复加载 |
| 已证明存在多个真实实现或变化轴 | `$design-patterns` | 模式取舍和扩展点设计约束 |
| 已由具体 symbol 证实的弱语义命名、方法粒度或可读性风险 | `$clean-code` | 只读生成约束；不作为通用质量门禁 |
| 逻辑行为、测试 seam、行为断言或边界替身 | `$tdd` | 优先测试设计约束；不把 TDD 流程复制到 Plan |
| 多 TASK、跨模块或迁移型 Plan 的草稿骨架 | `$superpowers:writing-plans` | 草稿生成，不得直接交付 |

路由表只定义专项选择；共享质量基线始终适用，再只选最小非重叠专项集合，通常为一个主路由加一个专项路由，不为“覆盖全面”批量加载。`$121-java-object-oriented-design` 与 `$solid-principles` 二选一；`$design-patterns` 只在已证明变化轴时加载；`$clean-code` 只在具体命名/方法结构风险已被事实证实时加载，不能代替共同质量基线；逻辑实现型 TASK 优先使用 `$tdd`，仅在 `$tdd` 不可用时读取 `references/test-design.md`。命中 Skill 的原则必须在生成代码前转成类职责、方法签名、异常合同、数据类型、测试行为或任务拆分；新风险在后续深读中出现时增量路由，不预加载。

调用 `$superpowers:writing-plans` 时只吸收其文件职责、任务切分、完整代码/无占位符和类型一致性草稿。本 Skill 中用户已确认的输出合同显式覆盖它的默认路径、Goal/Architecture/Tech Stack 头部、checkbox、TDD 步骤、验证命令、commit 步骤和执行交接。主 Agent 必须依本 Skill 模板重组草稿，再执行合同事实逐项反查和校验；不得把外部 Skill 的“必须”字段复制到最终 Plan。

不在 Plan 阶段调用 `$clean-code-guard`、`$java-code-review` 或 `$springboot-tdd`：它们的工作流要求已实现代码、项目验证或集成测试，与本 Skill 的只读 Plan 边界不匹配。事务、并发、日志和契约快速失败暂由本地质量基线转成代码设计约束。

命中的外部 Skill 不可用时，不得放弃该风险；使用共享质量基线中对应的原则和可用参考完成同一设计约束。最终 Plan 不写 Skill 名称、路径或调用过程。

冲突按以下顺序裁决：

1. 已批准 PRD/Design、外部合同和兼容性。
2. 正确性、安全性、数据一致性、事务、并发和可编译性。
3. 受影响完整链路的规则归属、Interface、Seam、Locality 和可测试性。
4. 命中的专项质量 Skill 建议。
5. 本地实现风格和最小改动便利。

冲突若会改变已批准业务结果、Interface、所有权、依赖方向或长期扩展点，返回上游 Design/PRD，不在 Plan 中静默取舍。

## 质量与契约约束

本节只规定共享质量原则如何落实到 Plan，不重复抄写基线、路由表或生成独立检查报告。质量路由的作用是在代码提案形成前决定应遵守哪些原则，而不是在代码生成后给出一个脱离修改的结论。

主 Agent 必须把适用原则落实到受影响图、生产代码、测试代码和限制条件中，至少处理：受影响链路、边界契约与失败语义、查询与命令职责分离、参数只作为输入、规则唯一归属、依赖方向、日志所有权、类型/Schema/协议一致性、兼容边界和全局重复。命中的专项 Skill 不能只读取不采纳；其结论必须改变或确认具体的类职责、方法、类型、异常、测试或任务切分。机械校验器只负责结构和高确定性问题，不能替代原则驱动的代码设计；不能从局部代码推断的链路、所有权、迁移或合同事实必须写入就近的图或 TASK，不能用空泛结论或另一个重复报告代替。

## Plan 文档合同

Plan 只写入 `docs/pretty/<topic>/plan.md`。最终文档只保留标题、按需的受影响图和实施任务，不重复 PRD/Design 的 Goal、Architecture、Tech Stack，也不写质量自评、重复性报告、执行状态或结尾总结。

```markdown
# <主题> Implementation Plan

## 实施任务

### TASK-001：<领域结果或独立风险>
```

### 变更链路

只在调用关系、交互顺序或状态迁移值得可视化时保留本节；简单任务可以省略。按需选择 Mermaid `flowchart`、`sequenceDiagram` 或 `stateDiagram-v2`，一个代码块只表达一张图。使用独立的小写 `mermaid` fenced block、ASCII 节点 ID 和带引号的展示文本，例如 `A["创建工单"]`；避免 IDEA 不兼容的主题指令、外部脚本、`click` 和非必要扩展。图表达全局受影响链路，不展示整个仓库；图中无法表达的不可改变边界、异常或不变量，写入对应 TASK 的约束。

### 实施任务

任务按可观察领域结果或独立风险垂直切分，不按 Controller/Service/Repository 层切分，也不按 commit 大小切分。任务标题以 `TASK-001` 开头并用一句话表达目标结果，不显示内部任务类型。

内部仅区分两种模板：

- **逻辑实现型**：改变控制流、领域规则、异常、副作用或行为；必须展示完整变更 symbol 的生产代码和核心测试代码。
- **声明/结构变更型**：DDL、配置、资源、文档、文件移动或确定性改名；展示完整变更内容和受影响路径，不伪造 Java/测试代码。

每个 TASK 按需包含以下内容，并按此顺序组织：

1. **约束**：只有存在不可改变的边界时才写，并放在 TASK 最前面。
2. **Files**：用 Superpowers 风格列出实际相对路径，只写 `Create`、`Modify` 或 `Test` 等有内容的项；不使用路径/symbol/修改目的表。
3. **修改**：逻辑实现型任务展示受影响的完整生产 symbol；声明/结构变更型任务展示完整变更内容。
4. **测试**：逻辑实现型任务展示公共行为入口、真实输入/fixture、必要边界替身和业务结果/状态/完整边界请求断言；没有适用测试时省略，不伪造测试代码。
5. **依赖**：仅在依赖关系确实影响任务顺序时填写。

代码提案使用代码块直接放在对应 TASK 下，不复制整个文件、不使用行号或占位描述。方法、字段和测试类名可以在代码块附近说明，但不另建定位表。

### 代码证据

逻辑实现型 TASK 的代码提案必须让人看出：

- public 行为入口、输入类型、输出类型和异常合同；
- 校验/规范化建立不变量的唯一边界；
- 正常流、异常流和副作用顺序；
- 真实外部协作者的最小替身及业务结果断言；
- 哪些本地重复被收敛，哪些兼容限制仍保留；
- 领域类型与 Schema 或外部协议的长度、精度、格式和可空性约束一致。

受影响图和 TASK 中的关键事实应能回指到具体实现、类型、配置、SQL/Schema、协议或有效测试，不以普通注释或单独的重复报告代替。Files 清单与代码块必须一致；链路依赖的 Adapter、配置绑定、协议请求/响应、异常映射或数据写入不得只留 Interface、一句说明或“后续补充”。具体 symbol 可以在代码块附近说明，但不另建路径/symbol/修改目的表。

新增或修改配置时，同时展示配置类型、校验、唯一消费者和完整配置内容；声明/结构变更型 TASK 给出完整变更内容和不变量，不伪造测试或执行步骤。

同一 TASK 若不可分割地混合逻辑与声明/结构变更，按逻辑实现型处理并展示配套声明变更。

Plan 不写 `#### 质量审查`、`#### TDD 与验证设计`、RED/GREEN/REFACTOR、checkbox、完成证据、验证命令、覆盖率、执行结果或结尾总结。不得使用 `TODO`、`TBD`、`FIXME`、伪代码、未解析路径、行号范围或 `...` 隐藏实现；不写“类似上一个任务”。

### 测试代码的边界

测试代码是实现提案的一部分，用来固定 public 行为和关键结果。存在逻辑实现型 TASK 时，优先读取并应用 `$tdd` 的测试 seam、行为断言和边界替身原则；`$tdd` 不可用时，读取并应用 `references/test-design.md`。Plan 不规定 TDD 流程、测试命令、覆盖率或最终测试质量。Execution 负责根据 PRD、Design、Plan 和仓库事实补充、调整、运行测试及覆盖率。声明/结构变更型任务不因格式要求伪造测试。

## 只读评审与交付

只读评审只报告阻塞问题、实现事实与合同偏差、链路/代码风险和需要返回上游的决策；不创建下游 Plan。创建或修订完成后只交付 Plan 路径和内容，请用户 Review；不得自动实现、执行项目验证或运行 Git 命令。
