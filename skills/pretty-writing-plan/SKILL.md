# 编写 Java/Spring Implementation Plan

本 Skill 把已批准的 PRD、Design 和真实仓库事实整理成供人工审查 AI 实现的 `plan.md`。它是 Plan 的唯一编排者和最终作者；外部质量 Skill 只提供按场景加载的顾问意见，本 Skill 的本地硬约束负责最终裁决。所有分析结果只汇总进这一个 Plan，不另产相同内容的扫描、质量或评审报告。

**硬规则：先确认合同，完成全仓广度盘点；再自动确定编排强度、路由质量规则、设计并深读完整受影响链路；代码提案必须通过契约 Gate。全仓盘点用于发现入口、消费者和注册点，不等于全仓重构或逐文件深读。只让一个类变干净、却让整条链路继续重复，不算完成。**

## 目标与边界

- 只处理 Java/Spring 新功能、Bug 修复和行为保持型重构。
- 只修改标准路径下的 `docs/pretty/<topic>/plan.md`；不修改生产代码、测试代码、PRD、Design 或项目 Git 状态。
- Plan 是实现代码提案和只读输入，不是实现动作。Execution 负责自行推导并执行编译、测试、覆盖率、静态检查和集成验证。
- Plan 保留核心生产代码和行为测试代码，但不写 TDD 流程、验证命令、覆盖率目标、执行结果、checkbox、状态或完成证据。
- 不在最终 Plan 中写外部 Skill 名称、路径、安装要求或调用过程。
- 不保留 `REQ/AC/DEC` 追溯。`TASK-001` 等编号只用于稳定的实施任务身份。
- 轻量与完整只改变分析编排和协作方式，不改变全仓盘点、完整受影响链路、代码级实现设计、测试设计或质量 Gate。
- 非轻量任务同样不得生成重复性报告；子 Agent 或外部草稿只提供中间事实，最终只提炼新增结论和证据到 `plan.md`。

## 模式与输入门禁

先根据用户意图进入一个模式：

- **创建**：新建标准路径下的 `plan.md`。
- **修订**：原地更新已有标准 `plan.md`，保留用户无关改动。
- **只读评审**：只读取并报告问题，不生成或修改 Plan。

只接受 `docs/pretty/<topic>/plan.md`，其中 `<topic>` 必须匹配 `^[a-z0-9]+(?:-[a-z0-9]+)*$`。创建或修订前必须同时满足：

1. 同一目录存在 `prd.md` 和 `design.md`。
2. 用户在当前对话中明确表示 PRD 与 Design 已批准、通过或进入 Plan。
3. 文档没有会改变业务结果、外部合同、模块 Interface、所有权、依赖方向、一致性或长期扩展点的未决问题。

文件存在、内容完整或先前评审结论不能代替用户批准。门禁不满足时停止，不创建空 Plan、不猜测路径或代码；业务结果未知返回 PRD，技术合同未知返回 Design。

## 自动编排强度

不按文件数量或代码行数判断任务大小，而按变更拓扑和风险自动选择编排强度。用户无需手动选择；无法明确判断时按完整编排处理。最终 `plan.md` 在标题后记录两行元信息：

```markdown
编排级别：轻量
判定依据：单一受影响链路；未命中复杂任务触发条件
```

命中任一条件即使用**完整编排**：

- 修改 HTTP、MQ、定时任务或其他外部边界；
- 修改持久化、Schema、迁移、事务或数据一致性；
- 涉及跨模块、跨领域上下文、多个入口或多个消费者；
- 新增或改变领域术语、状态、身份、幂等或生命周期规则；
- 涉及安全、权限、并发、重试、补偿、兼容或降级；
- 存在多个独立验收路径、动态注册或不明确的实现边界。

只有单一受影响链路、单一入口/消费者且未命中上述条件时，才使用**轻量编排**。两种编排都必须完成全仓广度盘点、受影响链路深读、达到逐行可审查粒度的代码级实现设计、测试设计和基础质量/契约 Gate；轻量编排不得用摘要、伪代码或只列文件替代完整变更 symbol。轻量编排只允许减少子 Agent、Superpowers、额外只读复核、多层任务拆分和重复性产物；专项 Skill 一旦被风险触发仍必须调用。

## 强制执行顺序

严格按以下顺序工作：

1. **确认合同**：读取用户请求、已批准 PRD/Design，确认目标、非目标、外部结果和不可改变的边界。
2. **全仓广度盘点**：盘点仓库结构、Java/Spring 与构建版本、模块依赖、路由/注解入口、依赖注入注册、实现注册点、共享类型、配置、Schema、外部协议和测试位置。使用检索和拓扑事实发现入口与消费者，不要求逐文件深读；此时不要把本地实现当成设计答案。
3. **自动确定编排强度**：依据上节触发条件判定轻量或完整，并把级别与具体依据写入最终 Plan；不确定时选择完整。
4. **质量路由**：根据全仓盘点事实加载下表中适用的精确 Skill；主 Agent 先读取并应用，缺失时退回本地质量基线。使用本地最新版本，不安装、升级、锁定或注册版本。
5. **完整受影响链路**：确定入口、所有有证据的 caller/callee、Adapter、持久化/外部系统、规则唯一归属、数据所有权、依赖方向、事务/并发/幂等边界和 TASK 切分。全仓盘点的范围可以很广，但实现设计范围止于受影响链路。
6. **阅读具体实现**：深入阅读真实调用方、被调用方、Adapter、映射、异常和副作用代码，以及全仓盘点发现的共享契约和消费者；注释只作线索，不能替代实现证据。用本地代码确认兼容性、迁移路径和可落地 symbol。
7. **可选草稿**：仅完整编排且存在多 TASK、跨模块、迁移或多个决策性 symbol 时，才把 `$superpowers:writing-plans` 当作草稿生成器；草稿不能直接交付，且本 Skill 规则优先。轻量编排直接生成，不生成同内容的草稿报告。
8. **契约与语义 Gate**：审查最终代码提案的边界契约、失败语义、命名、日志、参数/返回类型、查询/命令职责、参数输入语义、全局重复和兼容性；有问题就重写，不在 Plan 中写审查自评或重复报告。
9. **高风险复核**：仅完整编排且存在跨模块、事务/并发、数据迁移、外部高风险或多个真实方案时，最多增加一个只读复核 Agent。它只返回问题，不写最终文件；结论必须合并进 Plan，不附加重复报告。
10. **写入并校验**：只写标准 `plan.md`，运行本目录校验器；完成后停止并请求用户 Review，不执行项目验证或 Git 动作。

全程只在内部维护一份“内部合同事实集”：包含已批准的业务/技术决定、实际构建版本、数据库方言、外部协议、调用链路和可落地 symbol。它不是独立报告；人工 Review 所需的关键事实必须就近汇总到 `变更链路` 或 TASK，而不是另建重复产物。它用来阻止误将旧事实、探针草稿或猜测当成合同。写入前逐项反查：路径/symbol 表与代码块必须能回指到该事实集或已读取的具体实现；不得自行替换版本、技术栈、数据库方言或协议。任一项无法反查或与合同冲突，返回 Design/PRD；不以“可以后续补充”或校验器通过为由继续。

本地资源按需加载，不一次性把所有参考放入上下文：

| 资源 | 读取时机 |
| --- | --- |
| `references/quality-principles.md` | 创建/修订时在质量路由后读取，作为本地硬 Gate |
| `references/test-design.md` | 出现逻辑实现型 TASK 时读取 |
| `references/effective-java.md` | 相关 Java 质量 Skill 缺失且命中对应风险时读取 |
| `assets/plan.md` | 创建 Plan 或把旧 Plan 重构为当前合同时使用 |

## 精确质量路由

质量路由优先于把本地实现当作设计标准，但必须建立在全仓广度盘点和必要的受影响链路深读之后。路由 Skill 是顾问，不是并列作者；主 Agent 按本地优先级裁决冲突。

| 事实或风险 | 精确 Skill | 允许用途 |
| --- | --- | --- |
| Interface、Seam、Depth、Locality、跨模块规则归属 | `$codebase-design` | 全局模块与链路设计 |
| Java 职责、封装、重复、方法或异常合同 | `$121-java-object-oriented-design` | 只读 OOD 诊断 |
| primitive obsession、值对象、类型层级、签名混淆 | `$122-java-type-design` | 只读类型设计诊断 |
| 只需聚焦某一个 SOLID 原则 | `$solid-principles` | 聚焦审查；避免与 121 重复加载 |
| 已证明存在多个真实实现或变化轴 | `$design-patterns` | 比较模式是否真正需要 |
| 新增或修改的弱语义命名、方法粒度和可读性 | `$clean-code` | 只读命名/结构建议 |
| 多 TASK、跨模块或迁移型 Plan 的草稿骨架 | `$superpowers:writing-plans` | 草稿生成，不得直接交付 |

每次只选最小非重叠集合，通常为一个主路由加一个专项路由，不为“覆盖全面”批量加载。`$121-java-object-oriented-design` 与 `$solid-principles` 二选一；`$design-patterns` 只在已证明变化轴时加载；`$clean-code` 只处理本地 Gate 后仍存在的命名/结构风险。新风险在后续深读中出现时才增量路由，不预加载。

调用 `$superpowers:writing-plans` 时只吸收其文件职责、任务切分、完整代码/无占位符和类型一致性草稿。本 Skill 中用户已确认的输出合同显式覆盖它的默认路径、Goal/Architecture/Tech Stack 头部、checkbox、TDD 步骤、验证命令、commit 步骤和执行交接。主 Agent 必须依本 Skill 模板重组草稿，再执行合同事实逐项反查和校验；不得把外部 Skill 的“必须”字段复制到最终 Plan。

不在 Plan 阶段调用 `$clean-code-guard`、`$java-code-review` 或 `$springboot-tdd`：它们的工作流要求已实现代码、项目验证或集成测试，与本 Skill 的只读 Plan 边界不匹配。事务、并发、日志和契约快速失败暂由本地硬 Gate 负责。

外部 Skill 缺失时降级到 `references/quality-principles.md` 和按需的本地参考；交付说明可以告知降级，但最终 Plan 不写 Skill 名称。

冲突按以下顺序裁决：

1. 已批准 PRD/Design、外部合同和兼容性。
2. 正确性、安全性、数据一致性、事务、并发和可编译性。
3. 受影响完整链路的规则归属、Interface、Seam、Locality 和可测试性。
4. 命中的专项质量 Skill 建议。
5. 本地实现风格和最小改动便利。

冲突若会改变已批准业务结果、Interface、所有权、依赖方向或长期扩展点，返回上游 Design/PRD，不在 Plan 中静默取舍。

## 质量与契约 Gate

创建或修订时必须读取 `references/quality-principles.md`。该文件是 Plan 代码设计与生成质量原则的唯一详细定义；本节不重复抄写规则。Gate 的意义是阻止低质量、不可编译、契约不清或链路不完整的代码提案进入人工 Review，不是生成一份质量自评报告。

主 Agent 必须把原则落实到 `变更链路`、生产代码、测试代码和限制条件中，至少确认：完整受影响链路、边界契约与失败语义、查询与命令职责分离、参数只作为输入、规则唯一归属、依赖方向、日志所有权、类型/Schema/协议一致性、兼容边界和全局重复是否处理。机械校验器只负责结构和高确定性问题；不能从局部代码推断的链路、所有权、迁移或合同事实必须写入就近的链路关系表或 TASK，不能用空泛结论或另一个重复报告代替。

## Plan 文档合同

Plan 只写入 `docs/pretty/<topic>/plan.md`。最终文档只保留标题、编排级别元信息、完整变更链路和实施任务，不重复 PRD/Design 的 Goal、Architecture、Tech Stack，也不写质量自评、重复性报告或执行状态。

```markdown
# <主题> Implementation Plan

编排级别：轻量
判定依据：单一受影响链路；未命中复杂任务触发条件

## 变更链路

## 实施任务

### <领域结果或独立风险>（TASK-001）
```

### 变更链路

所有代码变更和影响行为/边界的声明变更都必须保留本节；单模块任务也至少给出完整受影响链路的一行摘要和关系表。用一行箭头链作摘要，用关系表作权威合同；图示或 Mermaid 只能是可选辅助，不能成为唯一事实来源。关系表记录会影响实现的入口、caller/callee、跨边界类型与转换、规则/数据归属、事务/并发/幂等/副作用边界、异常传播、关键证据和对应 TASK。全仓盘点用于发现链路，不把无关模块塞进实现范围。不要复述 Design 或写 Skill 名称。

### 实施任务

任务按可观察领域结果或独立风险垂直切分，不按 Controller/Service/Repository 层切分，也不按 commit 大小切分。任务标题只使用领域词汇和 `TASK-001` 编号，不显示内部任务类型。

内部仅区分两种模板：

- **逻辑实现型**：改变控制流、领域规则、异常、副作用或行为；必须展示完整变更 symbol 的生产代码和核心测试代码。
- **声明/结构变更型**：DDL、配置、资源、文档、文件移动或确定性改名；展示完整变更内容和受影响路径，不伪造 Java/测试代码。

每个逻辑实现型 TASK 必须包含：

1. 可观察结果、不可改变合同和实现限制。
2. 仓库相对路径、稳定 symbol 和修改目的表；不使用行号。
3. 接近可编译的核心生产代码：完整变更 symbol、签名、依赖、返回值、异常和高风险分支。
4. 核心测试代码：public 行为入口、真实输入/fixture、必要边界替身和业务结果/状态/完整边界请求断言。
5. 非显然的静态任务依赖（仅在需要时填写）。不填写完成证据、验证命令或状态。

声明/结构变更型 TASK 必须给出完整变更内容、受影响路径和不变量；不伪造测试或执行步骤。同一 TASK 若不可分割地混合两类内容，按逻辑实现型处理并展示配套声明变更。

Plan 不写 `#### 质量审查`、`#### TDD 与验证设计`、RED/GREEN/REFACTOR、checkbox、完成证据、验证命令、覆盖率或执行结果。不得使用 `TODO`、`TBD`、`FIXME`、伪代码、未解析路径、行号范围或 `...` 隐藏实现；不写“类似上一个任务”。

### 测试代码的边界

测试代码是实现提案的一部分，用来固定 public 行为和关键结果；Plan 不规定 TDD 流程、测试命令、覆盖率或最终测试质量。Execution 负责根据 PRD、Design、Plan 和仓库事实补充、调整、运行测试及覆盖率。声明/结构变更型任务不因格式要求伪造测试。

## 只读评审与交付

只读评审只报告阻塞问题、实现事实与合同偏差、链路/代码风险和需要返回上游的决策；不创建下游 Plan。创建或修订完成后只交付 Plan 路径和内容，请用户 Review；不得自动实现、执行项目验证或运行 Git 命令。

生成后运行：

```bash
python3 <pretty-writing-plan>/scripts/validate_plan.py docs/pretty/<topic>/plan.md
```

`<pretty-writing-plan>` 只允许出现在这条 Skill 内部说明中，不能进入生成的 Plan。校验器不替代语义 Gate，也不运行编译、测试或覆盖率。
