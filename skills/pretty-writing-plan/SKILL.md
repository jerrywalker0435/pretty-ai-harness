# 编写高质量实施计划

## 概述

产出可执行的实施计划，并把实施任务组织成可独立提交、Review、批准和当前分支集成的集成单元。确保设计、代码示例、测试、执行编排和交接通过明确门禁。计划质量与实施质量是两个相互独立且都必须通过的阶段。

**核心实现原则：** 在完整覆盖全部功能需求、边界行为和非功能约束的前提下，优先采用满足当前需求的最简单实现。代码必须命名准确、意图清晰、结构易读并直接表达业务规则；功能正确或测试通过不能替代简洁性、可读性和业务表达力审查。简洁不得以删减校验、错误处理、安全措施、可观测性或用户明确要求的行为为代价。

**必需子 Skill：** 使用 `superpowers:writing-plans` 提供基础计划格式和任务粒度。

## 工作流

### 1. 校验输入

Plan 必须以已批准且通过门禁的 Design 为输入；缺少 Design、Design 未批准或仍有阻塞项时停止并路由到 `pretty-writing-design`。Plan 不得补写或改变需求与设计。

### 2. 加载约束上下文

宣布："我正在使用 pretty-writing-plan Skill 编写并质量校验实施计划。"

如果仓库包含 `.trellis/`，起草前**必须使用子 Skill：** `before-dev`。读取适用的项目规范，并在每个代码示例和验证步骤中保留这些约束。

只检查足以确定准确文件、既有惯例、调用方、契约和测试命令的代码。时间压力不能成为虚构路径或 API 的理由。

明确限制探索范围：

1. 为入口、应用流程、领域端口、适配器、持久化、契约和测试编写证据清单。
2. 条件允许时，并行搜索相互独立的清单项。
3. 完成一轮仓库结构扫描和一轮定向依赖扫描后，停止宽泛探索。
4. 清单闭环后立即起草计划，不要继续浏览可有可无的上下文。
5. 如果关键清单项仍未知，向用户提出一个聚焦问题；不得无限探索或输出占位内容。

### 3. 选择并执行计划生成质量 Skill

始终使用 `superpowers:writing-plans`，并在起草前完整读取 [references/quality-gates.md](references/quality-gates.md) 的“Skill 选择”映射。建立“证据到 Skill”审计：当前阶段实际读取并应用所有被触发的计划生成 Skill；只用于实施的 Skill 则写入对应执行门禁。不得推测性加载、弱化确定性触发条件或在必需能力缺失时静默继续。

对于每个被触发的计划生成 Skill：

1. 在起草代码示例前完整读取其 `SKILL.md`。
2. 使用其审查清单检查拟议文件、职责、签名、类型、空值/错误行为和依赖方向。
3. 记录具体发现，包括“无发现”，并说明每项发现如何改变计划。
4. 修正后重新执行相关审查，直到不存在阻塞性发现。

起草前宣布触发了哪些计划生成质量 Skill 及其原因。计划生成 Skill 与实施阶段 Skill 必须明确区分。

### 4. 起草计划

严格遵循 `superpowers:writing-plans`，包括准确路径、细粒度复选步骤、代码变更步骤的完整代码、测试先行顺序、准确命令、预期结果，以及禁止占位内容。

覆盖 `superpowers:writing-plans` 的英文文档模板：计划标题、章节、任务名、步骤说明、正文、预期结果和执行交接必须使用中文。代码标识、类名、方法名、文件路径、命令、技术名称、Skill 名称和协议字段允许保留英文。业务代码示例中的分步注释必须遵循项目中文注释规范。Git 提交信息沿用仓库既有格式。

禁止残留 `Implementation Plan`、`Goal`、`Architecture`、`Tech Stack`、`Task`、`Files`、`Step`、`Run`、`Expected` 等英文模板标签。机械校验只检查结构化标签，语义审查还必须拒绝成段英文自然语言说明。

编写任何实施代码块前，必须根据仓库证据核实所属文件、导入、类型、签名和被调用 API。用户只提供文件名而没有源码内容，不足以支撑完整代码。如果无法推导准确代码，必须阻塞并提出一个聚焦问题；不得把猜测代码包装成看似可执行的计划。

起草前评估范围。如果计划跨越相互独立的子系统，完整代码会使单份计划不切实际，应按 `superpowers:writing-plans` 的要求拆分为可独立执行的子计划。不得为了维持一份过大的文档而削弱代码完整性。

对于机械性重复，仅当完整变更表逐项列出每个文件、符号、字段、映射和预期结果时，才可以用它替代重复代码。必需实施内容中禁止使用省略号、“类似修改”、`TODO` 或伪代码。

Plan 的顶级章节必须按以下唯一顺序组织，让用户先 Review 具体实现，再检查业务闭环、工程门禁和生成过程：

```text
## 输入、目标与边界
## 具体实施任务
## 集成单元与执行编排
## 需求到任务追溯
## 跨层验收矩阵
## 代码实现质量门禁
## 测试与覆盖率门禁
## 计划生成质量审查
## 执行交接说明
```

标题后的 Agent 执行要求不计入顶级章节。不得调换、重复或插入同级旁路章节；需要细分时使用三级标题。

### 4.1 先写可独立 Review 的实施任务

每个任务标题使用 `### 任务<连续正整数>-<中文动宾短语>`，例如 `### 任务3-实现全量稳定排序候选查询与锁定目标刷新`。`任务<n>` 是稳定主键，名称不得包含 Markdown、路径、命令、完成状态或换行；批准前改名必须同步全部引用，批准后 Plan 只读。

任务必须自包含任务类型、准确文件、完整失败测试、RED 命令与预期、最小实现、GREEN 命令与预期、重构动作和再验证。非行为任务改为记录带理由的任务类型、等价验证命令与预期。用户不应跳到文档后部才能理解当前任务如何实现和验证。

### 4.2 再定义集成、追溯与跨层验收

全部任务之后添加唯一的 `## 集成单元与执行编排`。每个集成单元的 `包含任务` 使用嵌套列表，一行一个反引号包裹的完整任务标识；名称必须与任务标题完全一致。任务恰好归属一个单元，单元依赖仍使用 `U<n>`。

`需求到任务追溯` 必须双向闭环：每条需求或非功能约束至少映射一个任务，每个任务也必须有明确需求或交付保障来源。`跨层验收矩阵` 按端到端业务链路组织，并引用完整任务标识；单层任务保留该章节并写基于文件和调用链证据的 `不适用（<理由>）`，不得留空或使用泛化结论。

### 4.3 最后记录全局门禁与生成审计

`代码实现质量门禁` 是当前 Plan 已完成的代码方案 Review 记录，不是未来提醒。使用表格逐项记录功能完整性、简洁性与必要性、可读性与业务表达、测试完整性保护和变更范围控制的具体结论，并关联完整任务标识。不得只复制原则性结论或夹带无关重构。

`测试与覆盖率门禁` 统一容纳覆盖率合同以及 `任务级验证`、`集成单元级验证`、`最终覆盖率与全量回归` 三个三级章节，不再创建独立的顶级最终回归门禁。任务级局部步骤留在任务正文，这里只记录跨任务统一口径。

`计划生成质量审查` 放在倒数第二，包含 `实际使用的计划生成 Skill`、`质量发现与计划修正` 和 `最终审查结论`。只声明本轮实际读取并应用的 Skill，删除无信息量的“未使用候选 Skill”清单。`执行交接说明` 严格置底，只记录权威 Plan 路径、校验状态、未决项和用户下一步选择，不重复任务、矩阵或门禁。

严格按 [references/quality-gates.md](references/quality-gates.md) 的固定合同生成全部字段。集成检查点必须表达“隔离 worktree 候选提交 -> Review -> 应用未暂存差异 -> 当前分支提交批准 -> 当前分支本地提交”，不得生成 `git merge --ff-only` 作为当前分支集成动作。旧格式 Plan 不做双格式兼容；必须显式迁移、重新校验并获得人工批准，执行器不得猜测名称或补齐引用。

### 5. 注入执行质量门禁

每份计划都必须要求使用项目执行包装 Skill 和实施质量 Skill。在计划头部加入以下要求：

```markdown
> **Agent 执行要求：** REQUIRED SUB-SKILL: 使用
> `pretty-executing-plan` 逐项执行本计划并维护执行报告。
>
> **必需实施质量：** 每个行为变更使用
> `superpowers:test-driven-development`；每个集成单元结束后使用
> `clean-code-guard`。适用跨层工作时使用 `check-cross-layer`。
> 声明完成前使用 `superpowers:verification-before-completion`
> 和仓库最终质量工作流。
```

按质量门禁注入任务级 TDD、集成单元级质量与 Reviewer、最终级新鲜全量验证；适用时加入 `check-cross-layer`、语言专项审查和 `improve-ut`。发现必须修正并复验，不能只记录。

### 5.1 注入测试与覆盖率门禁

任务类型、局部 TDD 与非行为等价验证直接沿用 4.1 的任务合同，不在后置章节重复。在任务和验收矩阵之后增加 `## 测试与覆盖率门禁`，明确范围、指标、阈值、排除项、真实命令、报告位置、成败判定和三级验证。

仓库没有覆盖率工具时，计划必须加入覆盖率基础设施任务，并同步写出真实命令和阈值。若引入工具会造成重大范围扩张或违反仓库约束，停止输出并询问用户，不得虚构命令或降级为人工检查。

覆盖率不能替代 TDD。最终覆盖率与全量回归只作为该章节的三级标题；覆盖不足时补充有效业务测试，不得扩大排除或弱化断言。

### 6. 发布唯一中文 Plan

唯一权威 Plan 写入：

```text
docs/pretty/<topic>/YYYY-MM-DD-<topic>-plan.md
```

`<topic>` 必须沿用已批准 Design 的小写 kebab-case 主题，目录名必须与文件名中的 `<topic>` 完全一致。日期使用 Plan 首次创建日期，后续修订不得改名。不得沿用 `superpowers:writing-plans` 的默认 `docs/superpowers/plans/` 路径，也不得省略 `-plan.md` 后缀。

同一主题已有权威 Plan 时更新原文件，不创建第二份。只有独立交付单元确实不同且已经单独批准时，才能使用新的主题目录。

### 7. 计划通过前阻止交付

运行：

```bash
bash <skill-dir>/scripts/validate-plan.sh <plan-file>
```

然后执行 [references/quality-gates.md](references/quality-gates.md) 中的语义审查。脚本只能检查机械契约，不能批准架构或代码质量。

任一门禁失败时，修正计划并重新运行。不得交付未通过的计划。如果失败依赖尚未解决的用户决策，停止并提出一个聚焦问题。

### 8. 交接执行

请求用户复审计划并停止。用户后续要求执行时，将其作为独立请求交由 `pretty-executing-plan`；不得直接调用底层 `superpowers:subagent-driven-development` 或 `superpowers:executing-plans` 绕过执行质量包装。默认告知用户将逐个集成单元停在 Review 检查点，也可以自然语言要求一次性执行。提醒执行者集成单元、质量 Skill、TDD 顺序、覆盖率合同、执行报告和复验规则都是验收标准，而非可选阅读。

## 危险信号

- 绕过本包装 Skill、已批准 Design 或 `pretty-executing-plan`。
- 已触发的生成 Skill 未实际使用，或只记录发现而不修正。
- 虚构路径、契约、命令、代码或预期结果。
- 缺少完整 TDD、覆盖率、集成单元或三级门禁。
- 让执行器猜测任务归属、依赖、风险、所有权或并行隔离。
- 为精简删减必要行为/测试，或夹带无关重构。
- 把机械校验通过当成语义质量通过。

出现任一危险信号时，立即停止，修复计划并重新验证。
