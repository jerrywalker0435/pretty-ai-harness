## 共同规则

四阶段服务 Java/Spring 变更：

```text
[用户批准 PRD]
  -> [Design]
  -> [用户批准 Design]
  -> [Plan]
  -> [用户批准 Plan]
  -> [Execution：基线 -> TDD 切片 -> 最终验证 -> 自动审计 -> 交付]
```

- PRD、Design、Plan 各请求一次用户 Review 并停止；一句批准即可，不记录审批元数据。
- Execution 不增加人工审批或只读审计阶段；自动审计完成后按真实状态直接交付并停止。
- commit、push、MR、合并和发布均需用户另行授权。
- 下游发现上游合同错误时，停止当前阶段并返回最早受影响阶段；上游重新批准后，从首个受影响阶段恢复。
- 固定制品位于 `docs/pretty/<topic>/`；`<topic>` 使用小写 kebab-case。
- 固定文件为 `prd.md`、`design.md`、`plan.md`、`execution.md`，不创建代码附件、评审稿或日期副本。
- Git 历史负责版本记录；文档不维护签名、时间戳、审批人、哈希链、证据指纹或 Skill 调用清单。

PRD、Design 和 Plan 支持只读评审：严格不修改、移动或复制文档，不更新领域文档，不生成下游制品。PRD/Design 可评审用户给出的现有文档；只有标准路径才运行完整链路校验。Plan 只接受 `docs/pretty/<topic>/plan.md`，并要求同目录 PRD、Design 和可定位的真实源码；非标准路径不接受、不迁移、不复制。只读评审结论不等于用户批准。

## 澄清与阶段回退

PRD 与 Design 先调查仓库、协议、领域文档、配置、相邻行为和测试。只有以下条件同时成立时才使用 `grilling`：

1. 存在两个以上会产生不同结果的真实答案；
2. 答案会改变业务结果或高影响技术合同；
3. 仓库和既有文档无法唯一裁决；
4. 不解决就会迫使下游代做决定。

一次只解决一个决策，给出具体场景、2–3 个结果、主要后果和推荐答案。直接提出业务或技术决策，不要向用户复述触发判定或 Skill 编排状态；“需要确认一个外部合同”“唯一阻塞决策”“这是 `grilling` 要求关闭的”等内部分类不得成为提问的开场或收尾。确认结果写入 `REQ/AC` 或 `DEC`，不保存问答审计。

Plan 不调用 `grilling`：

- 业务结果不清楚，返回 PRD；
- 边界、契约、所有权、一致性或 `DEC` 不清楚，返回 Design；
- 仓库事实自行调查；
- 低风险、外部等价的实现由 Plan 推荐，随 Plan 一并交用户批准。

Plan 可以留下外部资源是否已经存在的运行时未知，不能留下实施决策未知。

## 领域模型一致性

根目录存在 `CONTEXT-MAP.md` 时，定位并读取相关 `CONTEXT.md`；否则读取根目录已有的 `CONTEXT.md`。文件不存在不默认创建，也不构成阻塞。

- **PRD：** 核心术语、业务身份、生命周期、状态、不变量、归属或关系发生新增、歧义或冲突并影响需求时，使用 `domain-modeling`；只维护领域语言，不创建 ADR。
- **Design：** 实体、值对象、业务身份、状态流转、不变量、聚合、数据所有权、上下文关系或领域事件发生变化时，使用 `domain-modeling`；按真实影响同步 `CONTEXT.md`、`CONTEXT-MAP.md` 和必要 ADR。若改变外部结果，先返回 PRD。
- **Plan 与 Execution：** 只消费并核对领域文档，不调用 `domain-modeling`，不得更新 `CONTEXT.md`、`CONTEXT-MAP.md` 或 ADR。

PRD/Design 的一次用户 Review 同时覆盖本阶段领域文档变更，不增加额外审批。只读评审发现领域问题时只报告，不修改。

## 阶段合同

### PRD

- 输入：用户目标、现有行为、约束和领域语言。
- 决定：问题、目标、非目标、用户场景、外部可观察规则和验收结果。
- 不决定：类、方法、模块职责、schema、事务边界或实现模式。
- 输出：`prd.md`，定义 `REQ` 与 `AC`。
- 完整性标准：两种合理实现若都满足 PRD 却产生不同外部结果，PRD 必须继续澄清。
- 只读评审输出：阻塞问题、建议改进、下游影响、`可进入 Design / 修正后再进入 Design`。

### Design

- 输入：已批准 PRD 和足以支持决策的仓库事实。
- 决定：模块职责、依赖方向、跨边界契约、数据与一致性、兼容策略、关键验证边界和剩余风险。
- 不决定：逐文件任务、私有 helper、完整实现、测试 fixture、Mock 操作或执行命令。
- 输出：`design.md`；高影响、可独立挑战的问题使用 `DEC`。
- 只读评审输出：阻塞问题、重要改进、上下游与 Plan 影响、`可进入 Plan / 修正后再进入 Plan`。

### Plan

- 输入：已批准 PRD、Design、领域文档和真实源码/API。
- 角色：约束性实施合同与可审查实现提案，既是代码事实前置 CR，也是 Execution 的事实依据。
- 决定：垂直 `TASK`、准确代码事实、继承约束、拟议变更、行为切片、UT 方案、基线、验证命令和完成证据。
- 不决定：新的业务结果或技术合同；不实施代码，不执行 RED/GREEN，不声称 TDD 已发生。
- 输出：单一 `plan.md`，覆盖全部 `REQ/AC/DEC` 的真实落点。
- 只读评审只接受标准路径，固定输出：阻塞问题、重要改进、代码事实与上下游偏差、执行与验证影响、`可进入 Execution / 修正后再进入 Execution`。运行至 Plan 的机械校验，失败仅作为发现。

### Execution

- 输入：已批准 Plan 及完整上游链。
- 执行：采集工作区归因、运行可控基线、逐行为切片 TDD、最终验证、自动审计和新鲜证据核对。
- 输出：真实代码差异与增量维护的 `execution.md`。
- 不决定：新的业务结果、Design 合同或 Plan 测试边界；不自动执行 Git 或发布动作。

## 文档结构与证据

### 固定章节

- PRD：背景与问题、目标与非目标、用户与场景、需求、验收标准、约束与未决问题。
- Design：输入与范围、设计摘要、现状与约束、方案与权衡、详细设计、验证策略、风险与回退。
- Plan：输入与范围、实施摘要、代码事实与约束、实施任务、测试与验证。
- Execution：输入与基线、执行摘要、任务证据、测试与验证结果、偏差与未验证范围、最终审计与结论。

简单变更仍保留固定章节，但内容可以极短；删除不适用的条件块，不生成空表、虚假候选、虚假 `DEC` 或形式化“无影响”。

### Design 阅读视图

- 所有 Design 提供 3–6 行摘要。
- 跨模块/服务、外部或异步链路、三个以上步骤，或状态/事务/并发/失败隔离复杂时，增加 fenced `text` ASCII 主流程图。
- ASCII 固定使用 `->`、`+-- 条件 -->`、`!->` 和 `[边界]`；不使用 Mermaid、PlantUML、Unicode 框线或绘图脚本。
- 两个以上高影响 `DEC` 时增加决策索引；存在跨团队契约时增加契约矩阵。
- 图、索引和矩阵只提供阅读入口，正文合同与 `DEC` 才是权威来源。

一个 `DEC` 只回答一个可独立挑战的问题，包含驱动因素与相关 `REQ`、真实候选或决定性证据、采用方案与理由、正负后果和重新评估条件。普通仓库事实、编码规范、映射或内部形状不伪装成 `DEC`。

### 团队证据

区分 PRD 要求、已核实仓库事实和设计/实施提案。同仓库事实使用仓库相对路径加 symbol、测试或配置键；跨仓库事实使用团队可访问的仓库标识或稳定文档。个人绝对路径、私有本地资料和调查日志不能充当团队事实。

### Plan 结构

复杂 Plan 提供 3–6 行实施摘要；两个以上 TASK 增加：

```text
TASK -> 可观察行为 -> 主要文件/模块 -> 风险 -> UT 边界
```

TASK 优先按可验证行为或独立风险垂直切分，不按 Controller/Service/Repository 技术层或 commit 大小切分。每个 TASK 按适用性包含：目标行为或风险闭环、追溯落点、已核实代码事实、继承约束、拟议变更、具名行为切片、验证入口、真实任务依赖和完成证据。行为切片使用 TASK 内唯一短名称，不新增 `STEP/CASE` 编号。TASK 只声明真实依赖，列表顺序不默认构成全序；外部环境不是 TASK 依赖。

所有 `REQ/AC/DEC` 必须有真实落点，但落点可以是生产代码、UT、跨任务门禁或不变边界验证。

Plan 的“代码事实与约束”只放决定性事实和共享约束；完整拟议文件与 symbol 放入所属 TASK。展示深度按风险选择：高风险算法、SQL、事务、并发、兼容、异常或复杂 UT 可以展示完整代码；DTO、getter、普通映射、import、改名和样板使用签名、关键片段或机械变更表。展示的签名、类型和片段必须与仓库一致、自洽；不得用省略号隐藏高风险逻辑。Plan 不要求所有代码可单独编译，不为测试暴露生产方法，也不引入无真实用途抽象。

改变职责、依赖方向、所有权、事务、跨模块合同或长期扩展点时返回 Design；改变业务结果时返回 PRD。

## UT-only 与验证声明

### 强制测试边界

Pretty 只能新增或扩展 UT，以速度、确定性和可重复性优先。禁止新增或扩展：

- 集成测试、契约测试和端到端测试；
- Spring slice；
- `@SpringBootTest`、`@WebMvcTest`、`@DataJpaTest`；
- Testcontainers、嵌入式数据库或其他本地基础设施测试。

仓库已有这些测试也不作为默认门禁。只有用户或仓库强制规则明确要求时才运行，但仍不授权新增或扩展。

UT 测试稳定业务行为单元，可以覆盖多个真实领域对象和纯内存协作者；不启动 Spring，不访问真实或嵌入式基础设施。边界外的 Repository、Gateway、Service、远程客户端、时钟和随机性可以 mock/fake/stub，包括本方接口；被测规则使用真实对象。主要断言业务结果、状态变化或完整边界请求，不以调用次数或顺序作为主要成功标准。UT 必须快速、确定、可并行且无机器环境依赖。

SQL、配置、文档、生成物和纯机械修改不制造 UT，使用静态解析、编译、搜索不变量或确定性脚本；无法验证时严格降低声明。

### Plan 使用 `tdd`

行为变更和 Bug 修复的 Plan **REQUIRED SUB-SKILL：** 使用 `tdd` 审查测试方案质量，但不编写测试、不执行 RED/GREEN。每个行为切片说明：

- UT 边界和 Given-When-Then 场景；
- 来自 `REQ/AC`、业务规则、协议样例或独立推导的预期值；
- mock/fake/stub 边界；
- 因目标行为缺失而出现的预期 RED 原因；
- 当前切片的最小 GREEN 条件；
- 可解析验证入口。

完整 UT 代码按风险选择性展开；多个切片可以复用按测试方法、类或模块集中定义的命令。用户批准 Plan 即确认这些测试边界，Execution 不逐项再问。

阶段文档统一使用“UT 边界”或“测试边界”，不使用英文同义术语，避免跨阶段映射漂移。

### Execution 使用 `tdd`

行为切片 **REQUIRED SUB-SKILL：** 使用 `tdd`：每次只落地一个 UT，确认正确 RED，再写当前切片最小 GREEN。GREEN 后检查明确整理目标；确需整理时在该切片内 **REQUIRED SUB-SKILL：** 使用 `refactor`，小步复验。没有整理目标时不记录形式化“不触发”。独立行为保持型重构先取得通过基线，使用 `refactor` 小步复验，不制造 RED。

UT 首次通过时立即停止该切片，检查断言有效性、现有实现和用户原改动：行为完整存在则记录“已满足（无生产差异）”并运行回归 UT；部分存在则只为缺失行为取得真实 RED；必须改变测试入口、预期或任务合同时返回 Plan。同一稳定入口、行为和预期下遗漏的输入或错误分支可直接补 UT 并执行真实 RED/GREEN；更换测试层级/入口、改变预期或新增验收语义时返回对应上游。

### 覆盖率

优先继承仓库明确政策。仓库没有政策时，对可由 UT 覆盖的新增或实质修改 Java 行为默认行覆盖率 90%、分支覆盖率 80%。现有工具只机械统计相对基线新增可执行行和分支；修改既有行为以针对性 UT 证明，不伪造修改行覆盖率。SQL、配置、文档、生成物和机械修改为不适用。覆盖率不能替代关键场景与失败路径，不能为了数字创建非 UT、弱断言或无价值测试。

### Pretty 内外验证

- **Pretty 内验证：** UT、mock/fake/stub、编译、快速静态检查、机械校验和适用覆盖率。
- **Pretty 外验证：** 真实数据库、真实服务、凭证、基础设施语义、部署、人工联调和独立 Reviewer。

Pretty 外验证能力可以尚不存在，不要求在 Plan 阶段确认，也不阻塞 Plan 或 Execution。Design 只识别风险和声明限制；Plan 继承限制；Execution 把未执行部分写入“未验证范围”，不记录负责人、期限或审批结果，不得把 UT 称为集成、契约、端到端、真实部署或真实基础设施验证。

## Execution 证据与自动审计

### 基线与工作区归因

1. 在临时目录保存执行开始 HEAD、staged、unstaged、untracked 范围和必要 diff；临时材料不进仓库。
2. 尚未创建或修改 `execution.md` 时运行 Plan 基线。
3. 基线通过后立即创建 Execution；基线失败时创建最小停止记录。
4. 后续逐切片增量维护，最终整理为可读证据账本。

Plan 基线默认覆盖受影响模块编译、相关现有 UT、必要快速静态检查和将修改的测试入口；不默认全仓测试、非 UT 测试或外部环境检查。任一基线命令失败，Execution 强制停止：不开始 TDD，不修改生产代码，不自动把失败纳入本次修复；记录命令、退出码、摘要和恢复条件。外部能力缺失不能进入可控基线，因此不是基线失败。

不要求洁净工作区，不自动 stash、reset 或覆盖用户内容。同一位置无法安全区分且有覆盖风险时停止。临时归因基线丢失时，仅在存在写入覆盖风险时停止；否则继续并声明归因限制。

### 增量任务证据

Execution 是允许修订的最终证据账本，不是追加式终端日志。每个 TASK 记录：结果、实际相对路径与 symbol、行为切片 RED/GREEN/实际重构证据、实质偏差和任务级完成证据。证据保留命令、退出码、预期/实际失败摘要与通过摘要，不复制完整日志。

TASK 状态只有：`完成`、`已满足（无生产差异）`、`停止`。最终状态只有：`完成`、`停止：<原因>`、`返回 Plan / Design / PRD：<原因>`。

只记录实质偏差：文件/symbol、任务/切片、测试边界或命令、有意义的等价实现、未实施/必要新增内容和外部未验证范围。格式、import、局部变量等不记录。等价调整直接执行并记录；改变 Plan 返回 Plan，改变 `DEC` 返回 Design，改变业务结果返回 PRD。

多个任务中途停止时保留已完成证据，当前任务停止，后续任务标记未执行，最终不能写“部分完成”。上游修订获批后，从首个受影响任务恢复。

### 最终验证与自动审计

最终验证默认运行：受影响模块编译、本次全部新/改 UT、直接相关回归 UT、快速静态检查和适用新增代码覆盖率。不默认全仓测试或已有非 UT 测试。真实 diff 扩大影响范围时补跑新增范围，只声明“受影响范围通过”。

全部任务和最终验证完成后，当前 Agent 自动审计一次稳定最终版本。独立 Agent/Reviewer 是可选增强，不可用不阻塞。自动审计只检查，不在审计动作中直接实现或重构，核对：

- 最终 diff 与 TASK 归属；
- `REQ/AC/DEC/Plan` 一致性；
- RED/GREEN 与真实代码、测试和命令证据；
- 基线、编译、UT、覆盖率和静态证据；
- 实质偏差与验证声明；
- 代码质量、安全、异常、事务和兼容风险。

行为错误返回对应 TDD 切片；行为保持结构问题返回切片使用 `refactor`；超出合同返回上游。修正、复验后对新的稳定最终版本重新审计。审计一次通过且无影响验证的变化，不重复同一审计或命令。

有生产代码差异时使用 `clean-code-guard`；有 Java 生产代码差异时再使用 `java-code-review`。无生产代码差异时只核对任务、证据和声明。

最终顺序：

```text
[完成切片并更新任务证据]
  -> [最终验证]
  -> [自动审计]
       +-- 有问题 --> [返回切片或上游，修正、复验、重审]
  -> [superpowers:verification-before-completion 核对证据新鲜度]
  -> [写最终审计与结论]
  -> [校验最终 execution.md]
  -> [交付]
```

`superpowers:verification-before-completion` 不机械执行第三轮相同命令；只核对证据是否仍新鲜，审计后发生相关变化时重跑受影响范围。最终审计用“发现 -> 证据 -> 影响 -> 修正/处置 -> 复验”记录；无发现时写明真实核对范围和依据。

## 质量 Skill 路由

| 阶段            | 触发场景 | 使用 |
  |-----------------| --- | --- |
| PRD/Design      | 发生共享合同定义的领域模型变化 | `domain-modeling` |
| Design/Plan     | 对象职责、封装、聚合、组合或继承变化 | `121-java-object-oriented-design` |
| Design/Plan     | 值对象、泛型、类型层次、金额类型或 primitive obsession | `122-java-type-design` |
| Design/Plan     | 服务职责、端口、依赖方向或扩展点变化 | `solid-principles` |
| Design/Plan     | 模块接口深度、seam、adapter 或测试表面需要设计 | `codebase-design` |
| Design/Plan     | 已选定模块存在多个实质不同的合理接口形状 | `codebase-design` 的 `DESIGN-IT-TWICE.md` |
| Design/Plan     | 已证明存在构造、替换、通知或适配变化轴 | `design-patterns` |
| Plan            | 审查行为测试方案 | `tdd` |
| Execution       | 实施行为切片 | `tdd` |
| Execution       | 独立行为保持重构或切片内确需整理 | `refactor` |
| Execution       | 最终存在生产代码差异 | `clean-code-guard` |
| Execution       | 最终存在 Java 生产代码差异 | `java-code-review` |
| Execution       | 自动审计后声明完成 | `superpowers:verification-before-completion` |

JUnit 5、Mockito、AssertJ 等写法遵循 `tdd` 和最佳实践，并兼容仓库实际依赖版本，不盲目继承仓库坏习惯。纯 SQL、配置、部署、文档和机械变更不强制 Java/OOD Review。专项 Skill 的有效发现写入事实、决策、任务或最终审计，不保留调用清单。

## 依赖缺失

- 当前阶段无替代能力的必需 Skill 缺失时停止并说明。
- `domain-modeling`、对象/类型/SOLID/接口/模式等能力仅在真实风险命中时必需。
- `tdd` 对行为 Plan 和行为 Execution 必需。
- `refactor` 只在独立重构或实际整理时必需；没有整理目标时不加载。
- `clean-code-guard`、`java-code-review` 只按最终真实生产代码差异触发。
- 独立 Reviewer 不属于必需依赖。
