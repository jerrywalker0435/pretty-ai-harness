# Java/Spring 专项质量检查

只检查与当前变更相关的项目。遵循仓库健康惯例，不强制固定架构。

## Design 与 Plan

- Controller 只做协议转换、输入校验和响应映射；业务规则有明确归属。
- 使用构造器注入；依赖指向稳定业务边界，避免循环依赖和隐藏实例化。
- 事务边界覆盖一个完整业务用例；明确回滚、并发、锁、幂等与重试语义。
- DTO、领域对象和持久化对象按真实边界分离，避免无收益的逐层复制。
- 在 HTTP、消息、反序列化等信任边界执行 Bean Validation 或等价校验。
- 明确 Repository 查询规模、分页、批量操作、N+1 和索引影响。
- 异常保留原因与上下文，并稳定映射为外部错误契约。
- 日志不泄露凭证、个人信息或完整敏感载荷；关键失败具备必要上下文。
- 选择满足当前需求的最简单结构；没有第二个现实实现时不引入接口、工厂或策略。

## 测试分层

- 领域和业务规则：不启动 Spring 的快速单元测试。
- Controller/API：`@WebMvcTest` 或等价 MockMvc slice。
- Repository、SQL、事务：`@DataJpaTest`，需要真实数据库语义时使用 Testcontainers。
- 跨层关键链路：少量 `@SpringBootTest`。
- 外部系统：契约测试或可控 stub/container。
- 测试业务结果、状态和外部契约；不要只验证 Mockito 调用次数。

## 覆盖率

- 新增生产代码：行覆盖率至少 90%，分支覆盖率至少 80%。
- 修改遗留行为：必须有针对本次变化的特征或回归测试。
- 未触碰历史代码：不要求补测，也不要求提高模块或全仓覆盖率。
- 金额、权限、状态流转、幂等和事务一致性按行为矩阵覆盖关键路径。
- 覆盖率不能替代有意义的断言、边界测试或错误路径测试。
